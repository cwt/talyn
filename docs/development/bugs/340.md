# BUG-340 — Dispatching `Future` done callbacks after `loop.close()` dereferences freed `ready_tasks_queues` (use-after-free)

- **Status**: ✅ Fixed (2026-10-18) — `Future.Callback.call_done_callbacks` and `z_future_add_done_callback` now check `loop.initialized` before dispatching to `ready_tasks_queues`, releasing queued callback references and raising `RuntimeError("Event loop is closed")`
- **Severity**: 🔴 Critical — deterministic use-after-free or `RuntimeError: Event loop is closed` fail-miss when resolving/cancelling a `Future` or adding a done callback to a completed `Future` after `loop.close()`
- **Category**: Use-After-Free (UAF)
- **Files**:
  - `src/future/callback.zig:227-251`
  - `src/future/python/callbacks.zig:64-90`
- **Related**: [Lesson 19](../lessons/01-event-loop-and-lifecycle.md), [BUG-116](116.md)

## Overview & Root Cause

When `loop.close()` runs (`Loop.release()` in `src/loop/main.zig:189-243`), `self.ready_tasks_queues.deinit()` frees the underlying `DynamicRingBuffer` storage and sets `self.initialized = false`. However, `FutureObject` still holds a Python reference to `LoopObject`, keeping the `Loop` struct allocation alive.

1. In `src/future/callback.zig:227-251`, `call_done_callbacks` does not check `if (!self.loop.initialized)` before calling `Loop.Scheduling.Soon.dispatch_guaranteed`:

```zig
pub fn call_done_callbacks(self: *Future) !void {
    if (self.callbacks_queue.items.len == 0) {
        return;
    }
    ...
    Loop.Scheduling.Soon.dispatch_guaranteed(self.loop, self.callbacks_queue.items);
    self.callbacks_queue.clearRetainingCapacity();
}
```

`Soon.dispatch_guaranteed` (`src/loop/scheduling/soon.zig:26`) unconditionally calls `loop.ready_tasks_queues.append_many(callbacks)` on the deinitialized `DynamicRingBuffer`, writing into freed memory or re-allocating a leaked ring buffer after loop teardown.

2. In `src/future/python/callbacks.zig:64-90`, `z_future_add_done_callback` on an already-finished `Future` calls `Loop.Scheduling.Soon.dispatch(future_data.loop, &[_]CallbackManager.Callback{callback_data})` without checking `if (!future_data.loop.initialized)`, instead of raising `RuntimeError("Event loop is closed")` as required by `asyncio`.

## Trigger Scenario

1. Create a `Future` `fut = loop.create_future()` and register `fut.add_done_callback(cb)`.
2. Close the loop with `loop.close()`.
3. Call `fut.cancel()` or `fut.set_result(1)` (or call `done_fut.add_done_callback(cb)` on an already-resolved future).
4. `call_done_callbacks` / `z_future_add_done_callback` pushes to the already-deinitialized `loop.ready_tasks_queues`.

## Proposed Remediation

1. In `Future.Callback.call_done_callbacks` (`src/future/callback.zig:227`), check `if (!self.loop.initialized)`: if the loop is closed, release the pending callbacks in `self.callbacks_queue` via `release_callbacks_queue(self)` and return `error.LoopClosed` (raising `RuntimeError("Event loop is closed")`).
2. In `z_future_add_done_callback` (`src/future/python/callbacks.zig:64`), check `if (!future_data.loop.initialized)` before scheduling or appending callbacks, raising `RuntimeError("Event loop is closed")`.
