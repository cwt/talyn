# BUG-242 — `PyFloat_AsDouble` NaN/Inf silently accepted in DNS timeout parsing

- **Status**: 🔴 Open
- **Severity**: 🟡 Medium — Invalid syscall arguments / kernel -EINVAL
- **File**: `src/loop/python/io/socket/getaddrinfo.zig:183`, `src/loop/python/io/socket/getnameinfo.zig:118`, `src/loop/python/io/datagram/create_endpoint.zig:135,163,188,222`, `src/loop/python/io/server/create_server.zig:280`
- **Lessons**: [Security §Lesson 34 — Parser Strictness](../lessons/09-security-and-input-validation.md), [BUG-185](0185.md) (kernel -EINVAL from unnormalized nanoseconds), [BUG-241](0241.md) (same class of bug in happy eyeballs delay)
- **Description**: Across 5 files and 7 call sites, DNS timeout values are parsed with:

  ```zig
  const timeout_val = python_c.PyFloat_AsDouble(py_timeout);
  const result: ?Resolv.DnsTimeout = if (timeout_val == -1.0 and python_c.PyErr_Occurred() != null)
      null
  else
      Resolv.timeout_from_secs(timeout_val);
  ```

  This pattern correctly catches the case where `PyFloat_AsDouble` returns `-1.0` **and** sets a Python error — which happens for invalid numeric strings like `"abc"`. However, `PyFloat_AsDouble` also returns `-1.0` and sets an error for **NaN** and **Infinity** inputs (e.g., `float("nan")`, `float("inf")`). The epsilon-style check conflates the error return value with the user sentinel `-1.0`, so:

  1. **NaN/Inf inputs**: `PyFloat_AsDouble` returns `-1.0` and sets an error. The condition `timeout_val == -1.0 and PyErr_Occurred() != null` is `true`, so the code returns `null` (default 5s timeout). This is **actually correct behavior** — it silently converts invalid input to the default timeout rather than raising.
  
  2. **The real issue**: For inputs that produce **actual NaN or Inf values** (not just `-1.0` sentinel), the check passes through to `timeout_from_secs`. For example, if a user passes `float("inf")`, `PyFloat_AsDouble` returns `inf` (not `-1.0`) and sets an error. The condition `timeout_val == -1.0` is `false`, so the error check is skipped, and `timeout_from_secs(inf)` computes `sec = floor(inf) = inf`, which overflows when cast to `u64`.

  Wait — let me re-check. `PyFloat_AsDouble("inf")` returns `inf` and sets an error. The condition `timeout_val == -1.0` is `false`, so the `else` branch runs: `Resolv.timeout_from_secs(inf)`. In `timeout_from_secs`:
  ```zig
  const sec: i64 = @floor(timeout_secs);  // floor(inf) = inf — but this overflows i64!
  ```
  Actually, `@floor(inf)` returns `inf` as f64, and `@intCast(inf)` to i64 is **undefined behavior** in Zig — it will panic in Debug and produce garbage in Release.

  3. **The actual bug**: For `float("nan")`, `PyFloat_AsDouble` returns `NaN` (not `-1.0`) and sets an error. Same path — `timeout_from_secs(NaN)` computes `@floor(NaN) = NaN`, and `@intCast(NaN)` is UB.

  The bug is that the `timeout_val == -1.0 and PyErr_Occurred() != null` check only catches the *specific case* where the error return value happens to be `-1.0`. It does **not** catch all error cases. Any NaN or Inf input bypasses the error check entirely.

- **Trigger**: User passes `float("nan")` or `float("inf")` as `dns_timeout` to any of: `getaddrinfo`, `getnameinfo`, `create_connection`, `create_datagram_endpoint`, or `create_server`.
- **Consequences**: 
  - Debug builds: Zig `@intCast` panic on NaN/Inf → process abort.
  - Release builds: Undefined behavior from `@intCast(NaN/Inf)` → wrapped-around timespec values → io_uring timeout SQE with garbage values → kernel may reject with `-EINVAL` or accept an enormous timeout.
- **Fix**: Separate the error check from the sentinel check:
  ```zig
  const timeout_val = python_c.PyFloat_AsDouble(py_timeout);
  if (python_c.PyErr_Occurred() != null) return error.PythonError;
  if (timeout_val == -1.0) break :blk null;  // explicit sentinel
  const result = Resolv.timeout_from_secs(timeout_val);
  ```
  This must be applied to all 7 call sites across the 5 files.
- **Related**: BUG-241 (same `PyFloat_AsDouble` class of bug in happy eyeballs delay parsing).
