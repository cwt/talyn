# BUG-377 — `transport_write_lines` does not check `PyErr_Occurred()` after `PyIter_Next` returns `null`, returning `Py_None` with a live exception set (unfixed `BUG-298`)

- **Status**: ✅ Fixed
- **Severity**: 🔴 High — returning a non-null `PyObject` (`Py_None`) from a C function while an exception is set on the CPython thread state violates CPython's core C-API invariant (`SystemError` in debug builds, silent exception corruption in release builds)
- **Category**: Logic Bug (CPython Exception State Corruption / Regression of [BUG-298](298.md))
- **Files**:
  - `src/transports/stream/write.zig:168-189`
- **Related**: [BUG-298](298.md), [Lesson 47](../lessons/05-python-c-api-correctness.md)

## Overview & Root Cause

In `src/transports/stream/write.zig:168-189`, `transport_write_lines` iterates over `iter` using `PyIter_Next`:

```zig
var new_buffer_size: usize = 0;
while (true) {
    const py_buffer: PyObject = python_c.PyIter_Next(iter) orelse break;
    defer python_c.py_decref(py_buffer);

    new_buffer_size = write_transport.append_new_buffer_to_write(py_buffer) catch |err| {
        return utils.handle_zig_function_error(err, null);
    };
}

if (new_buffer_size >= instance.writing_high_water_mark) {
    if (instance.is_writing) {
        instance.is_writing = false;

        if (instance.protocol_pause_writing) |cb| {
            const ret = python_c.PyObject_CallNoArgs(cb) orelse return null;
            python_c.py_decref(ret);
        }
    }
}

return python_c.get_py_none();
```

In CPython, `PyIter_Next(iter)` returns `null` both when the iterator is exhausted (no exception set) **and** when `iter.__next__()` raises an exception (exception set on thread state).
Although [BUG-298](298.md) was marked `Fixed` in the bug tracker, the fix is not present in `src/transports/stream/write.zig`: after `while (true)` breaks on `orelse break`, `transport_write_lines` never checks `if (python_c.PyErr_Occurred() != null) return null;`!
Instead, it optionally calls `PyObject_CallNoArgs(cb)` (with a live exception set!) and returns `python_c.get_py_none()` (`Py_None`) with the iterator's exception still pending on the CPython thread state!

## Trigger Scenario

Pass a generator that raises an exception to `transport.writelines(gen())`. `PyIter_Next` sets the exception and returns `null`, `transport_write_lines` returns `Py_None` with the exception still active on the thread state, and CPython raises `SystemError: <method 'writelines' of 'talyn.StreamTransport' objects> returned a result with anexception set` (or attributes the exception to the next C-API call).

## Proposed Remediation

Immediately after the `while (true)` loop in `transport_write_lines` (`src/transports/stream/write.zig:176`), check `PyErr_Occurred()`:

```zig
if (python_c.PyErr_Occurred() != null) {
    return null;
}
```


## Resolution (2026-10-19)

Confirmed live exactly as described (the code evolution since BUG-298
kept the `orelse break` loop once again without the check) and fixed:
`transport_write_lines` (`src/transports/stream/write.zig`) now checks
`PyErr_Occurred()` right after the iteration loop and returns
`null` (letting the generator's exception propagate) instead of
`Py_None` with a live exception set.

The high-water-mark / `pause_writing` branch after the loop is also no
longer reachable with a pending exception, so `pause_writing` cannot
be invoked under one either (that secondary corruption route from the
report's overview is covered by the same early return).

from the C method; pre-fix the boundary elevated it to
`SystemError: <method 'writelines' of 'talyn.StreamTransport' objects>

(observed in the bite log). Post-fix: 131/131 zig tests, 442 passed +
