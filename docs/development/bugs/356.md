# BUG-356 — Leaked callback structs/buffers on `orelse return set_future_exception` and unresolved futures (infinite hang) on `try` / `cancelled()` across all 7 socket operations in `ops.zig`

- **Status**: ✅ Fixed (2026-10-18)
- **Severity**: 🔴 High — affects all 7 `loop.sock_*` operations (`sock_accept`, `sock_connect`, `sock_recv`, `sock_recv_into`, `sock_recvfrom`, `sock_sendto`, `sock_sendall`), causing either memory/`Py_buffer`/reference leaks or unresolved futures that hang coroutines forever
- **Category**: Memory/Ref Leak & Logic Bug (Infinite Hang)
- **Files**:
  - `src/loop/python/io/socket/ops.zig:39-111, 196-222, 310-340, 434-479, 574-610, 716-747, 925-957`
- **Related**: [Lesson 28](../lessons/02-zig-and-memory.md), [Lesson 41](../lessons/05-python-c-api-correctness.md)

## Overview & Root Cause

All 7 socket completion callbacks in `src/loop/python/io/socket/ops.zig` (`sock_accept_callback`, `sock_connect_callback`, `sock_recv_callback_with_buf`, `sock_recv_into_callback_with_buf`, `sock_recvfrom_callback`, `sock_sendto_callback`, and `sock_sendall_callback`) follow the same flawed cleanup pattern:

```zig
fn sock_recv_callback_with_buf(data: *const CallbackManager.CallbackData) !void {
    const d: *SockRecvData = @ptrCast(@alignCast(data.user_data.?));
    var success = false;
    defer if (success) cleanup_sock_recv(d);

    if (data.cancelled()) return;

    const err = data.io_uring_err();
    if (err != .SUCCESS) {
        const errno_val: c_int = @intCast(@intFromEnum(err));
        const exc = python_c.PyObject_CallFunction(python_c.PyExc_OSError, "is\x00", errno_val, "sock_recv failed\x00") orelse return set_future_exception(error.PythonError, d.future);
        defer python_c.py_decref(exc);
        const future_data = utils.get_data_ptr(Future, d.future);
        try Future.Python.Result.future_fast_set_result_or_exception(future_data, null, exc);
        success = true;
        return;
    }

    const res: usize = @intCast(data.io_uring_res());
    const py_bytes = python_c.PyBytes_FromStringAndSize(@ptrCast(d.buf.ptr), @intCast(res)) orelse return set_future_exception(error.PythonError, d.future);
    defer python_c.py_decref(py_bytes);

    const future_data = utils.get_data_ptr(Future, d.future);
    try Future.Python.Result.future_fast_set_result(future_data, py_bytes);
    success = true;
}
```

This pattern fails in three ways across all 7 callbacks:

1. **Leak of `d` (struct, heap buffer, `Py_buffer`, `future` ref, `loop` ref) on every `orelse return set_future_exception(...)`**:
   Because `set_future_exception` returns `void` (not a Zig error), `orelse return set_future_exception(error.PythonError, d.future)` returns normally (`void`) from the callback while `success` is still `false`!
   - Because `success == false`, `defer if (success) cleanup_...(d)` does **not** run.
   - Because the callback returned `void` (not an error), `CallbackManager` does **not** run the `.cleanup` callback either!
   - Thus `d` (including its 64 KB buffer in `sock_recv`/`sock_recvfrom`, its `Py_buffer` pin in `sock_recv_into`/`sock_sendto`/`sock_sendall`, or the accepted client `fd` in `sock_accept_callback` at lines 59–102) is permanently leaked!

2. **Leak of `d` and unresolved `d.future` when `if (data.cancelled()) return;` is taken**:
   When `data.cancelled()` is true (lines 44, 201, 315, 439, 579, 721, 930), the callback returns `void` with `success == false`. Note that in `IO.deinit()` (`src/loop/scheduling/io/main.zig:847-853`), `release_ring_buffer` calls `cleanup` only after `func` returns; if `data.cancelled()` is triggered outside `release_dynamic_ring_buffer`, `d` is not cleaned up, and `d.future` is never cancelled or given an exception.

3. **Unresolved `d.future` (infinite hang) when `try` returns an error (e.g. `try utils.PseudoSocket.fast_new_pseudosocket(...)` at line 60 or `try address_to_python(...)` at lines 70 and 602)**:
   In `sock_accept_callback` (lines 60, 70) and `sock_recvfrom_callback` (line 602), if `try` returns an error, `CallbackManager` invokes `cleanup_accept` / `cleanup_sock_recvfrom` (which frees `d` and decrefs `d.future`) **without** calling `set_future_exception` on `d.future`! Additionally, in `sock_accept_callback`, the accepted client socket descriptor `res_fd` (`data.io_uring_res()`) is **never closed** if lines 60, 70, 99, or 102 fail, leaking the accepted socket `fd`!

## Trigger Scenario

1. Call `await loop.sock_accept(server_sock)` when `PseudoSocket` or `address_to_python` fails -> `res_fd` is leaked and the caller awaiting `sock_accept` hangs forever because `d.future` is never resolved.
2. Call any `loop.sock_*` method when `PyBytes_FromStringAndSize` / `PyLong_FromLong` / `PyTuple_Pack` fails -> `orelse return set_future_exception(...)` returns `void` with `success == false`, leaking `d` and any pinned `Py_buffer` or heap buffer.

## Proposed Remediation

1. Replace the `var success = false; defer if (success) cleanup_...(d);` pattern with an unconditional `defer cleanup_...(d);` inside a `z_sock_*_callback(d)` helper (and set `.cleanup` to a separate function that only runs if the callback was cancelled before execution, or check `if (data.cancelled()) { cleanup_...(d); return; }`).
2. In `sock_accept_callback`, add `var owns_res_fd = true; errdefer if (owns_res_fd) { _ = std.os.linux.close(res_fd); };` until `PseudoSocket` takes ownership of `res_fd`, and catch all errors to call `set_future_exception(err, d.future)`.

## Resolution (2026-10-18)

All 7 completion callbacks in `src/loop/python/io/socket/ops.zig` were restructured:

1. `var success = false; defer if (success) cleanup_x(d);` → **unconditional `defer cleanup_x(d);`** (and in `sock_sendall_callback`, `var requeued = false; defer if (!requeued) cleanup_sendall(@ptrCast(sd));` so partial writes that successfully re-queue the remaining slice keep `sd` and `sd.data` alive for the next SQE while still cleaning up on terminal completion, error, or re-queue failure) — every terminal exit path releases the callback state.
2. The manager-side `.cleanup = &cleanup_x` registrations were **nulled** (the manager only ran them on error returns, which would double-free against the unconditional defer). This also fixes the loop-close drain path (`release_dynamic_ring_buffer` never invoked `.cleanup` at all).
3. The cancelled branch resolves a still-pending future with `RuntimeError("Socket operation cancelled")` instead of returning silently (unresolved future / hang), and the `io_uring_err != .SUCCESS` branches guard `future_fast_set_exception` with `if (future_data.status == .pending)` so user-cancelled socket futures do not raise `InvalidStateError`.
4. Every `orelse return set_future_exception(...)` and `orelse return error.PythonError` / `try` site in the callbacks now calls `ensure_exception(...)` (raise if no exception pending — it silently no-oped otherwise, leaving the future pending forever) and resolves the future via `set_future_exception` instead of a bare error return. In `sock_accept_callback` the accepted client fd is closed by the existing `owns_fd` defer on every failure path, and the future is resolved (previously both leaked/hung).

Note the `ensure_exception` helper mirrors the BUG-355 fix in `create_endpoint.zig`.

Test (`tests/test_socket_ops.py::test_bug356_accept_recvfrom_no_leak`): 100 accept/recv echo + sendto/recvfrom cycles leave `sys.getallocatedblocks()` flat. Passes on 3.13/3.13t/3.14/3.14t.
