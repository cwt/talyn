# BUG-258 — DNS cache TTL cap misses near-max values

- **Status**: ✅ Fixed
- **Severity**: 🟡 Medium — DNS cache correctness / TTL capping mandate
- **Files**: `src/loop/dns/cache.zig`
- **Lessons**: [Security §DNS](../lessons/09-security-and-input-validation.md)
- **Description**: `set_resolved_data` (line 41), `set_ptr_data` (line 47), and `create_new_record_from_resolved` (line 113) all compute `const effective_ttl: i64 = if (ttl < std.math.maxInt(u32)) @intCast(ttl) else 60;`. The cap only fires when `ttl == 4294967295`. Any value **below** the sentinel — e.g. `4294967294` (≈ 136 years) — is stored **uncapped**, so the cache entry lives for the lifetime of the process. This is an incomplete fix of BUG-176 (Infinite DNS TTL when `ttl == maxInt(u32)`), which only handled the exact sentinel; the TTL-capping mandate is violated for all near-max values.
- **Trigger**: A nameserver (or a poisoned response) returning a TTL just below `2^32 - 1`.
- **Consequences**: Effectively permanent cache poisoning of a resolved address for the process lifetime; eviction only by LRU capacity (1024) or explicit expiry.
- **Resolution**: Cap to a hard ceiling at all three sites, e.g. `const MAX_DNS_TTL: i64 = 86400 * 7; const effective_ttl = @min(@as(i64, ttl), MAX_DNS_TTL);`.
- **Verification**: Unit test with `ttl = 4294967294` asserting `expire_at` is within ~7 days, not ~136 years (extend the existing `maxInt TTL caps at 60s` test).
