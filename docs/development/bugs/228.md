# BUG-228 — WriteTransport parent_transport refcount imbalance across completion paths

- **Status**: ✅ False Positive
- **Severity**: 🟠 Medium-High — Reference count leak or underflow
- **File**: `src/transports/write_transport.zig:138-230` (write_operation_completed), `src/transports/write_transport.zig:195-205` (submit_next_chunk)
- **Lessons**: [Memory §Lesson 107 — Balancing Reference Increments in Asynchronous Completion Callbacks](../lessons/01-memory-and-reference-counting.md)
- **Description**: `submit_next_chunk` (line ~202) unconditionally calls `python_c.py_incref(self.parent_transport)` before queuing the write. The completion callback `write_operation_completed` uses a `defer if (success) python_c.py_decref(self.parent_transport)` pattern. However, `success` is set to `true` on the cancellation path (line ~145) and on the final-complete path (line ~220), but **not** on the partial-write path where `submit_next_chunk` is called recursively (line ~210).

  On the partial-write path: `success = false`, the function returns `error.PythonError` or calls `submit_next_chunk` and falls through — but if `submit_next_chunk` succeeds, the deferred cleanup never runs because `success` remains `false`. This leaks one reference per partial write chunk.

- **Trigger**: Any multi-chunk write where `buffer_size > 0` after a partial write completion and `submit_next_chunk` is called recursively.
- **Consequences**: Reference count leak on every partial write chunk — parent transport is never fully released, leaking the `StreamTransportObject` and all its Python references.
- **Fix**: Set `success = true` before the recursive `submit_next_chunk` call on line ~210, so the deferred cleanup fires. Alternatively, restructure to use `errdefer` for the release instead of a conditional `defer`.
