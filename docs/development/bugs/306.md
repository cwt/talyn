# BUG-306 — `link()` loses one signal occurrence if it arrives before the mask blocks it

- **Status**: 🟡 Open
- **Severity**: 🟢 Medium-Low — Single-event loss through a narrow setup window; worst case is a lost Ctrl+C (SIGINT) once per `add_signal_handler` call
- **Files**:
  - `src/loop/unix_signals.zig:141-160` (`link()`: handler installed :143, mask blocked :147, signalfd re-masked :150)
  - Distinct from fixed BUG-57 (`unlink()` failing to restore default disposition/mask)
- **Lessons**: [Concurrency & Thread Safety](../lessons/02-concurrency-and-thread-safety.md), [Defensive Programming](../lessons/10-defensive-programming-and-code-quality.md)
- **Description**: POSIX delivery semantics require the disposition to exist BEFORE the signal is blocked; otherwise a signal raised by an unblocked thread between handler installation and `sigprocmask(SIG_BLOCK)` executes the just-installed no-op `dummy_signal_handler` and disappears. The event neither raises Python's KeyboardInterrupt nor lands on the signalfd. For SIGINT specifically, Python owned the disposition prior to talyn linking, so pre-link behavior was working — this makes the silent drop user-visible rather than theoretical. The correct order is: block first → install dummy → open/re-mask signalfd → (optionally) drop any pending occurrence via `sigtimedwait` while transitioning.
  - Mirror shape in `unlink()` (:175 unblock precedes :179 default-handler install) is negligible: removal from talyn handling is the requested outcome and regression would surface only via the restore itself.
- **Trigger**: Any `loop.add_signal_handler(...)` racing with the corresponding signal being sent — e.g., the test harness or supervision code sending SIGTERM immediately after registering its handler.
- **Consequences**: One signal occurrence per link call can be lost entirely; no exception, no queue entry, no signalfd wakeup.
- **Proposed fix**: Reorder within `link()` to block→handler→signalfd→enqueue, keeping the siginterrupt restoration unchanged.
