# BUG-333 — `IOSQE_ASYNC` on `IORING_OP_TIMEOUT` causes `timeout_remove` failure, handle leaks, and quadratic latency degradation

- **Status**: ✅ Fixed (2026-09-25)
- **Severity**: 🔴 High — any service cancelling timers (e.g. `asyncio.wait_for`, connection read timeouts, throttlers) leaked 100% of cancelled `TimerHandle` objects and experienced severe progressive latency degradation (40x–400x slowdown over time), spending >94% CPU in `io_uring_enter`.
- **Files**:
  - `src/loop/scheduling/io/timer.zig:41` (removed `sqe.flags |= IOSQE_ASYNC`)
  - `src/loop/scheduling/io/read.zig:39,121` (removed `timeout_sqe.flags |= IOSQE_ASYNC`)
  - `src/loop/scheduling/io/write.zig:32,98,157` (removed `timeout_sqe.flags |= IOSQE_ASYNC`)
  - `tests/loop/test_loop_scheduling.py` (added regression test `test_call_later_cancel_no_leak_or_degradation`)
- **Discovered by**: Investigation of progressive slowdown in Wormhole proxy (`../wormhole`) when running with Talyn as its event loop.

## Symptoms & Impact

In applications like Wormhole that make heavy use of `asyncio.wait_for` (e.g., idle connection timeouts of 300s, request header timeouts of 5s) and `loop.call_later` throttlers:
1. Every cancelled timer leaked its `talyn.Handle`, `contextvars.Context`, and callback references.
2. Latency of timer operations and loop steps degraded quadratically over time. In microbenchmarks, 10 batches of 5,000 `call_later(300.0) + cancel()` degraded from **0.054s to 2.198s (over 40x slowdown)**.
3. CPU profiling showed 94% of CPU time consumed inside `{method 'cancel' of 'talyn.Handle' objects}` -> kernel `io_uring_enter`.

## Root Cause

1. `IORING_OP_TIMEOUT` and `IORING_OP_LINK_TIMEOUT` are non-blocking kernel hrtimers managed in-memory by `io_uring`. Setting `IOSQE_ASYNC` forced the kernel to offload timeout insertion to an `io-wq` worker thread.
2. When Python called `handle.cancel()`, `Cancel.perform_timer` queued `IORING_OP_TIMEOUT_REMOVE` with `timeout_user_data = task_id`.
3. Because the `timeout` was offloaded asynchronously to `io-wq`, `io_timeout_remove` ran before the timer had been added to `ctx->timeout_list`, returning `-ENOENT` (-2).
4. The timeout was therefore never cancelled in the kernel and remained active until its full duration (e.g., 300 seconds) elapsed.
5. In user space, `fetch_completed_tasks` never received a completion CQE for the cancelled timer. Consequently:
   - `callback_for_python_generic_callbacks` never ran.
   - `python_c.py_decref(handle)` was never called -> memory leak.
   - `BlockingTasksSet` slots were never returned to `free_slots`, leading to `busy_sets` allocation churn.
6. In kernel space (`io_uring/timeout.c`), `ctx->timeout_list` accumulated thousands of uncancelled timers. Every subsequent `timeout_remove` and timer check iterated this list linearly, resulting in $O(N^2)$ cumulative CPU cost in `io_uring_enter`.

## Fix

Removed the erroneous `IOSQE_ASYNC` flag from `Timer.wait` (`src/loop/scheduling/io/timer.zig`), as well as from `link_timeout` calls in `src/loop/scheduling/io/read.zig` and `src/loop/scheduling/io/write.zig`.

With `IOSQE_ASYNC` removed:
1. The kernel arming of the timeout occurs synchronously in submission order.
2. `IORING_OP_TIMEOUT_REMOVE` immediately matches the timeout in `ctx->timeout_list`.
3. Kernel emits CQE for `TIMEOUT_REMOVE` (`res = 0`) and CQE for `TIMEOUT` (`res = -ECANCELED`).
4. User space reaps the cancelled timer CQE, frees the `BlockingTask` slot, and decrefs the Python handle.
5. Zero memory leak and flat $O(1)$ latency: 5,000 cancels take ~5ms across all batches with 0% degradation.
