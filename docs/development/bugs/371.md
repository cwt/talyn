# BUG-371 — `Task.cancel()`, `Task.uncancel()`, and `Task.cancelling()` state machine bugs breaking Python 3.11+ `asyncio.TaskGroup` and `asyncio.timeout`

- **Status**: ✅ Fixed
- **Severity**: 🔴 High — breaks Python 3.11+ structured concurrency (`asyncio.TaskGroup`, `asyncio.timeout`) and drops `task.cancel()` calls when the awaited `Future` resolved in the same tick
- **Category**: Logic Bug (Task Cancellation State Machine)
- **Files**:
  - `src/task/cancel.zig:45-58, 82-98`
- **Related**: [Lesson 19](../lessons/01-event-loop-and-lifecycle.md)

## Overview & Root Cause

In `src/task/cancel.zig`, there are three bugs in the `Task` cancellation state machine:

1. **`fast_task_cancel` drops cancellation when `instance.fut_waiter` is already `.finished` (`src/task/cancel.zig:45-58`)**:
   ```zig
   if (instance.fut_waiter) |fut_waiter| {
       if (python_c.type_check(fut_waiter, Future.Python.FutureType)) {
           const fut_waiter_obj: *FutureObject = @ptrCast(fut_waiter);
           const fut_waiter_data = utils.get_data_ptr(Future, fut_waiter_obj);
           return Future.Python.Cancel.future_fast_cancel(fut_waiter_obj, fut_waiter_data, msg);
       } else {
           ...
       }
   }

   instance.must_cancel = true;
   return true;
   ```
   Consider what happens when a `Task` is awaiting `fut_waiter`, and in the **same event loop tick**:
   - Callback A calls `fut_waiter.set_result(value)` (which sets `fut_waiter_data.status = .finished` and schedules `wakeup_task` on the `Soon` queue; `instance.fut_waiter` is not cleared until `wakeup_task` runs!).
   - Callback B calls `task.cancel()` before `wakeup_task` runs.
   - `fast_task_cancel` sees `instance.fut_waiter != null` and calls `future_fast_cancel(fut_waiter_obj, ...)`, which returns **`false`** because `fut_waiter` is already `.finished`!
   - Instead of falling through to set `instance.must_cancel = true; return true;` (so `wakeup_task` throws `CancelledError` into the coroutine instead of sending `fut_waiter`'s result, as CPython `_asynciomodule.c` does), `fast_task_cancel` returns `false` immediately and **completely ignores the `task.cancel()` call**!

2. **`task_uncancel` re-arms `instance.must_cancel = true` when `cancel_requests` decrements from `2` to `1` (`src/task/cancel.zig:82-90`)**:
   ```zig
   pub fn task_uncancel(self: ?*TaskObject, _: ?PyObject) callconv(.c) ?PyObject {
       const instance = self.?;
       if (instance.cancel_requests > 0) {
           const new_cancel_requests = instance.cancel_requests - 1;
           instance.cancel_requests = new_cancel_requests;
           instance.must_cancel = (new_cancel_requests > 0);
       }
       return python_c.PyLong_FromUnsignedLong(instance.cancel_requests);
   }
   ```
   In CPython's `asyncio.Task.uncancel()`:
   ```c
   if (self->task_num_cancels_requested > 0) {
       self->task_num_cancels_requested -= 1;
       if (self->task_num_cancels_requested == 0) {
           self->task_must_cancel = 0;
       }
   }
   ```
   `uncancel()` must **only clear** `must_cancel = false` when `new_cancel_requests == 0`; it must **never** set `must_cancel = true`!
   In nested `asyncio.timeout()` blocks where two timeouts expire (`cancel_requests == 2`), once `CancelledError` is thrown into the coroutine (`must_cancel` is cleared to `false`), the inner `asyncio.timeout.__aexit__` catches `CancelledError` and calls `task.uncancel()` (decrementing `cancel_requests` from `2` to `1`) and then re-raises or handles the timeout. Because Talyn sets `instance.must_cancel = (new_cancel_requests > 0)` (`true`), the next `await` inside a `finally:` or outer cleanup block has a **second** unrequested `CancelledError` injected into it!

3. **`task_cancelling` returns `0` when the task is `.finished` or `.canceled` (`src/task/cancel.zig:92-98`)**:
   ```zig
   pub fn task_cancelling(self: ?*TaskObject, _: ?PyObject) callconv(.c) ?PyObject {
       const instance = self.?;
       const future_data = utils.get_data_ptr(Future, &instance.fut);
       const cancel_requests = if (future_data.status != .finished and future_data.status != .canceled) instance.cancel_requests else 0;
       return python_c.PyLong_FromUnsignedLong(cancel_requests);
   }
   ```
   In CPython 3.11+, `task.cancelling()` unconditionally returns `self->task_num_cancels_requested` regardless of whether the task has finished! `asyncio.TaskGroup` inspects `task.cancelling()` inside its task-done callback (after the task has finished!) to distinguish an internal cancellation from an external cancellation. Returning `0` for finished/cancelled tasks breaks `asyncio.TaskGroup` cancellation propagation.

## Trigger Scenario

1. Resolve `fut.set_result(1)` and call `task.cancel()` in the same tick while `task` is awaiting `fut` -> `task.cancel()` returns `False` and `task` is not cancelled.
2. Nest two `async with asyncio.timeout(...)` blocks -> `task.uncancel()` in the inner block sets `must_cancel = true`, injecting an extra `CancelledError`.
3. Inspect `task.cancelling()` in a done callback after `task` finishes -> returns `0` instead of `1`.

## Proposed Remediation

1. In `fast_task_cancel` (`src/task/cancel.zig:45-58`), if cancelling `fut_waiter` returns `true`, increment `instance.cancel_requests += 1` and return `true`; if it returns `false` (because `fut_waiter` already finished), fall through to set `instance.must_cancel = true; instance.cancel_requests += 1; return true;`.
2. In `task_uncancel` (`src/task/cancel.zig:87`), replace `instance.must_cancel = (new_cancel_requests > 0);` with `if (new_cancel_requests == 0) instance.must_cancel = false;`.
3. In `task_cancelling` (`src/task/cancel.zig:92-98`), unconditionally return `python_c.PyLong_FromUnsignedLong(instance.cancel_requests)`.


## Resolution (2026-10-18)

All three defects confirmed live in src/task/cancel.zig and fixed:

1. **Same-tick cancellation drop (fixed)**: `fast_task_cancel` no
   longer returns the waiter-cancel result verbatim. The request
   increment (`cancel_requests +|= 1`) already happened before the
   waiter branch; now, when `cancel_future_waiter` returns `false`
   (the waiter resolved in the same tick), execution falls through to
   `must_cancel = true; return true` so `wakeup_task` throws the
   `CancelledError` into the coroutine instead of delivering the
   result (mirrors CPython's task_cancel fall-through).

2. **`uncancel` re-arm (fixed)**: `task_uncancel` now only clears
   `must_cancel` when the request count reaches zero, exactly like
   CPython's `task_num_cancels_requested` handling. The old
   `must_cancel = (count > 0)` re-armed the flag after a caught
   exception in nested `asyncio.timeout()` cleanups and injected a
   second unrequested `CancelledError`.

3. **`cancelling` on finished tasks (fixed)**: `task_cancelling`
   reports `cancel_requests` unconditionally (the dead
   `get_data_ptr(Future, ...)` status switch is gone).
