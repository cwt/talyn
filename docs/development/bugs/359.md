# BUG-359 — Socket `fd` leak, `MultiConnectState` memory/reference leak, and unresolved future on error paths in `socket_connected_callback`

- **Status**: ✅ Fixed
- **Severity**: 🔴 High — leaks socket file descriptors, `MultiConnectState`, and all attached `PyObject` references, and hangs callers awaiting `create_connection` if an error occurs on the connect-failure path
- **Category**: FD Leak, Memory/Ref Leak, & Logic Bug
- **Files**:
  - `src/loop/python/io/client/create_connection.zig:917-974`
- **Related**: [BUG-120](120.md), [BUG-328](328.md), [BUG-336](336.md)

## Overview & Root Cause

In `src/loop/python/io/client/create_connection.zig:917-974`, the connect-error branch (`if (io_uring_err != .SUCCESS)`) of `socket_connected_callback` has two resource-cleanup bugs:

1. **Socket `fd` closed after fallible CPython calls (lines 917–927)**:
   ```zig
   if (io_uring_err != .SUCCESS) {
       // Connect failed for this address
       const errno_val: c_int = @intCast(@intFromEnum(io_uring_err));
       const exception = python_c.PyObject_CallFunction(python_c.PyExc_OSError, "is\x00", errno_val, "Connect call failed\x00") orelse return error.PythonError;
       defer python_c.py_decref(exception);
       if (python_c.PyList_Append(mcs.exceptions, exception) < 0) return error.PythonError;

       if (fd >= 0) {
           _ = std.os.linux.close(fd);
       }
   ```
   Note that `cleanup_socket_connected_callback` (`lines 977-980`) only calls `allocator.destroy(sd)` and does **not** close `sd.fd`! Therefore, if `PyObject_CallFunction` (line 920) or `PyList_Append` (line 922) returns `error.PythonError`, line 926 is never reached and `fd` is permanently leaked (and `mcs.active_tasks` is never decremented, so `mcs` is also permanently leaked!).

2. **`mcs.deinit()` at line 971 is skipped on any error between lines 932 and 969**:
   ```zig
   mcs.active_tasks -= 1;
   if (mcs.active_tasks == 0 and !mcs.connected) {
       // All attempts failed!
       ...
       try Future.Python.Result.future_fast_set_result_or_exception(future_data, null, first_exc);
       ...
       mcs.deinit();
   }
   ```
   When the last connect attempt fails (`mcs.active_tasks == 0 and !mcs.connected`), if any operation in lines 936–968 returns an error (such as `PyList_GetItem`, `PySequence_List`, `PyUnicode_FromString`, `PyTuple_Pack`, `PyObject_CallObject(exc_group_type, ...)`, or `future_fast_set_result_or_exception`, e.g., when `mcs.future` was already cancelled by the user!), `socket_connected_callback` returns early before line 971 (`mcs.deinit()`), leaking `MultiConnectState` and all its owned Python references (`future`, `loop`, `protocol_factory`, `ssl`, `server_hostname`, `ssl_handshake_timeout`, `exceptions`) and heap arrays (`addresses`, `task_ids`).

## Trigger Scenario

1. Start `fut = loop.create_connection(factory, "127.0.0.1", closed_port)` and cancel `fut.cancel()` while the connect SQE is in flight.
2. When the connect CQE completes with `ECONNREFUSED`, `mcs.active_tasks` reaches `0` and line 940 or 968 calls `try Future.Python.Result.future_fast_set_result_or_exception(future_data, null, ...)`.
3. Because `fut` was cancelled (`future_data.status == .canceled`), `future_fast_set_result_or_exception` raises `InvalidStateError` and returns `error.PythonError` **before** line 971 (`mcs.deinit()`) is reached!
4. `MultiConnectState` and all its owned memory and Python object references are leaked on every cancelled `create_connection` that fails to connect!

## Proposed Remediation

1. Close `fd` **immediately** at the top of `if (io_uring_err != .SUCCESS)` (before `PyObject_CallFunction`), and decrement `mcs.active_tasks` via `defer` inside the error branch.
2. Inside `if (mcs.active_tasks == 0 and !mcs.connected)`, register `defer mcs.deinit();` at the very top of the block (line 933) and check `if (future_data.status == .pending)` before calling `future_fast_set_result_or_exception`.


## Resolution

Fixed in `socket_connected_callback`'s connect-error branch:

1. **fd close hoisted**: the failed socket is closed at the top of the
   `io_uring_err != .SUCCESS` branch, *before* the fallible
   `PyObject_CallFunction`/`PyList_Append` exception-bookkeeping calls, so no
   early C-API failure can leak the fd (the callback cleanup never closes fds).
2. **`defer if (mcs.pending == 0 and !(mcs.timer_scheduled and !mcs.timer_fired)) mcs.deinit();`** registered at the top of the `io_uring_err != .SUCCESS` branch (before the `mcs.all_errors` bookkeeping): every possible early `return error.PythonError` inside the finalization (including `PyObject_CallFunction`/`PyList_Append` in `mcs.all_errors`, exception/ExceptionGroup construction, and `future_fast_set_exception`) now tears `MultiConnectState` and all owned references down exactly once.
   The redundant trailing `mcs.deinit()` (and the inner one in the
   `PyErr_GetRaisedException` fallback) were removed in favour of the `defer`.
3. **Cancelled/finished futures are no longer resolved a second time**: all
   `future_fast_set_exception` call sites (including the `PyErr_GetRaisedException` fallback) are guarded with
   `if (future_data.status == .pending)`. Previously a cancelled future had
   its `exception` field set and its done-callbacks fired a *second* time
   (`.canceled` then `.finished`) — harmless only because the BUG-265-era
   helper became status-tolerant.

## Analysis Note (2026-10-18 audit)

The report's headline trigger no longer *reproduces* on the current tree: the
original code called `future_fast_set_result_or_exception`, which raises
`InvalidStateError` on cancelled futures; that call was later replaced by the
status-tolerant `future_fast_set_exception` (BUG-265 centralisation), and the
stray exception reference is freed at future dealloc via
`deinitialize_object_fields`. The leak therefore became latent — the fix above
restores the invariant the report demanded (single guaranteed teardown, fd
closed before fallible calls, no resolution of a settled future) so the path
is safe again even under C-API failures.

## Test

`tests/test_create_connection.py::test_bug359_cancelled_connect_failure_no_mcs_leak`
exercises the exact reported trigger: 15 rounds of `create_connection` to a
closed loopback port where the task is cancelled via `call_soon` in the same
ready-queue pass as the coroutine's first step, so the refused CQE finalizes
against a cancelled future; the protocol factory's refcount must not grow.

**Bite verification**: the current tree passes both before and after the fix
(the InvalidStateError raised by the report's
`future_fast_set_result_or_exception` no longer exists). The test was proven
to bite by *reconstructing* the reported behavior on the pre-fix code — a
`if (future_data.status != .pending) return error.PythonError;` early return
in the finalization — under which the test fails with the exact reported
signature (`factory refcount 4 -> 19` over 15 cycles: one leaked
`MultiConnectState` holding one factory reference per cycle).
