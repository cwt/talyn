# BUG-386 — Unchecked `.?` on `contextvars` and `py_callback` in `Handle` after `handle_clear` (Mandate #4), repeated `__init__` memory/ref leaks in `Loop`/`Future`/`Task`/`Handle`/`TimerHandle`, and stale `blocking_task_id` reuse window in `TimerHandle`

- **Status**: ✅ Fixed
- **Severity**: 🟠 Medium-High — violates Architectural Mandate #4 (Null Discovery under GC `tp_clear`), leaks memory and `PyObject` references if `__init__` is called more than once on `Loop`, `Future`, `Task`, `Handle`, or `TimerHandle`, and leaves stale `blocking_task_id` on `TimerHandle`
- **Category**: Null-Unwrap Panic (Mandate #4), Memory/Ref Leak, & Stale Task ID
- **Files**:
  - `src/handle.zig:43-52, 79, 105-107, 132-139, 198-262`
  - `src/timer_handle.zig:29-42, 44-80`
  - `src/loop/python/constructors.zig:197-234`
  - `src/future/python/constructors.zig:16-55, 145-149`
  - `src/task/constructors.zig:32-74`
- **Related**: [Architectural Mandate #4](../architectural-mandates.md), [BUG-336](336.md), [Lesson 44](../lessons/05-python-c-api-correctness.md)

## Overview & Root Cause

1. **Unchecked `.?` on `handle.contextvars`, `handle.py_callback`, and `handle.loop` after `handle_clear` (`src/handle.zig:43-52, 79, 105-107, 132-139`)**:
   Architectural Mandate #4 states:
   > *"In free-threading, GC can null out fields concurrently. Always use `?PyObject` and handle `null` gracefully in callbacks."*
   In `src/handle.zig:132-139`, `handle_clear` sets `self.?.loop = null`, `self.?.py_callback = null`, `self.?.args = null`, and `self.?.contextvars = null` (without setting `self.?.cancelled = true`!).
   Yet:
   - `run_python_generic_callback` (lines 43–50) executes `const context = handle.contextvars.?;` and `handle.py_callback.?` unconditionally!
   - `callback_for_python_generic_callbacks` (line 79) executes `const loop: *Loop.Python.LoopObject = @ptrCast(handle.loop.?);` unconditionally!
   - `traverse_for_python_generic_callbacks` (lines 105–107) executes `visit.?(handle.py_callback.?, arg)` and `visit.?(handle.contextvars.?, arg)` unconditionally!
   If CPython's GC calls `handle_clear` on a cycle containing a `Handle` or `TimerHandle`, the next traversal or callback execution panics on `.?` unwrap of `null`!

2. **Repeated `__init__` calls on `Loop`, `Future`, `Task`, `Handle`, and `TimerHandle` leak previous state**:
   In Python, `obj.__init__(...)` can be called multiple times on an already-constructed instance (or via `super().__init__(...)` in a subclass).
   - `z_loop_init` (`src/loop/python/constructors.zig:197-234`): If `loop_data.initialized` is already `true`, calling `loop.__init__()` overwrites `self.exception_handler`, `self.task_factory`, and `loop_data` (`io_uring` ring, `eventfd`, `signalfd`, `inotify` fd, `DNS` arena, and `BlockingTasksSet`) without calling `loop_data.release()` or decrefing existing fields!
   - `z_future_init` (`src/future/python/constructors.zig:16-55`) and `fast_init_future` (lines 145–149): Overwrites `self.py_loop`, `self.context`, `self.cancel_msg_py_object`, and `future_data.*` without releasing existing callbacks/result/loop references!
   - `z_task_init` (`src/task/constructors.zig:32-74`): Overwrites `self.coro`, `self.name`, `self.context`, and `self.fut` without releasing existing fields!
   - `z_handle_init` (`src/handle.zig:198-257`) and `z_timer_handle_init` (`src/timer_handle.zig:44-80`): Overwrites `self.loop`, `self.py_callback`, `self.args`, and `self.contextvars` without decrefing existing fields!

3. **`TimerHandle.timer_callback` does not zero `timer.blocking_task_id` on completion (`src/timer_handle.zig:29-42`)**:
   In `TimerHandle.timer_callback`, when the `io_uring` timeout CQE completes (either normally or with `data.cancelled()`), `timer.blocking_task_id` is **not** reset to `0`!
   If `timer.cancel()` (`handle_cancel` in `src/handle.zig:264-288`) is called when `timer.handle.cancelled` has not yet been set (for example, if `data.cancelled()` returned early at `src/timer_handle.zig:31` before `callback_for_python_generic_callbacks` set `handle.cancelled = true`), `handle_cancel` sees `timer.blocking_task_id > 0` and queues `.{ .CancelTimer = timer.blocking_task_id }` on the already-freed `BlockingTask` slot ([BUG-336](336.md) class)!

## Trigger Scenario

1. Instantiate `l = talyn.Loop(); l.__init__()` (or `f = loop.create_future(); f.__init__(loop=loop)`) -> leaks the first `Loop` / `Future` resources and references.
2. Trigger GC `tp_clear` (`handle_clear`) on a `Handle` in a reference cycle -> `traverse_for_python_generic_callbacks` or `callback_for_python_generic_callbacks` panics on `handle.py_callback.?` / `handle.contextvars.?`.

## Proposed Remediation

1. In `handle_clear` (`src/handle.zig:132-139`), set `self.?.cancelled = true;` (using `@atomicStore` in `free_threaded` mode), and in `run_python_generic_callback`, `callback_for_python_generic_callbacks`, and `traverse_for_python_generic_callbacks`, use `if (handle.py_callback) |cb|` / `if (handle.contextvars) |ctx|` / `if (handle.loop) |l|` instead of `.?`.
2. In `z_loop_init`, `z_future_init`, `z_task_init`, `z_handle_init`, and `z_timer_handle_init`, clean up any previously initialized state (or reject re-initialization if already active/running) before overwriting fields.
3. In `TimerHandle.timer_callback` (`src/timer_handle.zig:29-42`), set `timer.blocking_task_id = 0;` at the very top of the callback (before `if (data.cancelled())`).

## Resolution

**Fixed** with the following changes:

1. **Safe null discovery in `Handle` (Mandate #4)**: In `src/handle.zig`, checked `if (handle.contextvars) |context|` and `if (handle.py_callback) |py_cb|` safely rather than unchecked `.?` in `run_python_generic_callback`, `callback_for_python_generic_callbacks`, and `traverse_for_python_generic_callbacks`. In `handle_clear`, set `instance.state = STATE_CANCELLED`.
2. **Zeroed `blocking_task_id` on all paths**: In `src/handle.zig`, ensured `handle.blocking_task_id = 0` on every cancellation and execution branch to prevent stale task cancellation attempts.
3. **Repeated `__init__` leak prevention**:
   - In `src/handle.zig` (`z_handle_init`): cleared previously initialized fields before assigning new ones.
   - In `src/timer_handle.zig` (`z_timer_handle_init`): invoked `timer_handle_clear()` on re-initialization.
   - In `src/loop/python/constructors.zig` (`z_loop_init`): raised `RuntimeError("Event loop is already initialized")` if already initialized, and cleared partial state if re-entered uninitialized.
   - In `src/future/python/constructors.zig` (`z_future_init`): invoked `future_clear()` and decremented `py_loop` before re-initializing.
   - In `src/task/constructors.zig` (`z_task_init`): raised `RuntimeError("Task is already initialized")` if `self.coro != null`.

**Test**: Covered by regression tests in `tests/test_lifecycle_safety.py`.
