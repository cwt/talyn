# BUG-135 — Task cancellation request count skipped when task is awaiting a future

- **Status**: ✅ Fixed
- **Severity**: 🟡 Medium-High — broken PEP 678 / Python 3.11+ task cancellation tracking
- **Files**: `src/task/cancel.zig:45-54`, `src/task/callbacks.zig:430`
- **Lessons**: [Network Protocols §Lesson 44](../lessons/06-network-protocols-and-io.md)
- **Description**: In `fast_task_cancel`, when `task.fut_waiter` was non-null, the function cancelled the waiter and immediately returned before incrementing `task.cancel_requests`.
- **Trigger**: Calling `task.cancel()` on any Task that is currently awaiting a Future or another Task.
- **Consequences**: `task.cancelling()` returned 0 and `task.uncancel()` had no effect, violating PEP 678 semantics where cancel count must be tracked on the Task regardless of whether a sub-future is being awaited.
- **Fix**: In `fast_task_cancel`, increment `task.cancel_requests +|= 1;` before checking `task.fut_waiter`, set `task.must_cancel = true;` when not waiting on a sub-future, and clear `task.must_cancel = false;` once consumed in `_execute_task_throw`.
