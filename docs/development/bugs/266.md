# BUG-266 — Empty DNS `hostnames_array` → out-of-bounds `queries[0]` in `resolv.zig`

- **Status**: 🟢 Fixed (2026-08-21)
- **Severity**: Medium-High — Panic / Out-of-Bounds Read (memory safety)
- **Files**:
  - `src/loop/dns/resolv.zig:450-470` (`get_hostname_array` → `build_hostname` rejection → `len == 0`)
  - `src/loop/dns/resolv.zig:690-720` (`prepare_data` proceeds with `queries_data` of empty `queries` per server)
  - `src/loop/dns/resolv.zig:880-920` (`queue` indexes `server_data.queries[0]`)
- **Lessons**: [Security & Input Validation](../lessons/09-security-and-input-validation.md), [io_uring & Kernel](../lessons/04-io-uring-and-kernel.md), [Zig-Specific Patterns](../lessons/08-zig-specific-patterns.md)
- **Related**: [BUG-188](188.md), [BUG-261](261.md). (A prior report attributing this OOB to `build_query` was validated as a false positive and removed from the tracker.)
- **Fix**: 2026-08-21 — `prepare_data()` now rejects an empty `hostnames_array` with `error.InvalidHostname` before building `queries_data`. The errdefers discard the cache record and release `ControlData` cleanly. Surfaced to Python as `RuntimeError` (via `handle_zig_function_error`), consistent with the pre-existing `>255`-char rejection in `DNS.lookup`. Regression test `tests/test_dns_hostname_bounds.py` runs the boundary hostnames (254/255-char non-FQDN, 255-char FQDN) against `getaddrinfo`/`create_connection`/`create_server` in a subprocess, asserting `RuntimeError` and a clean, crash-free exit with the loop still usable. Full suite (`test_all.sh --python=3.14 --starburst --verbose`) passes.

## Description

`loop.create_connection(host="<256+ char string>")` / `loop.create_server(host="<256+ char string>")` reach `dns.lookup` → `prepare_data`. `get_hostname_array` calls `build_hostname` for every candidate; `build_hostname` returns `false` when `new_len > 255` (`new_len = hostname.len + suffix.len + 1`). Any hostname longer than 254 characters is rejected for every search suffix, so `hostnames_array.len == 0`. `prepare_data` does not reject this: it still allocates `queries_data` (one `ServerQueryData` per `resolv.conf` server) with `queries = alloc(QuerySlot, 0)` (empty), and `build_queries` sets `server_data.queries = queries` (empty slice).

`queue` then iterates the servers and does:

```zig
for (control_data.queries_data) |*server_data| {
    const first = &server_data.queries[0]; // OOB when queries.len == 0
    // ...
}
```

When `queries.len == 0`, `server_data.queries[0]` is an out-of-bounds read of the empty slice — a panic in Debug/ReleaseSafe (`index out of bounds`) and an out-of-bounds read in ReleaseFast.

## Trigger

- `loop.create_connection(protocol_factory, host="<256+ character string>")` without `sock`.
- `loop.create_server(protocol_factory, host="<256+ character string>")`.
- Any input for which `get_hostname_array` yields zero candidates (e.g. a non-FQDN whose search suffixes all exceed 255 chars after concatenation).

## Consequences

- Panic / crash of the event loop on adversarial or pathological hostnames (ReleaseSafe: `index out of bounds`; ReleaseFast: OOB read of heap/garbage).
- Violates Mandate 1 (no panics on untrusted input).

## Fix (Not Applied)

Reject an empty `hostnames_array` in `prepare_data` (or `lookup`) before building `queries_data`, raising `ValueError` / `PythonError`, and skip the per-server `queries[0]` access when `server_data.queries.len == 0`. Example:

```zig
if (hostnames_array.len == 0) {
    control_data.record.discard();
    return error.PythonError; // or raise ValueError("host name resolution failed")
}
```
