# BUG-438 — `accept_callback` re-arms after the server was closed by `connection_made`

- **Status**: 🟢 Fixed
- **Severity**: 🟢 Low — spurious SQE / retry on a closed server
- **Category**: Accept loop / re-arm
- **Files**: `src/transports/streamserver/main.zig:162-188`
- **Related**: [Lesson 87](../lessons/03-event-loop-lifecycle.md), [BUG-33](033.md)

## Description

```zig
var should_reenqueue = !server.closed and server.loop != null;
defer { if (should_reenqueue and !server.accept_paused) { enqueue_accept(server) catch schedule_accept_retry(server); } }
...
const protocol = PyObject_CallNoArgs(protocol_factory) ...;
... connection_made(transport) ...   // may call server.close()
```

If `protocol_factory()`/`connection_made()` closes the server, `server.server_fd` becomes `-1` but the
defer still calls `enqueue_accept` with the stale `should_reenqueue == true`, queueing a `WaitReadable`
on fd `-1` (bad SQE) and scheduling a retry. The retry is harmless (it checks `server.closed`) but the
bad SQE is still submitted.

## Fix

Re-check `!server.closed and server.server_fd >= 0 and server.blocking_task_id == 0` inside the defer
(and keep `start_serving` idempotent).

## Resolution (2026-11-12)

The defer block now re-evaluates the full re-arm condition at run time
(`!server.closed and server.server_fd >= 0 and server.loop != null and !server.accept_paused`)
instead of consuming the pre-`connection_made` flag; the `should_reenqueue` variable (and its
EMFILE assignment) is gone — the fatal-error path still pauses via `accept_paused`, which the defer
checks. A server closed by `protocol_factory()`/`connection_made()` can no longer get a
`WaitReadable` SQE queued on fd -1.

Validation: `zig build test` green on Zig 0.16.0 and 0.17.1;
`./scripts/test_all.sh --python=3.15,3.15t --starburst --verbose` green (505 pytest passed on
py3.15, 504 + 1 skipped on py3.15t; stdlib asyncio green on both).
