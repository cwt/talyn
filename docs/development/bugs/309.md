# BUG-309 — Premature decref and use-after-free on custom socket create_connection

- **Status**: 🟢 Fixed (2026-09-07, together with BUG-312)
- **Severity**: 🔴 Critical — Python C-API refcount underflow and use-after-free on protocol factory callback
- **Files**:
  - `src/loop/python/io/client/create_connection.zig` (`z_loop_create_connection`: lines 176–177; `create_transport_and_set_future_result`: line 913)
- **Lessons**: [Python C-API Correctness](../lessons/05-python-c-api-correctness.md), [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md)
- **Description**:
In `z_loop_create_connection` on the pre-existing socket path:
```zig
transport_creation_data.protocol_factory = protocol_factory; // BORROWED
```
Later, when connection succeeds and dispatches `create_transport_and_set_future_result`:
```zig
defer python_c.py_decref(transport_creation_data.protocol_factory);
```
The cleanup defer unconditionally decrefs `protocol_factory`. Because `z_loop_create_connection` never acquired an owned reference via `python_c.py_newref(protocol_factory)`, this decref drops the caller's reference count. When the caller's scope exits or garbage collection runs, `protocol_factory` is prematurely deallocated while still in use.
- **Root Cause**: Asymmetric ownership: borrowed reference stored during setup but owned reference decremented during transport creation cleanup.
- **Trigger Scenario**: Invoking `loop.create_connection(protocol_factory, sock=pre_existing_socket)`.
- **Proposed Remediation**: Acquire an owned reference in line 176: `transport_creation_data.protocol_factory = python_c.py_newref(protocol_factory);`.

- **Fix (Applied — 2026-09-07)**:
  - `z_loop_create_connection` sock path (`src/loop/python/io/client/create_connection.zig`): `transport_creation_data.protocol_factory` now stores `python_c.py_newref(protocol_factory)`, matching the normal path (`:206`). The dispatched `create_transport_and_set_future_result` cleanup decref is now balanced.
  - Grouped with BUG-312: the same struct init gained a full `errdefer { py_decref(protocol_factory); py_decref(loop); py_decref(future); }` so a `Soon.dispatch` failure no longer leaks the owned references (required by this fix — with the new owned factory reference, the struct-destroy errdefer alone would have leaked it on the error path).
- **Regression tests**: `tests/test_create_connection.py::test_create_connection_sock_protocol_factory_refcount` (differential invariant: sock-path net factory reference delta == host/path delta over 4 cycles each; the bug made the sock path exactly one reference lower) and `test_create_connection_sock_factory_survives_gc` (factory class dropped while transport alive must survive). A minimal accept-and-close listener is used because rapid close cycles against a busy threaded echo server trigger an unrelated pre-existing hang (reproduced on the pre-fix build; filed for future investigation).
- **Validation (2026-09-07)**: Confirmed still present.
  - Sock path stores a borrowed `protocol_factory` (`src/loop/python/io/client/create_connection.zig:177`) — contrast the normal path which acquires `python_c.py_newref(protocol_factory)` (`create_connection.zig:206`).
  - `create_transport_and_set_future_result` (`create_connection.zig:902-926`) unconditionally decrefs `transport_creation_data.protocol_factory` at line 913 inside its cleanup `defer` → refcount underflow on the sock path exactly as described.
