# BUG-304 — `fast_new_task` failure paths double-free coro/context/name

- **Status**: 🟢 Fixed (2026-08-23)
- **Severity**: 🔴 Critical — Double free on task-construction failure
- **Files**:
  - `src/task/constructors.zig` (`fast_new_task` — now increfs stored fields; borrow semantics)
  - `src/loop/python/utils/task.zig` (`z_loop_create_task` — success-path releases added)
  - `src/loop/python/hooks.zig` (`append_new_task` — success-path releases added)
- **Lessons**: [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md), [Zig-Specific Patterns §Lesson 77](../lessons/08-zig-specific-patterns.md)
- **Description**: The old implicit contract was "consume the caller's reference on success" — but instance.dealloc unconditionally decrefs stored fields, so failure paths released twice (dealloc + caller errdefer). The BUG-303 guard created the first reachable post-store failure in the create_task path; the freed coroutine then crashed `gen_dealloc`, and full-suite GC later hit `subtype_traverse` corruption.
- **Fix (Applied — 2026-08-23)**: `fast_new_task` takes its own references to coro/context/name immediately after the store (borrow semantics); both callers release their locals on the success path while keeping their errdefers for failures.
- **Regression test**: covered by `tests/test_task_edge.py::test_create_task_on_closed_loop_raises_runtimeerror` (drives the post-store failure); validated by full-suite GC stability.
