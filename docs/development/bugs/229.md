# BUG-228 — `interleave_address_list` else-branch missing bounds check on `ipv4_index`

- **Status**: ✅ Fixed
- **Severity**: 🟠 Medium-High — Out-of-bounds read / uninitialized memory
- **File**: `src/loop/python/io/client/create_connection.zig:~370-400` (interleave_address_list)
- **Lessons**: [Data Structures §Lesson 23 — BTree split correctness; edge cases in capacity](../lessons/07-data-structures-and-algorithms.md), [BUG-212](0212.md) (related: out-of-bounds uninitialized read)
- **Description**: The `interleave_address_list` function mixes IPv4 and IPv6 addresses into a single output array. After the main `for` loop processes all addresses, the final `else` branch blindly writes `tmp_list[ipv4_index]` without verifying `ipv4_index < ipv4_addresses`:

  ```zig
  } else {
      v.* = tmp_list[ipv4_index];  // No bounds check!
      ipv4_index += 1;
  }
  ```

  When the number of IPv6 addresses differs from IPv4 addresses (e.g., 4 IPv6 + 1 IPv4, as in the BUG-212 test case), the loop may exhaust IPv6 entries first, then the `else` branch continues draining IPv4. If the interleave ratio causes IPv4 to be consumed faster than expected, `ipv4_index` can exceed `ipv4_addresses`, reading uninitialized memory from `tmp_list`.

  The existing tests all use equal counts or single-family lists, so this edge case is untested.

- **Trigger**: Happy eyeballs address resolution where IPv4 and IPv6 address counts differ significantly (e.g., 1 IPv4 + 4+ IPv6, or 1 IPv6 + 4+ IPv4).
- **Consequences**: Uninitialized memory in address list → corrupted connection attempts → potential crash or connection to wrong address.
- **Fix**: Add a bounds guard in the `else` branch: `if (ipv4_index < ipv4_addresses) { v.* = tmp_list[ipv4_index]; ipv4_index += 1; } else { break; }`.
