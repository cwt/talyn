# BUG-290 — `Cancel.perform` dereferences possibly-stale task id

- **Status**: 🟢 Fixed (2026-08-23)
- **Severity**: 🟡 Medium-Low — Stale pointer dereference / wrong-operation cancel
- **Files**:
  - `src/loop/scheduling/io/cancel.zig:5-11` (`@ptrFromInt(task_id)`; read `task.operation`; branch `timeout_remove` vs `cancel`)
  - `src/loop/scheduling/io/main.zig:70-78` (`reset()` sets `operation = undefined`, does not invalidate ids held by transports)
  - `src/loop/runner.zig:250-251` (slots deinit'd during batch fetch, BEFORE callbacks clear their stored ids)
- **Lessons**: [Memory & Reference Counting §Lesson 50](../lessons/01-memory-and-reference-counting.md), [Concurrency & Thread Safety §Lesson 59](../lessons/02-concurrency-and-thread-safety.md)
- **Description**: A transport's `blocking_task_id` remains set between slot-free (batch fetch) and the completion callback that zeroes it. If any code queues `.Cancel = id` in that window (e.g., an earlier callback in the same batch closing the transport), `Cancel.perform` reads `operation` from a popped slot: undefined memory if not yet reused (arbitrary timeout_remove-vs-cancel branch) or a NEW task's state if reused (cancelling the wrong operation).
- **Trigger**: Same-batch close-after-completion ordering, or cross-thread closes under free-threading.
- **Consequences**: Usually benign ENOENT; worst case cancels an unrelated new operation.
- **Fix (Applied — 2026-08-23)**: `BlockingTask.reset()` now poisons the freed slot's `operation` to `.Cancel` instead of leaving it `undefined`. A stale-id `Cancel.perform` read therefore lands on the plain `ring.cancel()` branch — a benign ENOENT for anything already gone; a reused slot reads its new task's real operation, and either branch against the old id is an equally benign kernel no-op.
- **Regression test**: structural (window is a same-batch interleaving); cancellation paths are heavily exercised by transport close tests.
