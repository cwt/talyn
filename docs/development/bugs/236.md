# BUG-236 — `set_future_exception` leaves dangling Python exception on OOM path

- **Status**: ✅ False Positive
- **Severity**: 🟡 Medium — Exception state corruption
- **File**: `src/loop/python/io/client/create_connection.zig:~95-100` (set_future_exception), same pattern in `create_server.zig`, `create_endpoint.zig`, `socket/ops.zig`
- **Lessons**: [Python C API §Lesson 27 — NULL return checks](../lessons/05-python-c-api-correctness.md), [Python C API §Lesson 36 — Reference leak in get_result with Exception](../lessons/01-memory-and-reference-counting.md)
- **Description**: `set_future_exception` is called from many error paths across the codebase:

  ```zig
  fn set_future_exception(err: anyerror, future: *FutureObject) !void {
      utils.handle_zig_function_error(err, {});  // Raises Python exception
      const exc = python_c.PyErr_GetRaisedException() orelse return error.PythonError;
      defer python_c.py_decref(exc);
      const future_data = utils.get_data_ptr(Future, future);
      try Future.Python.Result.future_fast_set_exception(future, future_data, exc);
  }
  ```

  `handle_zig_function_error` calls `PyErr_SetRaisedException` or `PyErr_SetString`, which **steals** the exception reference. Then `PyErr_GetRaisedException` retrieves it (giving a new ref). If `future_fast_set_exception` then fails (e.g., OOM during `py_newref` of the exception), the function returns `error.PythonError` — but the Python interpreter's exception state is now set to the original exception (from `handle_zig_function_error`), while `future_fast_set_exception` never ran. The caller's `catch |err|` will see `error.PythonError` and typically call `set_future_exception` again or propagate the error, leading to double-raising.

  This pattern exists in at least 8 call sites across `create_connection.zig`, `create_server.zig`, `create_endpoint.zig`, and `socket/ops.zig`.

- **Trigger**: Any connection/server/datagram creation path where an error occurs and `set_future_exception` is called, followed by an OOM during future exception setting.
- **Consequences**: Dangling exception in interpreter state; double exception raise; confusion in exception handler chains.
- **Fix**: Restructure `set_future_exception` to not call `handle_zig_function_error` before `future_fast_set_exception`. Instead, set the exception directly on the future first, then check for errors. Or use a local exception variable and only raise it after the future is updated.
