# BUG-425 — `transport_force_close` lacks a direct `connection_lost` settlement

- **Status**: 🟢 Fixed
- **Severity**: 🟠 High — protocol stuck in limbo (no `connection_lost`)
- **Category**: Lifecycle / connection teardown
- **Files**: `src/transports/stream/lifecycle.zig:230-272`
- **Related**: [BUG-378](378.md), [BUG-40](040.md), [BUG-16](016.md)

## Description

```zig
read_transport.force_close() catch ...;
write_transport.force_close() catch ...;
...
cancel_and_close_fd(instance);
// no maybe_close_fd / schedule_connection_lost_once here
```

`ReadTransport.force_close` sets the closed flags but never calls `maybe_close_fd`.
`WriteTransport.force_close` calls `maybe_close_fd`, **but** it begins with `if (self.closed) return;`.
If the write side was already closed (EOF/error) while the read side is open, `transport_force_close`
sets `instance.closed = true`, `read.force_close` does not settle, `write.force_close` early-returns,
and `maybe_close_fd` / `schedule_connection_lost_once` is never reached → `connection_lost` never
fires.

## Trigger

`abort()`/`_force_close()` on a half-closed connection (write side already closed).

## Consequences

Protocol never receives `connection_lost`, `Server.wait_closed()` / cleanup logic hangs, resources held.

## Fix

Call `maybe_close_fd(instance)` (or `schedule_connection_lost_once`) explicitly at the end of
`transport_force_close`, after both force-closes.

## 2026-11-12 Validation

- Structural claims verified: `transport_force_close` has no `maybe_close_fd` /
  `schedule_connection_lost_once` call (`lifecycle.zig:260-271`); `ReadTransport.force_close`
  early-returns on `self.closed` and never settles (`read_transport.zig:92-103`, asymmetric with
  `close()` at `:74`); `WriteTransport.force_close` begins with `if (self.closed) return;` then
  settles via `maybe_close_fd` (`write_transport.zig:125,137`).
- Impact correction: "connection_lost never fires" is overstated. (a) An in-flight read op's CancelIO
  completion reaches `cleanup_resources_callback` → `maybe_close_fd` →
  `schedule_connection_lost_once` (`read_transport.zig:130`); (b) `write.closed == true` with
  `instance.closed == false` arises only via `close_transports` (the sole `write.close()` caller,
  `lifecycle.zig:63-64`), which runs `read.close()` first — an idle read closes immediately (so the
  write side's own `maybe_close_fd` settles) and an armed read leaves a completion that settles. No
  reachable fully-stuck state was found through current callers (including the `streamserver` errdefer
  at `streamserver/main.zig:247`, where the write side is still open).
- Kept **Open** as a hardening fix: the read `force_close`/`close()` asymmetry is real; the proposed
  explicit settlement at the end of `transport_force_close` remains sound.

## Resolution (2026-11-12)

`transport_force_close` now calls `schedule_connection_lost_once(instance)` explicitly at the end,
after both force-closes and `cancel_and_close_fd`. The once-only guard makes a redundant earlier
settlement harmless, so the notification fires exactly once with the pending exception regardless of
which side had already closed. (The 2026-11-12 validation had reclassified the impact as
"latent hardening gap"; the explicit settlement closes it outright.)

Regression test added: `test_bug425_abort_after_write_eof_fires_connection_lost` in
`tests/test_review_regressions.py` (write_eof → abort on a half-closed transport must notify).

Validation: `zig build test` green on Zig 0.16.0 and 0.17.1;
`./scripts/test_all.sh --python=3.15,3.15t --starburst --verbose` green (505 pytest passed on
py3.15, 504 + 1 skipped on py3.15t; stdlib asyncio green on both).
