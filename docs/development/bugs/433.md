# BUG-433 — DNS response modulo heuristic resolves early

- **Status**: 🟡 Open
- **Severity**: 🟡 Medium — dropped addresses / wrong result set
- **Category**: Protocol logic / DNS
- **Files**: `src/loop/dns/resolv/response.zig:337-365`
- **Related**: [BUG-384](384.md), [BUG-317](317.md), [BUG-8](008.md)

## Description

```zig
const types_per_host: usize = if (... queries.len >= hostnames_array.len * 2) 2 else 1;
const current_candidate_done = (server_data.responses_received % types_per_host) == 0;
```

Queries for all candidates × {A, AAAA} are written back-to-back (each `on_query_sent` fires on **write**
completion, not on response), so UDP responses can interleave across candidates. The code assumes
responses arrive in exact send order; with interleaved replies (`a.A, b.A, a.AAAA, b.AAAA`) it declares
a candidate done after two responses and calls `mark_resolved_and_execute_user_callbacks` with a
partial/mixed result set — dropping AAAA addresses.

## Trigger

Dual-stack host, multiple candidate names, responses arriving out of send order.

## Consequences

IPv6 addresses omitted / premature resolution.

## Fix

Match each response to its `QuerySlot` (available as `matched_slot`) and track completion per
hostname/type instead of a global modulo counter.
