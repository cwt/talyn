# BUG-283 — `new_datagram_transport` error path bypasses dealloc cleanup

- **Status**: 🟢 Fixed (2026-08-23)
- **Severity**: 🟡 Medium — Resource/refcount leak on bounded pools
- **Files**:
  - `src/transports/datagram/constructors.zig:131` (`errdefer ... tp_free(instance)` — raw memory only)
  - `src/transports/datagram/constructors.zig:61` (`self.loop = py_newref(loop)`)
  - `src/transports/datagram/constructors.zig:70-71` (`register_fixed_file(fd)` — bounded slot consumed)
  - `src/transports/datagram/constructors.zig:76-84` (buffer pool lease or `alloc(u8, 65536)`)
  - `src/transports/datagram/constructors.zig:86` (`try set_protocol(self, protocol)` — raises TypeError for non-DatagramProtocol)
  - `src/loop/python/io/datagram/create_endpoint.zig:288` (user-triggerable propagation path)
- **Lessons**: [Memory & Reference Counting §Lesson 49](../lessons/01-memory-and-reference-counting.md), [Python C API Correctness](../lessons/05-python-c-api-correctness.md)
- **Description**: On failure, `tp_free` releases only raw object memory, bypassing `datagram_dealloc`/`cleanup_resources`. Each failed call permanently leaks one strong loop reference, one fixed-file slot (bounded pool — repeatable failures exhaust it), and one registered-buffer lease or 64 KiB heap allocation. The `z_datagram_init` constructor path fails identically yet cleans up correctly via CPython calling dealloc — proving the asymmetry unintended.
- **Trigger**: `create_datagram_endpoint(protocol_factory=...)` returning an object that fails the `asyncio.DatagramProtocol` isinstance check.
- **Consequences**: Cumulative fd-slot/buffer-pool exhaustion under repeated bad-factory usage.
- **Fix (Applied — 2026-08-23)**: The errdefer now mirrors `datagram_dealloc`'s resource release — GC untrack, `cleanup_resources()` (fixed-file slot + buffer lease/heap buffer), loop decref, tp_free. The fd is intentionally left to the caller (`create_datagram_endpoint` still owns it until transfer, guarded by its own `owns_fd` errdefer).
- **Regression test**: `tests/test_datagram.py::test_bad_protocol_factory_no_resource_leak` — six consecutive bad-factory failures followed by a successful endpoint (proves the fixed-file pool wasn't exhausted).
