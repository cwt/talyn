# BUG-336 — `call_later` timers scheduled inside a `create_connection` protocol factory fire immediately

- **Status**: ✅ Fixed (2026-09-30) — stray `CancelIO` for already-completed connect tasks killed factory-scheduled timers via `BlockingTask` slot reuse
- **Severity**: 🔴 High — silent wrong-time execution (not a crash): affected timers fire ~instantly, so watchdogs abort healthy operations; failure is deterministic, not flaky
- **Files**:
  - `src/loop/python/io/client/create_connection.zig` (fix: `SocketData.task_id`, `MultiConnectState.happy_timer_id`, `removeTaskId`; connect IDs removed on completion, happy-eyeballs timer tracked separately so CancelIO rounds only hit still-pending tasks)
  - `tests/test_create_connection.py` (`test_create_connection_factory_call_later_not_fired_early`, `test_create_connection_factory_call_at_not_fired_early`)
  - Reproducers below are localhost-only (no network, no SSH server needed)
- **Related**: [BUG-334](334.md) (same timeout machinery, different mechanism), [BUG-120](120.md) (`mcs` teardown ownership), [BUG-116](116.md) (unconditional teardown cancel), [Lesson 105](../lessons/04-io-uring-and-kernel.md) (condition teardown cancellation on active state)
- **Discovered by**: Dogfooding Talyn 0.9.10 as the event loop for `ananta` (SSH batch tool); every SSH connection failed instantly while uvloop and stdlib asyncio connected in ~0.2s.

## Symptoms & Impact

- Under Talyn, `asyncssh.connect()` to a healthy server fails in <0.05s with `ConnectionLost: Login timeout expired`, even with `login_timeout=15` (default: 2 minutes).
- asyncssh debug log shows a normal start that dies without waiting: TCP connects, `Sending version SSH-2.0-...` goes out, then `Login timeout expired` → `Aborting connection`. No server banner is ever processed.
- In the downstream application this surfaces as `Error connecting to <host>: Login timeout expired` for every host, while the identical code on uvloop/stdlib connects and runs commands normally.
- Secondary wart (same environment): `sys.exit(2)` inside `asyncio.run` under Talyn additionally raises `RuntimeError: Event loop stopped before Future completed` during runner close; stdlib propagates `SystemExit` cleanly.
- Blast radius is any asyncio program that calls `loop.call_later`/`loop.call_at` from inside a `create_connection` protocol factory — asyncssh is one instance (login watchdog, keepalive timers).

## Isolation matrix

Timers, socket reads, and `create_connection` data delivery were each tested separately under Talyn 0.9.10 (CPython 3.14.7, Linux x86_64) with uvloop/stdlib controls:

| Case | Result under Talyn |
|---|---|
| Raw `open_connection` + banner read | ✅ banner received |
| `create_connection` + `data_received` (banner + kex packet) | ✅ delivered |
| `sleep(2)` / `call_later(2)` in task context | ✅ fire on time |
| `call_later(15)` + network await in task context | ✅ does not fire early |
| `call_later(15)` inside protocol factory (lambda callback) | ❌ fires in ~0ms |
| `call_later(15)` inside protocol factory (bound-method callback) | ❌ fires in ~0ms |
| Task-level 15s timer scheduled right after the same `create_connection` | ✅ behaves (only the factory-scheduled one misfires) |
| Localhost server (rules out network/DNS/Tailscale) | ❌ still misfires |

So it is the *factory context*, not the callback type and not I/O: the misfire is network-independent and deterministic.

## Root Cause (localized, Zig site unisolated)

Instrumenting the asyncssh path shows the timer is *scheduled* correctly and *fired* wrongly:

```text
timer scheduled: loop.time()=89473.261 → handle when=89488.261 (fires in 15.000s)  ✅ correct
timer FIRED:     loop.time()=89473.261                                            ❌ same tick, clock frozen
```

- The `TimerHandle` deadline (`when`) is computed correctly (+15s), so the fault is on the firing/dispatch side, not argument parsing.
- At fire time `loop.time()` is unchanged from schedule time: the callback runs essentially synchronously after scheduling, on the next loop pass, as if the deadline bookkeeping treated the factory-queued timer as already expired.
- Task-level timers scheduled moments later in the same loop behave, so the general timer wheel is sound — the defect is specific to timers queued while the loop is inside the synchronous protocol-factory invocation of `create_connection`.
- Raw reads, `data_received` delivery, and `sleep` all work, so selectors, transports, and the common delayed path are intact.

Hypothesis for the owner to confirm: the delayed-call path (`z_loop_delayed_call` in `src/loop/python/scheduling.zig`) derives its deadline from a cached/clock value that is stale (or comparably misordered) during the factory invocation, or the factory-queued timer bypasses the normal deadline ordering. This smells related to the BUG-333/334 family (kernel/user-space visibility and lifetime assumptions around deferred work), but on the dispatch side rather than the submit side.

## Minimal reproduction (localhost-only)

```python
import asyncio, threading, socket, time

srv = socket.socket()
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("127.0.0.1", 0))
srv.listen(1)
port = srv.getsockname()[1]
threading.Thread(target=lambda: (lambda c, _: (time.sleep(0.5), c.close()))(*srv.accept()), daemon=True).start()

class P(asyncio.Protocol):
    pass

async def go():
    loop = asyncio.get_running_loop()
    box = []
    def factory():
        loop.call_later(15, lambda: box.append(time.monotonic()))
        return P()
    t, p = await loop.create_connection(factory, "127.0.0.1", port)
    await asyncio.sleep(0.2)
    t.close()
    assert not box, f"timer misfired: {box}"

import talyn
asyncio.set_event_loop_policy(talyn.EventLoopPolicy())
asyncio.run(go())
```

- Under Talyn 0.9.10: `AssertionError` — the 15s timer fires within ~0ms.
- Expected (uvloop/stdlib behavior): no fire; assertion holds.

## Suggested next steps

- Triage `z_loop_delayed_call` / timer-deadline computation for timers queued during `create_connection`'s factory invocation.
- Add a regression test shaped like the reproducer above: a factory-scheduled `call_later` must not fire before its delay (assert on `loop.time()` delta, not wall clock).
- Downstream (`ananta`) keeps Talyn selection held until a fixed release; no application-side workaround exists because the timer is scheduled by library (asyncssh) internals.

## Fix (2026-09-30)

- **Actual root cause** (not the `scheduling.zig` hypothesis): `socket_connected_callback`'s success path queued `CancelIO` for every id in `mcs.task_ids`, including the just-completed connect whose `BlockingTask` slot was already freed. The factory runs synchronously inside transport creation, so its `call_later` timer reused that exact freed slot (task ids are raw slot pointers, no generation). `mcs.deinit()` then queued `CancelIO` for the stale id again, the kernel cancelled the new timer, and its callback ran immediately (`handle.cancelled` was never set, so nothing suppressed it). Verified: `sock=` path (no connect tasks) was clean, deferring `call_later` via `call_soon` was clean, and of two factory timers only the first (slot-reusing) misfired.
- **Fix**: each `SocketData` records its `task_id` and removes it from `task_ids` on completion (all paths); the happy-eyeballs timer moved out of `task_ids` into `MultiConnectState.happy_timer_id`, cleared when it fires/is cancelled; the success path cancels pending connects plus the still-armed timer explicitly; `deinit` cancels pending connects plus the still-armed timer. Cancel rounds now only target live tasks.
- **Validation**: bug reproducer passes (`OK: timer did not fire early`); `call_at` variant passes; short-delay factory timer fires on time (`early=0 late=1`); `tests/test_create_connection.py` 21/21 pass; full `./scripts/test_all.sh --starburst --verbose` green.
