# BUG-345 — `callback_for_python_generic_callbacks` sets `handle.cancelled = true` on normal execution, breaking `Handle.cancelled()` and causing `loop.add_signal_handler` callbacks to fire only once

- **Status**: 🔴 Open
- **Severity**: 🔴 Critical — breaks standard `asyncio.Handle.cancelled()` semantics after every `call_soon`/`call_later` callback and breaks repeated Unix signal handling (`loop.add_signal_handler` only fires once per registration)
- **Category**: Logic Bug
- **Files**:
  - `src/handle.zig:54-72, 290-298`
  - `src/loop/python/unix_signals.zig:73-77`
  - `src/loop/unix_signals.zig:90-94`
- **Related**: [Lesson 19](../lessons/01-event-loop-and-lifecycle.md)

## Overview & Root Cause

In `src/handle.zig:54-72`, `callback_for_python_generic_callbacks` conflates "callback has already executed" with "handle was cancelled by the user":

```zig
const already_claimed = if (python_c.free_threaded)
    @atomicRmw(bool, &handle.cancelled, .Xchg, true, .acq_rel)
else blk: {
    const prev = handle.cancelled;
    handle.cancelled = true;
    break :blk prev;
};
if (already_claimed or data.cancelled()) {
    python_c.py_decref(@ptrCast(handle));
    return;
}
```

This causes two severe bugs:

1. **`Handle.cancelled()` / `TimerHandle.cancelled()` returns `True` after normal execution**:
   In `asyncio`, `handle.cancelled()` must return `True` **only** if `handle.cancel()` was explicitly called before the callback ran, and `False` after normal execution. Because `callback_for_python_generic_callbacks` sets `handle.cancelled = true` on normal execution, `h.cancelled()` returns `True` for every completed `call_soon`, `call_soon_threadsafe`, `call_later`, and `call_at` handle.

2. **`loop.add_signal_handler` callbacks fire only once**:
   In `src/loop/python/unix_signals.zig:73-77`, `z_loop_add_signal_handler` creates a single `PythonHandleObject` (`handle`) and stores it in `UnixSignals`.
   In `src/loop/unix_signals.zig:90-94`, whenever a signal arrives on `signalfd`, `signalfd_read_callback` dispatches `callback_for_python_generic_callbacks` with that same `handle`:

   ```zig
   try Soon.dispatch(self.loop, &.{
       .{
           .func = &Handle.callback_for_python_generic_callbacks,
           .cleanup = &Handle.cleanup_for_python_generic_callbacks,
           .data = .{ .user_data = handle },
       },
   });
   ```

   On the **first** signal delivery, `callback_for_python_generic_callbacks` sets `handle.cancelled = true` and runs the Python signal handler.
   On the **second and all subsequent** deliveries of the same signal, `callback_for_python_generic_callbacks` sees `already_claimed == true` (`handle.cancelled == true`), decrefs `handle`, and returns immediately without calling the Python signal handler!

   (Note: `FDWatcher` in `src/loop/python/io/watchers.zig:97` had to work around this exact bug by manually setting `handle.cancelled = false;` after calling `callback_for_python_generic_callbacks`, which `UnixSignals` does not do.)

## Trigger Scenario

1. **`Handle.cancelled()`**:
   ```python
   h = loop.call_soon(lambda: None)
   await asyncio.sleep(0)
   assert not h.cancelled()  # FAILS under Talyn: returns True
   ```
2. **Signal handler**:
   ```python
   count = 0
   loop.add_signal_handler(signal.SIGUSR1, lambda: nonlocal_inc())
   os.kill(os.getpid(), signal.SIGUSR1)  # fires (count == 1)
   os.kill(os.getpid(), signal.SIGUSR1)  # silently dropped (count stays 1)!
   ```

## Proposed Remediation

1. Separate `handle.cancelled: bool` (set **only** by `handle_cancel`) from `handle.executed: bool` (or only use one-shot claim for one-shot `call_soon`/`call_later` handles, while `handle_cancelled` reads `handle.cancelled`).
2. For `UnixSignals` (and `FDWatcher`), either invoke a dedicated repeating callback helper that checks `handle.cancelled` without setting it to `true` on execution, or do not mark repeating handles as executed/cancelled when they fire.
