# BUG-351 — Stale `ReadTransport.blocking_task_id` during P15 batch dispatch cancels reused `BlockingTask` slots on `pause_reading()`/`close()`/`abort()`, and `ReadTransport.close()` omits `!self.cancelling` guard

- **Status**: 🔴 Open
- **Severity**: 🔴 Critical — exact [BUG-336](336.md) class bug on the read hot path: calling `pause_reading()`, `close()`, or `abort()` inside `protocol.data_received()` cancels whatever newly scheduled timer or IO operation reused the freed `BlockingTask` slot, and prevents `read_transport.close()` from marking `read_transport.closed = true`
- **Category**: Use-After-Free (Stale `BlockingTask` Slot Cancel) & Logic Bug
- **Files**:
  - `src/transports/read_transport.zig:66-85, 87-98, 130-141, 210-219`
  - `src/loop/scheduling/io/main.zig:760-831`
  - `src/loop/runner.zig:124-189, 390`
- **Related**: [BUG-336](336.md), [Lesson 105](../lessons/04-io-uring-and-kernel.md)

## Overview & Root Cause

1. **Stale `ReadTransport.blocking_task_id` during `dispatch_completion_batch` (`src/loop/scheduling/io/main.zig:760-831` & `src/loop/runner.zig:390`)**:
   When a stream read CQE arrives in `IO.wait_for_io`:
   - `IO.wait_for_io` appends a `.stream_read` or `.buffered_read` record to `completion_batch`.
   - `IO.wait_for_io` appends `ReadTransport.read_operation_completed` to `ready_tasks_queues`.
   - At line 830, `IO.wait_for_io` **immediately frees** the `BlockingTask` slot back to `set.free_slots` via `set.release(data)`.
   - However, `read_transport.blocking_task_id` is **not** reset to `0` until `ReadTransport.read_operation_completed` runs during `call_once` (`src/transports/read_transport.zig:139`).
   - In `Runner.start` (`src/loop/runner.zig:390`), `dispatch_completion_batch` runs **before** `call_once`!
   - Therefore, during the entire execution of `protocol.data_received(data)` or `protocol.buffer_updated(nbytes)` inside `dispatch_completion_batch`, `read_transport.blocking_task_id` still holds the raw pointer to the **already-freed** `BlockingTask` slot!
   - If `data_received()` schedules any new `io_uring` task (such as `loop.call_later(...)`, `transport.write(...)` flush, or `loop.create_connection(...)`), `BlockingTasksSet.push()` reuses that exact freed slot.
   - If `data_received()` then calls `transport.pause_reading()`, `transport.close()`, or `transport.abort()`, `ReadTransport.cancel()` / `close()` / `force_close()` sees `self.blocking_task_id != 0` and queues `.{ .CancelIO = self.blocking_task_id }`, cancelling the newly scheduled unrelated timer or IO operation!
   - Furthermore, if `data_received()` calls `transport.pause_reading()` followed by `transport.resume_reading()`, `transport_resume_reading` (`src/transports/stream/read.zig:177`) sees `if (read_transport.blocking_task_id != 0) return python_c.get_py_none();` while `read_transport.cancelling` was set to `true` by `pause_reading()`.

2. **Missing `!self.cancelling` check in `ReadTransport.close()` (`src/transports/read_transport.zig:78-82`)**:
   ```zig
   _ = try self.loop.io.queue(.{ .CancelIO = blocking_task_id });
   // BUG-336: exactly one CancelIO per op generation — a second cancel
   // after completion+slot-reuse would kill the new occupant. Mark
   // cancelling so cancel() becomes idempotent (completion resets it).
   self.cancelling = true;
   ```
   Although the comment explicitly cites `BUG-336`, `ReadTransport.close()` omits `if (!self.cancelling)` before queuing `.CancelIO` (unlike `ReadTransport.force_close()` at line 93 and `WriteTransport.close()` at line 105). Calling `transport.pause_reading()` (which sets `self.cancelling = true` and queues `CancelIO`) followed by `transport.close()` queues a **second** `CancelIO` for the same `blocking_task_id`.

## Trigger Scenario

1. Inside `Protocol.data_received(self, data)`:
   ```python
   def data_received(self, data):
       self.timer = self.loop.call_later(10.0, self.on_timeout)
       self.transport.pause_reading()
   ```
2. Because `data_received` runs inside `dispatch_completion_batch` after the read's `BlockingTask` slot was freed by `wait_for_io` (and reused by `call_later(10.0)`), `self.transport.pause_reading()` queues `CancelIO` on `read_transport.blocking_task_id`, immediately cancelling `self.timer` (causing it to fire in 0ms, identical to [BUG-336](336.md))!

## Proposed Remediation

1. In `IO.wait_for_io` (`src/loop/scheduling/io/main.zig:770-798`), clear `read_transport.blocking_task_id = 0` and `read_transport.cancelling = false` **before** calling `set.release(data)` (at the moment the CQE is harvested and the slot is released).
2. In `ReadTransport.close()` (`src/transports/read_transport.zig:78`), guard the `CancelIO` queue call with `if (!self.cancelling)`:
   ```zig
   if (!self.cancelling) {
       _ = try self.loop.io.queue(.{ .CancelIO = blocking_task_id });
       self.cancelling = true;
   }
   ```
