# BUG-369 — Re-entrant finalizer or GC access during `Future.release` and `future_clear` causes double-free/double-decref and null-unwrap panic in `future_result`

- **Status**: ✅ Fixed
- **Severity**: 🔴 High — re-entrant `__del__` finalizers during `Future.release` cause double-decref and double-free, and calling `fut.result()` or `fut.exception()` on a GC-cleared finished `Future` panics on `future_data.result.?` (Mandate #4 violation)
- **Category**: Double-Free / Double-Decref & Null-Unwrap Panic (Mandate #4 Violation)
- **Files**:
  - `src/future/main.zig:16-24, 33-41`
  - `src/future/python/constructors.zig:66-92`
  - `src/future/python/result.zig:34-36, 62-63`
- **Related**: [Lesson 44](../lessons/05-python-c-api-correctness.md), [Architectural Mandate #4](../architectural-mandates.md)

## Overview & Root Cause

1. **Re-entrancy hazard in `Future.release` (`src/future/main.zig:16-41`)**:
   ```zig
   pub fn release(self: *Future) void {
       if (self.released) return;

       if (self.result) |res| {
           if (self.exception) {
               python_c.PyErr_SetNone(res);
           }
           python_c.py_decref(res);
       }
       ...
       Future.Callback.release_callbacks_queue(self);
       self.exceptions_queue.deinit(self.loop.allocator);

       self.released = true;
   }
   ```
   - `self.released = true` is set on the **last** line (line 40), and `self.result` is **not** set to `null` before calling `python_c.py_decref(res)` (line 23)!
   - In CPython, `py_decref` can synchronously invoke an arbitrary Python `__del__` finalizer or weakref callback, which can trigger a garbage collection pass (`future_clear` / `future_traverse`) or access the `Future` while `self.released` is still `false` and `self.result` still holds the freed pointer!
   - Also note line 21: `if (self.exception) { python_c.PyErr_SetNone(res); }` unconditionally **sets a Python exception on the active thread state** inside `Future.release` (called from `future_dealloc`!), corrupting the thread's exception state during garbage collection/deallocation!

2. **Null-unwrap panic in `future_result` / `future_exception` after `future_clear` (`src/future/python/constructors.zig:66-92` & `src/future/python/result.zig:34-36, 62-63`)**:
   In `future_clear`:
   ```zig
   if (future_data.result) |res| {
       future_data.result = null;
       python_c.py_decref(res);
   }
   future_data.released = true;
   ```
   `future_clear` sets `future_data.result = null` and `future_data.released = true`, **without** changing `future_data.status` (which remains `.finished`).
   If a `__del__` finalizer in the same reference cycle calls `fut.result()` or `fut.exception()` on the cleared `Future`, `z_future_result` (`src/future/python/result.zig:34-36`) sees `status == .finished` and executes:
   ```zig
   if (future_data.exception) {
       python_c.PyErr_SetObject(@ptrCast(python_c.Py_TYPE(future_data.result.?)), future_data.result.?);
       return error.PythonError;
   }
   return python_c.py_newref(future_data.result.?);
   ```
   unwrapping `future_data.result.?` when it is `null` — an immediate panic violating Architectural Mandate #4!

## Trigger Scenario

1. Create a reference cycle containing a resolved `Future` (`fut.set_result(obj_with_del)`) where `obj_with_del.__del__` calls `fut.result()`.
2. When cycle GC runs `future_clear(fut)` followed by `obj_with_del.__del__()`, `fut.result()` sees `future_data.status == .finished` with `future_data.result == null` and panics on `future_data.result.?`.
3. Create a failed `Future` (`fut.set_exception(ValueError())`), retrieve its exception so `result_retrieved = true`, and let `fut` be deallocated -> `Future.release` calls `python_c.PyErr_SetNone(res)` inside `future_dealloc`, setting an active `ValueError` on the CPython thread state during deallocation!

## Proposed Remediation

1. In `Future.release` (`src/future/main.zig:16-41`):
   - Set `self.released = true;` **first** (right after `if (self.released) return;`).
   - Detach `const res = self.result; self.result = null;` before `py_decref`.
   - Remove the erroneous `if (self.exception) { python_c.PyErr_SetNone(res); }` call from `Future.release` (setting a thread-state exception during deallocation is always wrong).
2. In `z_future_result` and `z_future_exception` (`src/future/python/result.zig`), guard against `future_data.result == null` (returning `Py_None` or raising `InvalidStateError` if cleared by GC instead of unwrapping `.?`).


## Resolution (2026-10-18)

The report's `Future.release` snippets were partially stale (the
`PyErr_SetNone(res)` / `py_decref(res)` lines were already gone), but
the underlying hazards were all live in the current code:

1. **`Future.release` re-entrancy fence (fixed)**: `self.released =
   true` is now set FIRST (right after the idempotence return), before
   any decref — the callbacks-queue release and the exceptions-queue
   decrefs can synchronously run Python finalizers; a re-entrant call
   previously re-ran the whole teardown (double-free of the callbacks
   queue, double `reserved_slots` decrement because the `pending`
   check ran after the status may have been mutated re-entrantly). The
   `pending` reserved-slot decrement happens before the decrefs too.

2. **`future_clear` detach-before-decref (fixed)**: the result object
   is detached (`future_data.result = null`) BEFORE its decref — the
   decref could run the result object's finalizer, which re-enters
   the Future while the field still pointed at the dying object
   (use-after-free through `get_result`).

3. **Zombie-state mutation gates (fixed)**: `future_set_initial_values`
   marks `tp_new`-created Futures `released = true` (never armed: no
   `loop`, undefined queues), so any Python-visible mutation on them
   was UB. `future_fast_cancel` now returns `false` immediately for
   released futures (inert cancel), `add_done_callback` /
   `remove_done_callback` are no-ops, `future_fast_set_result` and
   `set_future_exception` no-op when `status != .pending or released`, and
   `z_future_set_result` / `z_future_set_exception` / `future_fast_set_exception`
   raise `InvalidStateError` — pre-fix those
   armed `call_done_callbacks` on the garbage-armed future
   (guaranteed SIGSEGV through `loop.initialized` /
   `loop.reserved_slots` on the zero-filled tp_alloc memory).

4. **`get_result` null guard (fixed)**: a finished Future whose
   `tp_clear` detached the result (cycle GC) now raises
   `InvalidStateError` from `result()` instead of unwrapping
   `future_data.result.?` (`future_exception` was already safe —
   it returns `None` after clear).

- three zombie-state probes (`set_result` / `cancel` /
  `set_exception` on a `tp_new`-only `talyn_zig.Future`) asserting
  `InvalidStateError` / inert `False` instead of UB;

  clean collection — documented honestly as a smoke only: CPython
  clears closure cells, weakrefs and instance dicts before finalizers
  run, so a mid-teardown re-entry carrying a strong handle is not
  buildable from Python; the release fence, the detach-before-decref
