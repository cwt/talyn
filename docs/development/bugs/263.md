# BUG-263 — `PyFloat_AsDouble` `-1.0` sentinel ambiguity in DNS timeout parsing

- **Status**: 🟢 Fixed (2026-08-21)
- **Validation**: 2026-08-21 — CONFIRMED REAL but LOW. The `-1.0` sentinel is genuinely present (`create_server.zig`: `if (timeout_val == -1.0) break :blk null`; `create_connection.zig` relies on `timeout_from_secs(-1.0)` → `null`). A real `dns_timeout=-1.0` is silently treated as no-timeout (5s default) instead of `ValueError`. However the original report's "Exception State Leak" framing is inaccurate: `PyErr_Occurred()` is checked *before* the `-1.0` sentinel, so no exception leaks. Severity lowered Medium→Low (sentinel ambiguity, not a crash/leak).
- **Fix**: 2026-08-21 — Added `Resolv.parse_dns_timeout()`: raises `TypeError` on non-float input (via `PyFloat_AsDouble`) and `ValueError` ("DNS timeout must be non-negative") on any negative value; NaN/Inf still map to the default timeout via `timeout_from_secs`. All 5 parse sites now use it (`create_connection.zig`, `create_server.zig`, `create_endpoint.zig`, `getaddrinfo.zig`, `getnameinfo.zig`), removing the redundant `-1.0` sentinels. Also fixed the Python layer: `talyn/loop.py` `create_connection`/`create_server` (and their `_create_ssl_*` paths) did not accept `dns_timeout` at all, so the kwarg never reached the C parser — added the parameter and forwarded it. Regression tests: negative `dns_timeout` now raises `ValueError` on `create_connection`, `create_server`, `create_datagram_endpoint`, `getaddrinfo`, and `getnameinfo`; NaN/Inf still accepted. Full suite (`test_all.sh --python=3.14 --starburst --verbose`) passes.

## Description

```zig
// server/create_server.zig:280-284
const timeout_val = python_c.PyFloat_AsDouble(py_dns_timeout);
if (python_c.PyErr_Occurred() != null) return error.PythonError;
if (timeout_val == -1.0) break :blk null; // sentinel for “no timeout” — but -1.0 is also a valid double
```

`PyFloat_AsDouble` returns `-1.0` on error *and* for legitimate input `-1.0`. The code checks `PyErr_Occurred` *first*, so a true error is caught; but then it re-uses `-1.0` as a sentinel for “no timeout” via `if (timeout_val == -1.0) break :blk null;`. If the caller passes `dns_timeout=-1.0` (e.g., `float("-1.0")`), it is silently treated as “no timeout” instead of being rejected or clamped. More critically, the earlier client path `src/loop/python/io/client/create_connection.zig:143` does `if (PyErr_Occurred()!=null) return error; dns_timeout = timeout_from_secs(timeout_val);` where `timeout_from_secs` now returns `null` for negative values, but the `-1.0` sentinel check is missing, so negative timeouts fall through to `timeout_from_secs` which returns `null` (treated as no timeout) rather than raising `ValueError`.

## Trigger

`loop.create_server(..., dns_timeout=-1.0)` or `loop.create_connection(..., dns_timeout=-1.0)`.

## Consequences

- Negative DNS timeout silently becomes “no timeout” (5s default) instead of `ValueError` → unexpected 5s hangs.

## Fix (Not Applied)

Check `PyErr_Occurred` immediately after `PyFloat_AsDouble`, then validate `timeout_val < 0.0` via `PyErr_Occurred` or explicit range check before sentinel.
