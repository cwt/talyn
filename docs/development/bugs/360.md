# BUG-360 — Uninitialized `sockaddr.storage` read in `sock_accept_callback` and `sock_recvfrom_callback` (`AF_UNIX`), plus null `pbuf.buf` pointer cast panic in `sock_sendall`, `sock_sendto`, and `sock_recv_into`

- **Status**: ✅ Fixed
- **Severity**: 🔴 High — reads uninitialized memory into Python strings on `AF_UNIX` `sock_accept`/`sock_recvfrom` and panics on empty `bytearray()` buffers in `sock_sendall`/`sock_sendto`/`sock_recv_into`
- **Category**: Uninitialized Memory Read & Panic (Mandate #1 Violation)
- **Files**:
  - `src/loop/python/io/socket/ops.zig:28, 69, 134, 521, 563, 601, 672, 797, 899`
  - `src/utils/address.zig:84-90`
- **Related**: [BUG-318](318.md), [Architectural Mandate #1](../architectural-mandates.md)

## Overview & Root Cause

1. **Uninitialized `sockaddr.storage` read in `sock_accept_callback` and `sock_recvfrom_callback` (`src/loop/python/io/socket/ops.zig:28, 69, 134, 563, 601, 672` & `src/utils/address.zig:84-90`)**:
   In `z_loop_sock_accept` (line 134) and `z_loop_sock_recvfrom` (line 672), `addr: std.posix.sockaddr.storage` is initialized to `undefined`:

   ```zig
   d.* = .{
       .future = python_c.py_newref(fut),
       .loop = python_c.py_newref(self),
       .addr = undefined,
   };
   ```

   When the `accept` or `recvmsg` CQE completes, `sock_accept_callback` (line 69) and `sock_recvfrom_callback` (line 601) call `utils.Address.fromStorage(&d.addr)` **without** passing `d.addrlen` or `d.msg.namelen`!
   In `src/utils/address.zig:84-90`:

   ```zig
   pub fn fromStorage(storage: *const std.posix.sockaddr.storage) Address {
       return switch (storage.family) {
           std.posix.AF.INET => .{ .ip4 = @as(*const std.posix.sockaddr.in, @ptrCast(@alignCast(storage))).* },
           std.posix.AF.INET6 => .{ .ip6 = @as(*const std.posix.sockaddr.in6, @ptrCast(@alignCast(storage))).* },
           std.posix.AF.UNIX => .{ .unix = @as(*const std.posix.sockaddr.un, @ptrCast(@alignCast(storage))).* },
           else => unreachable,
       };
   }
   ```

   - For an unnamed `AF_UNIX` client socket (the default for `socket(AF_UNIX, SOCK_STREAM)` connecting to a Unix server, or an unbound `AF_UNIX` datagram sender), the Linux kernel sets `addr.family = AF_UNIX` and `addrlen = sizeof(sa_family_t) = 2`, writing **zero** bytes into `sun_path`!
   - Or for `sock_recvfrom` on a connected stream/datagram socket where the kernel sets `msg.namelen = 0`, the kernel writes **nothing** into `d.addr` (not even `d.addr.family`), so `storage.family` is garbage and hits `else => unreachable` (panic)!
   - In `address_to_python` (`src/loop/python/io/socket/ops.zig:94-99`):
     ```zig
     .unix => |*un| {
         const path_bytes = std.mem.sliceTo(&un.path, 0);
         break :blk python_c.PyUnicode_FromStringAndSize(path_bytes.ptr, @intCast(path_bytes.len)) orelse return error.PythonError;
     },
     ```
     `std.mem.sliceTo(&un.path, 0)` scans up to 108 bytes of uninitialized heap memory in `un.path` until it happens to hit a `0` byte (or end of array) and returns heap garbage as the peer's Unix socket path (instead of `""`)!

2. **Null `pbuf.buf` pointer cast panic in `z_loop_sock_recv_into` (line 521), `z_loop_sock_sendto` (line 797), and `z_loop_sock_sendall` (line 899)**:
   ```zig
   const buf_slice = @as([*]u8, @ptrCast(pbuf.buf))[0..nbytes];
   ```
   In CPython, a newly initialized empty `bytearray()` (or custom buffer object with `len == 0`) has `pbuf.buf == null` and `pbuf.len == 0`. In Zig, `@as([*]u8, @ptrCast(pbuf.buf))` casts a nullable C pointer (`?*anyopaque`) to a non-null many-item pointer (`[*]u8`), which triggers a safety check panic (`cast causes pointer to be null`) whenever `pbuf.buf == null`!
   Notice that `z_loop_sock_sendall` checks `if (total_len == 0)` at line 900 **one line after** the `@as([*]const u8, @ptrCast(pbuf.buf))` cast at line 899!

## Trigger Scenario

1. Call `conn, addr = await loop.sock_accept(unix_server_sock)` when an unnamed `AF_UNIX` client connects -> `addr` contains uninitialized heap bytes instead of `""`.
2. Call `await loop.sock_sendall(sock, bytearray())` or `await loop.sock_recv_into(sock, bytearray())` -> immediate Zig null-pointer cast panic at line 899 / 521.

## Proposed Remediation

1. Zero-initialize `addr = std.mem.zeroes(std.posix.sockaddr.storage)` in `AcceptData` and `SockRecvFromData`, and check `d.addrlen` / `d.msg.namelen` before reading `d.addr`.
2. In `z_loop_sock_recv_into`, `z_loop_sock_sendto`, and `z_loop_sock_sendall`, check `if (pbuf.len == 0 or pbuf.buf == null)` **before** casting `pbuf.buf` to `[*]u8` / `[*]const u8`.


## Resolution

Fixed in `src/loop/python/io/socket/ops.zig`:

1. **Zero-filled storages**: `AcceptData.addr` and `SockRecvFromData.addr`
   are `std.mem.zeroes(...)` instead of `undefined`, so kernel writes shorter
   than `sizeof(sockaddr.storage)` no longer leak stale allocator contents
   into the Python address object.
2. **CPython-matching length handling**:
   - `sock_accept_callback`: a peer whose `addrlen <= offsetof(sockaddr_un,
     path)` on an `AF_UNIX` listener yields `''` (CPython's unnamed-client
     behaviour) instead of reading the zeroed/garbage path.
   - `sock_recvfrom_callback`: `msg.namelen == 0` (kernel wrote nothing —
     unnamed/unbound `AF_UNIX` datagram sender) yields `None` as the sender
     address, exactly like CPython's `recvfrom`.
3. **Null `pbuf.buf` guards**:
   - `z_loop_sock_sendall`: empty data resolves the future immediately with
     `None` — matching CPython, which performs no syscall for
     `sendall(b'')`. (A zero-length write SQE would fail with EFAULT;
     io_uring rejects zero-length writes outright.)
   - `z_loop_sock_sendto`: never dereferences the null buffer while *still
     delivering the empty datagram* — the `msghdr` keeps `msg_iovlen = 0`
     (io_uring's send path rejects a zero-length iovec with EFAULT, but the
     syscall scheme with an empty iov delivers the zero-byte datagram
     normally, receiving it later shows `b''`, `None`).
   - `z_loop_sock_recv_into`: empty/writably-null buffers resolve `0`
     without queueing a syscall — mirroring CPython, where
     `recv_into(bytearray())` returns `0` and leaves already-received data
     queued (proved in the test: the earlier-sent byte is still readable
     afterwards).

## Test

`tests/test_socket_ops.py::test_bug360_unnamed_unix_accept_and_unbound_recvfrom`
covers the two unnamed-`AF_UNIX` address paths; `test_bug360_empty_buffer_socket_ops`
covers all three empty-buffer surgeries (including the delivered empty
datagram and the preserved pending data).

**Bite verification**: both tests fail against a pre-fix ReleaseSafe build —
the accept path fails with `UnicodeDecodeError: 'utf-8' codec can't decode
byte 0xaa` (the undefined storage carried the safe-mode allocator's 0xaa
fill pattern straight into the returned address string), and the empty
`sendall` fails with `OSError(EFAULT)` from the rejected zero-length write
SQE (under Debug/ReleaseSafe pre-fix the null cast also panics). Passes on
3.13/3.13t/3.14/3.14t in ReleaseFast after the fix.

## Discovered During Testing (not part of this fix)

- `loop.sock_sendto` to an abstract-namespace peer obtained from
  `socket.socketpair()`'s auto-bound address fails for *any* payload length
  (ECONNREFUSED) — the auto-bound abstract name does not survive the
  `Address.fromPyAddr` round-trip. CPython delivers to path-bound sockets
  the same way talyn now does; fixing the abstract-name parse belongs to
  the BUG-287 family and needs its own tracking.
