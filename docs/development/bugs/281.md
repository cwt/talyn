# BUG-281 — `submit_next_chunk` state-machine ordering duplicates writes on flush failure

- **Status**: 🔵 Open (2026-08-23)
- **Severity**: 🟡 Medium-High — Duplicate data / UAF of released Python buffers
- **Files**:
  - `src/transports/write_transport.zig:198-217` (`io.queue(.PerformWrite)` — SQE queued, deferred submission)
  - `src/transports/write_transport.zig:218` (`py_incref(parent_transport)`)
  - `src/transports/write_transport.zig:219` (`try flush_pending_sqes()` — fallible while SQE stays queued)
  - `src/transports/write_transport.zig:222` (`write_in_flight = true` set LAST)
  - `src/transports/write_transport.zig:262-264` (consumed Py_buffer released after first completion)
  - `src/transports/write_transport.zig:86-92` (prepare hook resubmits when `!write_in_flight`)
- **Lessons**: [io_uring & Kernel Interaction §Lesson 9](../lessons/04-io-uring-and-kernel.md), [Defensive Programming](../lessons/10-defensive-programming-and-code-quality.md)
- **Description**: If `flush_pending_sqes` fails, the SQE remains in the ring but `write_in_flight == false`. The prepare hook then calls `submit_next_chunk` again for the SAME offset: duplicated bytes to the peer, two completions advancing offsets twice, and the first completion releasing the `Py_buffer` whose memory the second in-flight kernel write still references.
- **Trigger**: `io_uring_enter` failure under SQ pressure (EAGAIN/enqueue-full) during vectored writes.
- **Consequences**: Protocol-level data duplication plus kernel reading freed/reused Python buffer memory.
- **Fix (Proposed)**: Set `write_in_flight = true` immediately after a successful queue, before flushing; treat flush failure as retryable without requeueing.
