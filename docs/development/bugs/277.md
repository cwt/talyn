# BUG-277 — Duplicate-pid `add_child_handler` silently orphans the previous handler

- **Status**: 🟢 Fixed (2026-08-23)
- **Severity**: 🟠 High — fd leak / refcount leak / memory leak / wrong logic
- **Files**:
  - `src/loop/child_watcher.zig:76` (`self.handlers.putAssumeCapacity(pid, handler)` — no duplicate guard)
  - `src/loop/child_watcher.zig:190-198` (`on_child_exit` fetchRemove identity check drops the *new* entry uncleaned when the orphan fires first)
- **Lessons**: [Concurrency & Thread Safety §Lesson 99](../lessons/02-concurrency-and-thread-safety.md)
- **Description**: Re-registering a pid (a normal asyncio child-watcher pattern) overwrites the map entry. The old handler is never cleaned up: pidfd stays open (fd leak), callback reference never released (PyObject leak), struct never freed. Its armed `WaitReadable` still references it; when it later fires, `fetchRemove(handler.pid)` evicts the NEW entry, the pointer identity check fails, and the new handler is dropped without cleanup as well.
- **Trigger**: Calling `add_child_handler(pid, ...)` twice for the same pid.
- **Consequences**: Bounded-resource fd exhaustion plus permanent Python reference leaks per re-registration; `remove_child_handler(pid)` can also return false unexpectedly.
- **Fix (Applied — 2026-08-23)**: `add_child_handler` now `fetchRemove`s any existing entry just before `putAssumeCapacity` and runs the identical teardown sequence (cancel armed op, close pidfd, decref callback, free struct).
- **Regression test**: `tests/test_child.py::test_duplicate_add_child_handler_replaces_cleanly` — double register + remove semantics + loop liveness.
