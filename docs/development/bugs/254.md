# BUG-254 — execute_task_throw passes borrowed `task.exception` → use-after-free / double-free

- **Status**: 🔍 Open
- **Severity**: 🔴 Critical — Memory safety / reference-counting (use-after-free, double-free, refcount underflow)
- **Files**: `src/task/callbacks.zig`
- **Lessons**: [Memory §Reference Count Discipline](../lessons/01-memory-and-reference-counting.md)
- **Description**: `create_new_py_exception_and_add_event` stores an owned reference: `python_c.py_xdecref(task.exception); task.exception = exception;` (lines 171-172). `execute_task_throw` then calls `@call(.always_inline, _execute_task_throw, .{ task, task.exception.? })` at line 498 — passing that reference **borrowed**. Inside `_execute_task_throw`, the `defer if (exception_value) |ev| python_c.py_decref(ev);` at line 431 decrements `task.exception`'s object to **zero and frees it**, while the `task.exception` field is **never set to `null`**. Every other caller passes an owned copy: `wakeup_task` uses `python_c.py_newref(exception)` (line 600) and `py_wake_up` passes a `PyErr_GetRaisedException()` owned ref (line 648). This is the only caller that transfers ownership incorrectly.
- **Trigger**: A coroutine raises, or is yielded a bad future (legacy future whose `_asyncio_future_blocking` is not a bool, self-await, or a future in another loop), so `create_new_py_exception_and_add_event` sets `task.exception` and schedules `execute_task_throw`, which runs its non-cancelled throw path (line 498).
- **Consequences**: After the callback returns, `task.exception` is a dangling pointer. `task_traverse` (GC) and the type's `tp_clear` / `deinitialize_object_fields` later read or `py_decref` the freed object → **use-after-free, double-free, and refcount underflow**; potential crash or memory corruption during GC.
- **Resolution**: Pass an owned copy so the callee's defer consumes the copy and `task.exception` stays valid: `@call(.always_inline, _execute_task_throw, .{ task, python_c.py_newref(task.exception.?) })` at line 498 (mirroring `wakeup_task`). Optionally also clear `task.exception = null` inside `_execute_task_throw` after consuming.
- **Verification**: Repro — schedule a task that awaits an object whose `_asyncio_future_blocking` is not a bool, drive the loop, then force `gc.collect()`; assert `task.exception` remains a valid object after the throw callback. Add a unit test that the same `task.exception` is still traversable post-throw.
