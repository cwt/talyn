# BUG-389 — Python C-API error handling bugs: `PyObject_IsTrue(...) != 0` treating `-1` as `true`, returning `null` without setting Python exception, `setup_asyncgen_hooks` partial failure leak, and `z_loop_create_task` passing `name` to custom `task_factory`

- **Status**: 🔴 Open
- **Severity**: 🟡 Medium — violates CPython C-API error conventions (`SystemError: returned NULL without setting an exception`, or continuing execution with a live exception after `PyObject_IsTrue` returns `-1`) and breaks custom `loop.set_task_factory` callbacks when `loop.create_task(coro, name=...)` is called

## Overview & Root Cause

1. **`PyObject_IsTrue(obj) != 0` treats `-1` (error) as `true` across 9 call sites**:
   In CPython, `PyObject_IsTrue(obj)` returns `1` for true, `0` for false, and **`-1` on error** (when `__bool__` raises an exception).
   Checking `python_c.PyObject_IsTrue(obj) != 0` evaluates `-1 != 0` as **`true`** and continues execution with an active exception on the CPython thread state!
   Affected sites:
   - `src/loop/python/control.zig:96`: `self.debug = python_c.PyObject_IsTrue(enabled.?) != 0;`
   - `src/loop/python/io/client/create_connection.zig:701`: `const is_ssl = if (creation_data.py_ssl) |s| python_c.PyObject_IsTrue(s) != 0 else false;`
   - `src/loop/python/io/datagram/create_endpoint.zig:117, 244, 251`: `reuse_port` and `allow_broadcast`
   - `src/loop/python/io/server/create_server.zig:406, 411`: `reuse_address` and `reuse_port`
   - `src/transports/stream/lifecycle.zig:58`: `const closed = python_c.PyObject_IsTrue(is_closed_py) != 0;`

2. **Returning `error.PythonError` (`null`) without setting a Python exception (`src/loop/python/control.zig:214, 224, 308`)**:
   In `z_loop_add_hook` (lines 214, 224) and `z_loop_watch_path` (line 308):
   ```zig
   if (python_c.PyCallable_Check(callback) == 0) {
       return error.PythonError;
   }
   ```
   `PyCallable_Check` does **not** set a Python exception when it returns `0`! And `utils.handle_zig_function_error(error.PythonError, null)` assumes a Python exception is already set on the thread state, returning `null` to CPython with no exception set (`SystemError: <built-in method> returned NULL without setting an exception`).
   Similarly, in `z_loop_set_exception_handler` (`src/loop/python/control.zig:379-394`), `PyCallable_Check(h) < 0` is checked instead of `PyCallable_Check(h) == 0`, so non-callable objects are silently accepted as the loop's exception handler instead of raising `TypeError`!

3. **`z_loop_create_task` passes `name` as a 3rd positional argument to custom `task_factory` (`src/loop/python/utils/task.zig:56-82`)**:
   ```zig
   if (self.task_factory) |factory| {
       task = python_c.PyObject_CallFunctionObjArgs(
           factory, self, coro, name, @as(?PyObject, null)
       ) orelse return error.PythonError;
   ```
   Per the Python `asyncio` specification (`loop.set_task_factory`), a custom `task_factory` has signature `factory(loop, coro, **kwargs)` (2 positional arguments: `(loop, coro)`, plus optional `context=` in Python 3.11+), **and `task.set_name(name)` is called by `loop.create_task` AFTER `factory(loop, coro)` returns `task`**!
   Furthermore, in `PyObject_CallFunctionObjArgs`, `null` is the **varargs sentinel**! When `name` is `null` (not passed), `name` acts as the sentinel (2 args passed); when `name` is non-null (e.g. `loop.create_task(coro, name="worker")`), `PyObject_CallFunctionObjArgs` passes **3 positional arguments** `(self, coro, name)` to `factory(loop, coro)`, crashing every standard 2-argument custom `task_factory` with `TypeError: factory() takes 2 positional arguments but 3 were given`!

4. **`setup_asyncgen_hooks` leaks `weakref_mod` / `weakset_cls` on partial failure (`src/loop/python/hooks.zig:80-104`)**:
   If `PyObject_CallNoArgs(weakset_cls)` fails at line 85, `weakref_mod` and `weakset_cls` are not decref'd! And if `PyObject_CallFunctionObjArgs(set_hooks, ...)` fails at line 99, `self.asyncgens` is already assigned without saving `old_firstiter`/`old_finalizer`. Also, in `asyncgen_firstiter_hook` (lines 14–26) and `asyncgen_finalizer_hook` (lines 56–68), `loop_obj` is cast to `*LoopObject` without `python_c.type_check(loop_obj, Loop.Python.LoopType)` (which crashes if a stdlib `asyncio` loop is running on another thread).

## Trigger Scenario

1. Set a custom task factory `loop.set_task_factory(lambda loop, coro: asyncio.Task(coro, loop=loop))` and call `loop.create_task(coro, name="my_task")` -> raises `TypeError: <lambda>() takes 2 positional arguments but 3 were given`.
2. Call `loop.add_hook(0, "not_callable")` -> raises `SystemError: returned NULL without setting an exception`.
3. Call `loop.set_exception_handler("not_callable")` -> succeeds without raising `TypeError`.

## Proposed Remediation

1. Replace `PyObject_IsTrue(x) != 0` with a helper that checks `const rc = python_c.PyObject_IsTrue(x); if (rc < 0) return error.PythonError; const truthy = rc == 1;`.
2. Call `python_c.raise_python_type_error("callback must be callable\x00")` when `PyCallable_Check(...) == 0` in `z_loop_add_hook`, `z_loop_watch_path`, and `z_loop_set_exception_handler`.
3. In `z_loop_create_task` (`src/loop/python/utils/task.zig:56-82`), call `factory(self, coro)` (passing `context=` keyword if provided), and if `name` is non-null, call `set_name(name)` on the returned task.
4. Add `defer python_c.py_decref(weakref_mod)` and `defer python_c.py_decref(weakset_cls)` in `setup_asyncgen_hooks` and check `type_check(loop_obj, Loop.Python.LoopType)` in `hooks.zig`.
