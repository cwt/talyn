# BUG-285 — `start_exit_watcher` queue-failure path: stale closed pidfd + orphaned incref

- **Status**: 🔵 Open (2026-08-23)
- **Severity**: 🟡 Medium — Refcount leak + fd double-close hazard
- **Files**:
  - `src/transports/subprocess/transport.zig:388` (`transport.pidfd = pidfd`)
  - `src/transports/subprocess/transport.zig:389` (`errdefer close(pidfd)` — does not reset the field)
  - `src/transports/subprocess/transport.zig:391-403` (`py_incref(transport)` then `try io.queue(...)`; no errdefer for the incref)
  - `src/transports/subprocess/transport.zig:171-174` (later `subprocess_close` closes `instance.pidfd >= 0` unconditionally)
- **Lessons**: [Memory & Reference Counting §Lesson 107](../lessons/01-memory-and-reference-counting.md), [io_uring & Kernel Interaction](../lessons/04-io-uring-and-kernel.md)
- **Description**: Two defects on one path. (1) When `io.queue` fails, no op was registered so no cleanup will ever run — but the `+1` self-reference from :391 is never dropped → the transport object leaks permanently. (2) The errdefer closes the descriptor while `transport.pidfd` keeps the now-invalid number; a later close hits whatever fd the kernel reassigned (classic double-close hazard). Distinct from fixed BUG-196 and open BUG-223 (different paths).
- **Trigger**: Submission-ring exhaustion or OOM while starting a subprocess exit watcher.
- **Consequences**: Transport leak per occurrence; spurious closure of unrelated descriptors.
- **Fix (Proposed)**: Add `errdefer python_c.py_decref(@ptrCast(transport));` after :391 and reset `transport.pidfd = -1` inside the :389 errdefer.
