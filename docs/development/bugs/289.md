# BUG-289 — `RingBuffer(N).try_push` publish order defeats GC traversal on slot reuse

- **Status**: 🔵 Open (2026-08-23)
- **Severity**: 🟡 Medium — Free-threading GC race / latent UAF
- **Files**:
  - `src/callback_manager.zig:182-185` (`callbacks[idx] = callback`; store `write_idx`; then `executed[idx] = false`)
  - `src/callback_manager.zig:224-252` (`traverse` skips in-range slots with `executed == true`)
  - `src/callback_manager.zig:343-352` (`DynamicRingBuffer.try_push` does it in the SAFE order — inconsistency proves intent)
- **Lessons**: [Memory & Reference Counting §Lesson 4](../lessons/01-memory-and-reference-counting.md), [Concurrency & Thread Safety §Lesson 1](../lessons/02-concurrency-and-thread-safety.md)
- **Description**: Physical slots are recycled, so `executed[idx]` holds `true` from the previous consumption. Between the `write_idx` release-store and the `executed=false` store, a concurrent free-threaded GC `traverse()` sees the new element as in-range but skips it because `executed` still reads true — objects pinned only by that callback (e.g., a Task visited via payload.traverse) become invisible for that pass and can be collected → UAF when the callback later executes.
- **Trigger**: Free-threading builds with concurrent cycle collection coinciding with ring wraparound.
- **Consequences**: Rare but catastrophic premature collection of live tasks/futures.
- **Fix (Proposed)**: Clear `executed[idx]` BEFORE publishing `write_idx`, matching the DynamicRingBuffer order.
