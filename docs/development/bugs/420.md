# BUG-420 — `task_clear` decrefs `result` before nulling it (re-entrant finalizer UAF)

- **Status**: 🟡 Open
- **Severity**: 🟠 High — use-after-free through `Task.result()`/`exception()` from a finalizer
- **Category**: GC `tp_clear` ordering / re-entrancy
- **Files**: `src/task/constructors.zig:120-141`, `src/future/python/constructors.zig:51-71`
- **Related**: [BUG-369](369.md) (the `future_clear` fix), [BUG-341](341.md), [BUG-386](386.md)

## Description

```zig
const _result = future_data.result;
if (_result) |res| {
    python_c.py_decref(@ptrCast(@alignCast(res)));   // decref FIRST
    future_data.result = null;                        // null SECOND
}
future_data.release();
```

The sibling `future_clear` was explicitly fixed for BUG-369 to **detach before decref**
(`future_data.result = null;` then `py_decref`) because the decref can synchronously run the
result object's finalizer, which re-enters `Task.result()` while `future_data.result` still points
at the dying object. `task_clear` still uses the old (unsafe) order.

## Trigger

A reference cycle containing a finished `Task` whose result object defines `__del__` that calls
`task.result()` / `task.exception()`, collected by the cycle GC.

## Consequences

`get_result` sees `status == .finished` with a non-null, already-freed `result` → use-after-free /
`InvalidStateError` inconsistency, possible crash.

## Fix

Swap to detach-before-decref:

```zig
const _result = future_data.result;
future_data.result = null;
if (_result) |res| python_c.py_decref(@ptrCast(@alignCast(res)));
```
