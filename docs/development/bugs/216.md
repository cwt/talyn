# BUG-216 — Premature `continue` in `fetch_completed_tasks` on null stream protocol causes permanent `reserved_slots` desync and `blocking_task` allocation leak

- **Status**: 🔴 Open
- **Severity**: 🔴 Critical — Event Loop Slot Corruption & Memory Leak
- **Files**: `src/loop/runner.zig:220`
- **Lessons**: [Event Loop Lifecycle §Lesson 3](../lessons/03-event-loop-lifecycle.md), [Memory & Reference Counting §Lesson 1](../lessons/01-memory-and-reference-counting.md)
- **Description**: In `src/loop/runner.zig`, `fetch_completed_tasks` attempts to optimize CQE completion handling by batching consecutive `ReadTransport.read_operation_completed` events. Line 220 executes `_ = stream_transport.protocol orelse continue;`. When `stream_transport.protocol` is `null` (such as during transport shutdown, close, or protocol swapping), `continue` immediately jumps to the next CQE in the outer `while (index < cqe_len)` loop. This skips:
  1. `blocking_task.check_result(err)`
  2. `ready_queue.try_push(v.*)`
  3. `self.reserved_slots -= 1`
  4. `blocking_task.deinit()` (which returns the task to the pool)
- **Trigger**: CQE completion arrives for a `ReadTransport` whose parent `StreamTransportObject.protocol` has been cleared to `null` or is closing.
- **Consequences**: `self.reserved_slots` is permanently decremented out-of-sync, leading to slot starvation where new IO tasks cannot be reserved. The `blocking_task` heap memory is permanently leaked and never returned to the pool.
- **Fix**: Guard the batching logic with `if (stream_transport.protocol != null) { ... }` so if `protocol` is null, batching is skipped and the loop falls through to normal push and task cleanup.
