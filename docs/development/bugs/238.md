# BUG-238 — `StreamTransportObject.fixed_file_index` not initialized in `z_stream_new`

- **Status**: ✅ Fixed
- **Severity**: 🟢 Low — Uninitialized field / GC safety
- **File**: `src/transports/stream/constructors.zig:~115-140` (z_stream_new)
- **Lessons**: [Zig §Lesson 49 — Struct Initialization](../lessons/08-zig-specific-patterns.md), [Zig §Lesson 50 — Stale CompletionRecord Detection](../lessons/01-memory-and-reference-counting.md), [BUG-204](0204.md) (uninitialized struct field after tp_alloc)
- **Description**: In `z_stream_new`, `initialize_object_fields` is called with a specific list of fields to zero-initialize:

  ```zig
  python_c.initialize_object_fields(instance, &.{"ob_base", "fd", "family", "protocol_type", "is_closing", "closed"});
  ```

  The `fixed_file_index` field (type `u16`, default `0` in struct definition) is **not** in this list. While struct literal defaults only apply to struct literals (not `tp_alloc` memory), the field is explicitly set later:

  ```zig
  self.fixed_file_index = 0;  // ← This line exists in stream_init_configuration, NOT in z_stream_new
  ```

  Looking more carefully at `z_stream_new` (line ~130), `fixed_file_index` is indeed missing from both the `initialize_object_fields` call AND the explicit field assignments that follow. The field remains as whatever garbage bytes were in the `tp_alloc`-allocated memory.

  In practice this is low-severity because:
  1. `z_stream_new` is only called from `stream_new` which is a Python `__new__` method, and the object is immediately initialized via `stream_init` → `stream_init_configuration` which sets it.
  2. The `dispatch_generation` field (which has the same pattern) was explicitly fixed in BUG-32 with a comment.

  However, the same pattern is missing for `fixed_file_index`, and if the initialization order ever changes, this could become a real issue.

- **Trigger**: Any code path that creates a `StreamTransportObject` via `tp_alloc` without immediately calling `stream_init_configuration`.
- **Consequences**: Uninitialized `fixed_file_index` read during GC traverse or early teardown → potential invalid fixed-file slot release or silent fd leak.
- **Fix**: Add `"fixed_file_index"` to the `initialize_object_fields` call in `z_stream_new`, matching the pattern used for `dispatch_generation`.
