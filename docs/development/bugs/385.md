# BUG-385 — `ControlData.traverse` omits `v.data.traverse()` on pending DNS user callbacks, and multiple IO callback state structs lack GC `traverse` wiring

- **Status**: 🟢 Fixed
- **Severity**: 🟠 Medium-High — reference cycles involving `LoopObject`, `FutureObject`, `protocol_factory`, or `ssl` contexts held inside in-flight DNS/socket/connection callbacks are invisible to `loop_traverse` and CPython's cycle GC
- **Category**: Logic Bug (GC Traversal Incomplete)
- **Files**:
  - `src/loop/dns/resolv.zig:232-244`
  - `src/loop/python/io/client/create_connection.zig`
  - `src/loop/python/io/server/create_server.zig`
  - `src/loop/python/io/datagram/create_endpoint.zig`
  - `src/loop/python/io/pipe/unix.zig`
  - `src/loop/python/io/socket/ops.zig`
  - `src/loop/python/io/socket/getaddrinfo.zig`
  - `src/loop/python/io/socket/getnameinfo.zig`
- **Related**: [Lesson 44](../lessons/05-python-c-api-correctness.md)

## Overview & Root Cause

1. **`ControlData.traverse` in `src/loop/dns/resolv.zig:232-244` omits `v.data.traverse`**:
   Compare `CallbackManager.CallbacksSet.traverse` (`src/callback_manager.zig:239-260`), which visits both `item.data.exception_context` and `if (item.data.traverse) |t|`:
   ```zig
   if (item.data.traverse) |t| {
       const ret = t(item.data.user_data, visit, arg);
       if (ret != 0) return ret;
   }
   ```
   with `ControlData.traverse` in `src/loop/dns/resolv.zig:232-244`:
   ```zig
   pub fn traverse(self: *ControlData, visit: python_c.visitproc, arg: ?*anyopaque) c_int {
       for (self.user_callbacks.items) |*v| {
           if (v.data.exception_context) |exc_context| {
               if (exc_context.callback_ptr) |cb| {
                   const ret = visit.?(cb, arg);
                   if (ret != 0) return ret;
               }
               ...
           }
       }
       return 0;
   }
   ```
   `ControlData.traverse` completely forgets to call `if (v.data.traverse) |t| { const ret = t(v.data.user_data, visit, arg); if (ret != 0) return ret; }`!

2. **Heap-allocated IO callback state structs do not provide `CallbackData.traverse`**:
   While `Handle.traverse_for_python_generic_callbacks` (`src/handle.zig:103`) and `Future.Callback.traverse_python_future_callbacks_set_data` (`src/future/callback.zig:134`) wire up `.traverse` on `CallbackData`, none of the async IO state structs that hold strong `PyObject` references to `LoopObject`, `FutureObject`, `protocol_factory`, etc. (`SocketConnectionData`, `TransportCreationData`, `MultiConnectState`, `ServerSocketData`, `DatagramCreationData`, `UnixConnectData`, `GetAddrInfoData`, `GetNameInfoData`, `AcceptData`, `SockConnectData`, `SockRecvData`, `SockRecvIntoData`, `SockRecvFromData`, `SockSendToData`, `SockSendallData`) set `.traverse` on their `CallbackManager.CallbackData`.

## Trigger Scenario

If a `Loop` and a pending `Future` / `protocol_factory` closure form an isolated reference cycle while a DNS query or socket operation is queued (and the program drops all external references to the loop), CPython's cyclic GC cannot see the `LoopObject` and `FutureObject` references held inside the pending callback's `user_data` struct.

## Resolution

1. In `src/loop/dns/resolv.zig:ControlData.traverse`, added `if (v.data.traverse) |t| { const ret = t(v.data.user_data, visit, arg); if (ret != 0) return ret; }`, properly propagating GC visits to pending callback user data.
2. In `src/loop/python/io/socket/getaddrinfo.zig` and `src/loop/python/io/socket/getnameinfo.zig`:
   - Added `python_payload: python_c.CallbackPythonPayload` to `GetAddrInfoData` and `GetNameInfoData`.
   - Implemented `traverse(user_data, visit, arg)` visiting `self.future` and `self.loop`.
   - Initialized `CallbackData.init_python(data, &data.python_payload)` with `.traverse = traverse`.
3. Added GC cycle tests in `tests/test_dns_resolver_resilience.py` (`test_dns_gc_cycle_traversal_getaddrinfo`, `test_dns_gc_cycle_traversal_getnameinfo`) and verified across all four Python versions.
