# BUG-223 — Reference count leak on io_uring re-arm failure in `SubprocessTransport.pidfd_exit_callback`

- **Status**: ✅ Fixed
- **Severity**: 🟠 High — Python Reference Count Leak
- **Files**: `src/transports/subprocess/transport.zig:340-356`
- **Lessons**: [Memory & Reference Counting §Lesson 1](../lessons/01-memory-and-reference-counting.md), [Python C-API Correctness §Lesson 5](../lessons/05-python-c-api-correctness.md)
- **Description**: In `src/transports/subprocess/transport.zig`, when `waitid` returns a non-fatal retry status, `pidfd_exit_callback` prepares to re-arm the pidfd readable watcher. It calls `python_c.py_incref(@ptrCast(transport))` and then executes `transport.pidfd_task_id = try loop.io.queue(...)`. If `loop.io.queue` returns an error (e.g. `SystemResources`, ring exhaustion, or OOM), the function returns with an error immediately. Since `success` remains `false`, the function's local `defer if (success)` does not execute. `CallbackManager` catches the error and executes `cleanup_pidfd` for the prior task, but the newly incremented reference added before `try` is leaked.
- **Trigger**: Failure during `loop.io.queue` when re-arming a pidfd readable watcher on subprocess status check retry.
- **Consequences**: Permanent Python reference count leak on `SubprocessTransportObject`.
- **Fix**: Added `errdefer python_c.py_decref(@ptrCast(transport));` immediately after `python_c.py_incref(transport);`. (2026-08-23 audit note: the re-arm path no longer exists — `pidfd_exit_callback` now finalizes in every branch, so the leak site is gone entirely.)
