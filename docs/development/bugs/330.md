# BUG-330 — SQ pressure corrupts a WriteTransport ArrayList header (iovec-shaped overwrite)

- **Status**: 🔴 Open (2026-09-07)
- **Severity**: 🔴 High — Heap corruption under write pressure: garbage list headers, OutOfMemory from a healthy allocator, pre-existing flaky SIGSEGV/MemoryError in the SQ-pressure regression
- **Files**:
  - `src/transports/write_transport.zig` (victim: `pending_buffers` / `pending_py_buffers` list headers)
  - Suspect surface: the `PerformWrite`/`PerformWriteV` `BlockingTask` slot lifecycle (`src/loop/scheduling/io/main.zig`, `src/loop/scheduling/io/write.zig`) — 16-byte `write_iov`/`msg_storage` stores into task slots
- **Lessons**: [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md), [io_uring & Kernel](../lessons/04-io-uring-and-kernel.md)
- **Description**:
  Under the `test_writev_sq_pressure_no_double_free` pressure profile (300 transports × 20 rounds of 8×4KB `writelines` into a peer that accepts but never reads), `append_new_buffer_to_write` intermittently fails with `error.OutOfMemory` while the failing list shows:
  - `items.len` = a corrupted-pointer-shaped value (observed `0x6f785a0ba2a8dbfe` — bit-level noise around a userspace pointer), and
  - `capacity` intact.
  The write therefore targets exactly the first 16 bytes of the heap-allocated list header — an **iovec-shaped `{base, len}` overwrite** (the `BlockingTask` pool stores iovec/msghdr data in 16-byte-shaped fields: `write_iov`, `msg_storage`).
- **Established constraints (from the 2026-09-07 investigation)**:
  1. **Needs multiple transports** — a single-transport 200-round variant is clean (3/3).
  2. **Load/layout sensitive** — the failure rate flipped with system state (dirty leftover-socket state vs calm) and across compiler builds; an interleaved base-vs-tip A/B is therefore NOT reliable evidence for code regressions in this area (an early A/B wrongly suspected unrelated commits).
  3. **The `-Ddebug-alloc` build did not reproduce** (timing changes).
  4. **Valgrind clean** (the race window closes under instrumentation).
  5. The pre-existing flaky SIGSEGV/MemoryError symptoms of the SQ-pressure test were ALSO partly caused by BUG-329's double-release (now fixed) — with that fix, the segfault class is gone, but this OOM/corruption signature remains reproducible (8/8 on the fixed binary during one window).
- **Root Cause**: Undetermined. Leading hypothesis: a stale/duplicated `BlockingTask` slot write (an iovec store through a corrupted or reused `data_ptr`) lands on the freed-and-reused heap neighbourhood of a transport's list headers. The slot lifecycle under SQ pressure (`get_blocking_tasks_set` set rotation, `discard`/`deinit` reuse, BUG-290-class stale ids) is the audit target.
- **Trigger Scenario**: Sustained multi-transport `writelines` pressure with kernel-side backpressure (peer never reads).
- **Proposed Remediation (investigation plan)**:
  1. Deterministic reproducer: drive N transports with fine-grained SQ-pressure forcing (`ulimit`, small rings) so the failure rate approaches 100%.
  2. Audit every 16-byte store in the write submission path (`PerformWrite`/`PerformWriteV` slot fields) for stale-slot reuse, and audit `get_blocking_tasks_set` rotation vs in-flight ops.
  3. Watchpoint the failing list header (gdb `watch`, deterministic reproducer first) to identify the writer.
  4. Consider poisoning task-slot free/alloc transitions in a `-Ddebug-alloc`-gated build to surface stale writes.

## Validation (2026-09-07)

Discovered during the BUG-329 investigation: after fixing the double-release and stuck in-flight flag, the SQ-pressure repro still fails with the OOM signature above (8/8 in one window, 0/16 in another across fresh builds — load sensitive).
