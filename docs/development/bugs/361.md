## Overview & Root Cause

Although [BUG-324](324.md) fixed a subset of integer narrowing casts, a comprehensive audit of all Python-to-Zig numeric conversions uncovered unchecked `@intCast` and `@intFromFloat` sites that panic on out-of-range Python inputs:

1. **`DnsTimeout.from_seconds` float-to-integer overflow (`src/loop/dns/resolv.zig:26, 56`)**:
   ```zig
   const whole_sec: i64 = @intFromFloat(secs);
   ```
   `parse_dns_timeout` (`src/loop/python/utils/time.zig:7-22`) rejects `NaN`, `Inf`, and `<= 0`, but allows finite floats like `1e20` (`> std.math.maxInt(i64)`), causing `@intFromFloat(secs)` to panic in `DnsTimeout.from_seconds`.

2. **Port, flowinfo, and scope_id narrowing to `u16` / `u32` without bounds checks**:
   - `src/loop/python/io/socket/ops.zig:250, 260, 265` (`parse_py_address` for `sock_connect` / `sock_sendto`):
     `@intCast(port_long)` to `u16`, `@intCast(fi)` to `u32`, and `@intCast(si)` to `u32` with no bounds checks (`port = -1` or `port = 70000` panics!).
   - `src/loop/python/io/datagram/create_endpoint.zig:62` (`parse_addr_tuple`):
     `return .{ .host = host, .port = @intCast(port_long) };` panics on `port < 0` or `port > 65535`.
   - `src/loop/python/io/client/create_connection.zig:691`:
     `break :blk @intCast(p);` (`u16`) panics on `port < 0` or `port > 65535`.
   - `src/loop/python/io/server/create_server.zig:396`:
     `break :blk @intCast(p);` (`u16`) panics on `port < 0` or `port > 65535`.
   - `src/loop/python/io/socket/getaddrinfo.zig:139, 147, 152, 157`:
     `@intCast(v)` to `u16` (`port`) and `i32` (`family`, `sock_type`, `proto`) without bounds checks.
   - `src/loop/python/io/socket/getnameinfo.zig:88`:
     `const flags: u32 = @intCast(flags_long);` panics on negative `flags`.

3. **Socket `fd`, `family`, `backlog`, `nbytes`, and `mask` narrowing without bounds checks**:
   - `src/loop/python/io/socket/ops.zig:127, 381, 502, 650, 659, 664, 780, 886, 987`:
     `@intCast(fd_long)` to `std.posix.fd_t` (`i32`), `@intCast(family_long)` to `u16`, and `@intCast(nbytes_raw)` to `usize` (`sock_recv_into` at line 502 checks `if (nbytes_raw < 0)` only at line 503 **after** `@intCast` at line 502!).
   - `src/loop/python/io/watchers.zig:158, 228`:
     `const fd: std.posix.fd_t = @intCast(py_fd);` panics if `py_fd > maxInt(i32)` or `< minInt(i32)`.
   - `src/loop/python/io/client/create_connection.zig:164, 174, 181` & `src/loop/python/io/server/create_server.zig:116, 126` & `src/loop/python/io/datagram/create_endpoint.zig:236` & `src/loop/python/io/pipe/unix.zig:192`:
     `@intCast` on `fileno()`, `family`, and `backlog` without `std.math.cast`.
   - `src/loop/python/control.zig:107-108, 222, 344-345, 371`:
     `@intCast(fd_long)`, `@intCast(how_long)`, `@intCast(kind_long)`, `@intCast(mask_long)` (`u32`), and `@intCast(pid_long)` (`pid_t`) without `std.math.cast`.
   - `src/loop/child_watcher.zig:65`:
     `const pid_fd: std.posix.fd_t = @intCast(rc);` before checking if `pidfd_open` returned an errno (`@as(isize, @bitCast(rc)) < 0`)! If `pidfd_open` fails (e.g. `ESRCH` or `EMFILE`), `rc` is `~usize(0) - errno`, which panics on `@intCast` to `i32` before line 66 is reached!
   - `src/utils/pseudosocket.zig:182-183`:
     `const level: i32 = @intCast(level_long); const optname: i32 = @intCast(optname_long);` without `std.math.cast`.

## Trigger Scenario

1. Call `await loop.sock_connect(sock, ("127.0.0.1", 70000))` or `await loop.create_connection(factory, "127.0.0.1", -1)` -> immediate Zig `@intCast` panic instead of `OverflowError` / `ValueError`.
2. Call `loop.add_child_handler(nonexistent_pid, cb)` -> `pidfd_open` returns `-ESRCH` as `usize`, and `@intCast(rc)` at `src/loop/child_watcher.zig:65` panics before the error check on line 66!
3. Call `await loop.sock_recv_into(sock, buf, -1)` -> line 502 executes `@intCast(nbytes_raw)` to `usize` before line 503's `if (nbytes_raw < 0)` check!

## Proposed Remediation

1. Replace all unchecked `@intCast` conversions of Python-supplied integers with `std.math.cast(TargetType, val) orelse { python_c.raise_python_value_error(...); return error.PythonError; }`.
2. In `src/loop/child_watcher.zig:64-68`, check `switch (std.posix.errno(rc))` **before** casting `rc` to `std.posix.fd_t`.
3. In `src/loop/python/io/socket/ops.zig:502-503`, check `if (nbytes_raw < 0)` **before** `@intCast(nbytes_raw)`.
4. In `DnsTimeout.from_seconds` (`src/loop/dns/resolv.zig:26`), clamp or reject `secs >= @as(f64, @floatFromInt(std.math.maxInt(i64)))` before `@intFromFloat`.


## Resolution

Added `utils.checkedNarrow(comptime T, value, what)` — a range-checking
narrowing helper that raises `ValueError` instead of panicking (or silently
truncating in ReleaseFast) — and applied it at every Python-supplied
integer entry point:

| Entry point | Guarded values |
| --- | --- |
| `loop.sock_*` (accept/connect/sendall/sendto/recv/recvfrom/recv_into) | `fd` (7 sites from `fileno()`), `family` (3 sites, incl. the monkey-patchable `sock.family` attribute) |
| `loop.create_server` | sock= `fileno` (i64 upper bound), `family`, user `port` (0–65535), `getsockname` ports (2 sites), `backlog >= 0` (a negative value panicked the `listen()` u32 narrowing) |
| `loop.create_connection` | `port` (0–65535; negative values panicked the u16 narrowing), sock= `fileno` upper bound |
| `loop.create_datagram_endpoint` | `get_addr_tuple` ports, `family` (u32; negatives panicked) |
| `loop.getaddrinfo` | `port` (0–65535), `family`/`type`/`proto` (i32) |
| `loop.getnameinfo` | `flags` |
| `loop._add_hook` | hook type (i32); the invalid-hook-type `else` branch now raises `ValueError` properly instead of returning bare `error.PythonError` (which surfaced as `SystemError`) |
| `loop._add_path_watcher` | inotify mask (u32) |
| `loop.add_reader/add_writer/remove_reader/remove_writer` | `fd` (add + remove paths) |
| `loop.add_child_handler` / `remove_child_handler` | `pid` (i32) |
| `getsockopt` (PseudoSocket) | `level`/`optname` (mirrors the BUG-324 `setsockopt` fix) |
| `StreamTransport.__init__`, `StreamServer.__init__`, `DatagramTransport.__init__` | `fd` (`fd_t` bounds) and `family` (`c_int`), plus fixed `DatagramTransport.__init__` format string from `"OO\|L"` to `"OO\|O"` for `py_fd: ?PyObject` |

## Analysis Note (2026-10-18 audit)

The report's line numbers had drifted against the post-BUG-324/326 tree, and
several of its items no longer reproduced:

- `child_watcher.zig`'s `@intCast(rc)` already runs *after* the
  BUG-326 errno check, so a failed `pidfd_open` can no longer reach it.
- `parse_py_address`'s port/flowinfo/scope_id casts were already guarded by
  BUG-324 (`fromPyAddr` raises `ValueError` for ports outside 0–65535).
- `DnsTimeout.from_seconds`'s float→u64 `@intFromFloat` was already bounded
  by an isFinite/negative/max-secs clamp — but the parsed seconds could
  still exceed `maxInt(i64)`, panicking later at
  `dns_timeout_to_kernel_timespec`'s i64 narrowing. `timeout_from_secs` now
  clamps to `maxInt(i64) / 2` (exactly representable in f64, ~146 Myr —
  already "effectively forever" for a DNS timeout).
- `create_connection`'s `interleave` cast is a 64-bit no-op (`u64` vs
  64-bit `usize`), and the happy-eyeballs delay already validated
  NaN/Inf/negatives with a bounded clamp.

## Test

Ten new regression tests across the domain files
(`test_bug361_socket_integer_bounds`,
`test_bug361_getaddrinfo_getnameinfo_bounds`, `test_bug361_connect_port_bounds`,
`test_bug361_create_server_bounds`, `test_bug361_datagram_endpoint_port_bounds`,
`test_bug361_add_child_handler_pid_bounds`, `test_bug361_add_hook_bounds`,
`test_bug361_path_watcher_mask_bounds`, `test_bug361_watcher_fd_bounds`,
`test_bug361_getsockopt_bounds`).

**Bite verification**: with all twelve touched source files reverted to the
pre-fix state under ReleaseFast, all ten tests fail with the report's
behaviours — silent truncations ("DID NOT RAISE": truncated ports connect to
garbage ports, out-of-range u32 masks truncate to 0, huge fds become garbage
fd numbers), wrong-exception failures (truncated port → ECONNREFUSED
instead of `ValueError`, truncated pid → `OSError` from a random
`pidfd_open`, invalid hook type → `SystemError`), and the guard-free paths
never raising. Passes on 3.13/3.13t/3.14/3.14t in ReleaseFast after the fix.
