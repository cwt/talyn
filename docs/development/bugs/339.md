# BUG-339 — Self-assignment `py_xdecref` before `py_newref` on `cancel_msg_py_object` causes use-after-free on Task/Future cancellation

- **Status**: ✅ Fixed (2026-10-18) — `future_fast_cancel`, `fast_task_cancel`, and `failed_execution` now increment the new reference (`py_newref`) before decrementing the old reference (`py_xdecref`), matching CPython `Py_XSETREF` semantics
- **Severity**: 🔴 Critical — deterministic use-after-free when a `Task` cancelled with a dynamically allocated message (`refcount == 1`) completes cancellation in `set_result`
- **Category**: Use-After-Free (UAF)
- **Files**:
  - `src/future/python/cancel.zig:14-18`
  - `src/task/callbacks.zig:199, 424-426`
  - `src/task/cancel.zig:40-43`
- **Related**: [Lesson 41](../lessons/05-python-c-api-correctness.md)

## Overview & Root Cause

In `src/future/python/cancel.zig:14-18`, `future_fast_cancel` replaces `instance.cancel_msg_py_object` by decrefing the old pointer **before** increfing the incoming `pyobj`:

```zig
python_c.py_xdecref(instance.cancel_msg_py_object);
if (pyobj) |value| {
    instance.cancel_msg_py_object = python_c.py_newref(value);
} else {
    instance.cancel_msg_py_object = null;
}
```

In `src/task/callbacks.zig:199`, `set_result` calls `future_fast_cancel` passing `task.fut.cancel_msg_py_object` as `pyobj` on the exact same `task.fut` instance:

```zig
const cancelled = try Future.Python.Cancel.future_fast_cancel(
    &task.fut, future_data, task.fut.cancel_msg_py_object
);
```

Because `instance` is `&task.fut` and `pyobj` is `task.fut.cancel_msg_py_object`, `instance.cancel_msg_py_object` and `pyobj` are identical pointers. When the caller of `task.cancel(msg)` did not retain an external reference to `msg` (so `msg` has `ob_refcnt == 1`), `python_c.py_xdecref(instance.cancel_msg_py_object)` drops `ob_refcnt` to `0` and deallocates `msg`. Immediately afterward, `python_c.py_newref(value)` increments `ob_refcnt` on the **already-freed** `PyObject`.

The same unsafe `py_xdecref`-before-`py_newref` pattern also exists in:
- `src/task/cancel.zig:40-43` (`fast_task_cancel`):
  ```zig
  python_c.py_xdecref(instance.fut.cancel_msg_py_object);
  if (msg) |value| {
      instance.fut.cancel_msg_py_object = python_c.py_newref(value);
  }
  ```
- `src/task/callbacks.zig:424-426` (`failed_execution`):
  ```zig
  if (python_c.PyObject_GetItem(args, zero_index)) |item| {
      python_c.py_xdecref(task.fut.cancel_msg_py_object);
      task.fut.cancel_msg_py_object = python_c.py_newref(item);
  }
  ```

## Trigger Scenario

1. A task is cancelled with a temporary string: `task.cancel(f"timeout after {n}s")`.
2. `fast_task_cancel` stores `py_newref(msg)` in `task.fut.cancel_msg_py_object`; once `task.cancel(...)` returns, `ob_refcnt` of that string is `1`.
3. When the coroutine finishes or yields and `set_result` runs (`src/task/callbacks.zig:199`), `future_fast_cancel(&task.fut, future_data, task.fut.cancel_msg_py_object)` frees `cancel_msg_py_object` via `py_xdecref` and then calls `py_newref` on the freed object.

## Proposed Remediation

Always `py_newref` the new value **before** calling `py_xdecref` on the old field (the standard CPython `Py_XSETREF` idiom):

```zig
const new_msg = if (pyobj) |value| python_c.py_newref(value) else null;
python_c.py_xdecref(instance.cancel_msg_py_object);
instance.cancel_msg_py_object = new_msg;
```

Apply the same `Py_XSETREF` order in `src/future/python/cancel.zig:14-18`, `src/task/cancel.zig:40-43`, and `src/task/callbacks.zig:424-426`.
