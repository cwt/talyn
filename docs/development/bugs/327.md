# BUG-327 — create_server sock-path error unwind double-decrefs shared references

- **Status**: 🟢 Fixed (2026-09-07; discovered by the BUG-318 regression test, grouped in the same commit)
- **Severity**: 🔴 High — Double-decref on every error path after the heap copy: refcount underflow, premature `PyObject_GC_Del`, abort
- **Files**:
  - `src/loop/python/io/server/create_server.zig` (`z_loop_create_server`: stack `creation_data` errdefer at `:95` vs heap `creation_data_ptr` errdefer at `:123`)
- **Lessons**: [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md), [Python C-API Correctness](../lessons/05-python-c-api-correctness.md)
- **Description**:
  `z_loop_create_server` builds a stack `ServerCreationData`, parses kwargs into it (`parse_vector_call_kwargs` takes owned references), stores owned `loop`/`future`/`protocol_factory` references, then heap-copies the struct for dispatch:
  ```zig
  var creation_data = ServerCreationData{};
  errdefer python_c.deinitialize_object_fields(&creation_data, &.{});   // (A) stack
  ... parse kwargs + py_newref loop/future/factory ...
  const creation_data_ptr = try allocator.create(ServerCreationData);
  creation_data_ptr.* = creation_data;                                   // shared pointers, no new refs
  errdefer creation_data_ptr.deinit();                                   // (B) heap
  ```
  On any error after the copy (e.g. the BUG-318 malformed-address rejection, an invalid `fileno()`, a failed `getsockname()` call) both errdefers fire (LIFO: B then A) and each decrefs the SAME references → refcount underflow → the objects are freed while the caller still holds them. Observed as `Fatal Python error: Aborted` inside `PyObject_GC_Del` (glibc free abort) when the transport/future objects were subsequently deallocated.
- **Root Cause**: Two owners, one reference count: the heap copy duplicates the pointers without acquiring references, while both structs carry cleanup that decrefs.
- **Trigger Scenario**: Any error return in `z_loop_create_server` after the heap copy — first exercised by the BUG-318 sock-path test (`create_server(sock=...)` with a malformed `getsockname` host).
- **Proposed Remediation**: Transfer ownership to the heap copy at the copy site: `creation_data = .{};` (stack struct emptied — its errdefer becomes a no-op), and read the sock from `creation_data_ptr.py_sock` below. On success the stack deinitialize is likewise a no-op, leaving the dispatched heap copy as the single owner.

## Fix (Applied — 2026-09-07)

- `z_loop_create_server`: after the heap copy, the stack struct is reset to `.{}` (ownership transfer) and the sock branch reads `creation_data_ptr.py_sock`. Verified: the stack errdefer can no longer double-release; the dispatched heap copy remains the single owner across success and error paths.
- Covered by the BUG-318 regression test (`test_create_server_sock_malformed_ipv4_rejected`), whose first run reproduced the abort on the unfixed unwind.

## Validation (2026-09-07)

Discovered during the BUG-307..325 fix pass: the new BUG-318 sock-path test was the first code ever to exercise a `create_server(sock=...)` error return, surfacing the abort. The success path's early kwargs release on the heap copy (`:232`, sock branch only — kwargs ignored for pre-existing bound sockets) is pre-existing, non-crashing behavior left unchanged.
