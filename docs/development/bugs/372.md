# BUG-372 — `KeyboardInterrupt` and `SystemExit` raised inside a `Task` are swallowed and double-set on `task.fut.exception` (plus `exc` reference leak in `wakeup_task`)

- **Status**: ✅ Fixed
- **Severity**: 🔴 High — raising `SystemExit` (`sys.exit()`) or `KeyboardInterrupt` inside an `asyncio.Task` fails to stop the event loop, overwrites `task.fut` exception state twice, and leaks exception references
- **Category**: Logic Bug & Reference Leak
- **Files**:
  - `src/task/callbacks.zig:447-467, 581-596, 660-673, 686-707`
- **Related**: [BUG-336](336.md) (noted secondary symptom: "`sys.exit(2)` inside `asyncio.run` under Talyn additionally raises `RuntimeError: Event loop stopped before Future completed`")

## Overview & Root Cause

In `src/task/callbacks.zig:447-467`, when a coroutine raises an exception other than `StopIteration` or `CancelledError`, `failed_execution` sets the exception on `task.fut` and checks whether it is `KeyboardInterrupt` or `SystemExit`:

```zig
const future_data = utils.get_data_ptr(Future, &task.fut);
try Future.Python.Result.future_fast_set_exception(&task.fut, future_data, exception);

inline for (.{ python_c.PyExc_KeyboardInterrupt, python_c.PyExc_SystemExit }) | critical_exc| {
    switch (python_c.PyObject_IsInstance(exception, critical_exc)) {
        1 => {
            python_c.PyErr_SetRaisedException(python_c.py_newref(exception));
            return error.PythonError;
        },
        ...
    }
}
```

However, look at what all three callers of `_execute_task_send` / `_execute_task_throw` (`execute_task_send` at lines 581–596, `execute_task_throw` at lines 660–673, and `wakeup_task` at lines 686–707) do when `_execute_task_send` / `_execute_task_throw` returns `error.PythonError`:

```zig
_execute_task_send(task, result) catch |err| {
    utils.handle_zig_function_error(err, {});
    const exc = python_c.PyErr_GetRaisedException() orelse return;
    defer python_c.py_decref(exc);
    const future_data = utils.get_data_ptr(Future, &task.fut);
    Future.Python.Result.future_fast_set_exception(&task.fut, future_data, exc) catch {};
    return;
};
```

And in `wakeup_task` (lines 686–707):

```zig
_execute_task_throw(task, exc_value) catch |err| {
    utils.handle_zig_function_error(err, {});
    const exc = python_c.PyErr_GetRaisedException() orelse return;
    const future_data = utils.get_data_ptr(Future, &task.fut);
    Future.Python.Result.future_fast_set_exception(&task.fut, future_data, exc) catch {};
    return;
};
```

This causes three bugs:

1. **`KeyboardInterrupt` and `SystemExit` are swallowed**:
   `failed_execution` deliberately re-sets `KeyboardInterrupt` / `SystemExit` on the CPython thread state and returns `error.PythonError` so that `CallbackManager` / `Runner.start` will abort the loop tick and propagate `SystemExit` / `KeyboardInterrupt` out of `loop.run_forever()`.
   Instead, the `catch |err|` block in `execute_task_send`, `execute_task_throw`, and `wakeup_task` calls `PyErr_GetRaisedException()` — which **clears** `SystemExit`/`KeyboardInterrupt` from the CPython thread state! — and returns `void` (normal completion) to `CallbackManager`! Thus `Runner.start` never sees `error.PythonError` and `loop.run_forever()` never exits on `KeyboardInterrupt` or `SystemExit`!

2. **Double `future_fast_set_exception` on `task.fut` (reference leak)**:
   In `failed_execution` (line 449), `future_fast_set_exception` already set `task.fut.data.result = py_newref(exception)` and `task.fut.data.status = .finished`.
   Note that `Future.Python.Result.future_fast_set_exception` (`src/future/python/result.zig:87-102`) does **not** check `if (self.status != .pending)` and does **not** decref an existing `self.result` before overwriting `self.result = python_c.py_newref(exception)`!
   So when the `catch |err|` block in `execute_task_send` / `execute_task_throw` / `wakeup_task` calls `future_fast_set_exception(&task.fut, future_data, exc)` a **second** time, it overwrites `future_data.result` without decrefing the first reference and dispatches `task.fut`'s done callbacks a second time!

3. **`exc` reference leak in both `catch` blocks of `wakeup_task` (`src/task/callbacks.zig:688-691, 701-704`)**:
   Unlike `execute_task_send` and `execute_task_throw` (which have `defer python_c.py_decref(exc);`), both `catch` blocks in `wakeup_task` omit `defer python_c.py_decref(exc);`, leaking the reference returned by `PyErr_GetRaisedException()`.

## Trigger Scenario

1. Run a task that calls `sys.exit(2)` or `raise KeyboardInterrupt` while `loop.run_forever()` is running -> `execute_task_send` catches `error.PythonError`, clears `SystemExit`/`KeyboardInterrupt` via `PyErr_GetRaisedException()`, leaks 1 reference to the exception via double `future_fast_set_exception`, and returns `void`.
2. In `Future.Python.Result.future_fast_set_exception` (`src/future/python/result.zig:87-102`), calling `future_fast_set_exception` on an already-finished `Future` overwrites `self.result` without raising `InvalidStateError` or decrefing the previous `self.result`.

## Proposed Remediation

1. In `execute_task_send`, `execute_task_throw`, and `wakeup_task`, if `PyErr_ExceptionMatches(python_c.PyExc_KeyboardInterrupt) != 0` or `PyErr_ExceptionMatches(python_c.PyExc_SystemExit) != 0` (or if `future_data.status != .pending`, meaning `failed_execution` already set the exception on `task.fut`), do **not** clear the exception or call `future_fast_set_exception` again — propagate `return error.PythonError;` directly so `Runner.start` terminates cleanly with the active `SystemExit` / `KeyboardInterrupt`.
2. Add `defer python_c.py_decref(exc);` in both `catch` blocks of `wakeup_task` (`src/task/callbacks.zig:688, 701`).
3. In `future_fast_set_exception` (`src/future/python/result.zig:87-102`), check `if (self.status != .pending)` and raise `InvalidStateError` (matching `future_fast_set_result` at lines 78–81).


## Resolution (2026-10-18)

The core swallow-path was live in the evolved code (execute_task_send /
execute_task_throw / wakeup_task catch blocks fetching the thread state
with `PyErr_GetRaisedException`) — note the two executor hooks already
had their `defer py_decref(exc)` from BUG-273; only wakeup_task's two
catch blocks lacked their own. Fixes:

1. **Fatal-propagation gates (fixed)**: each of the three catch blocks
   checks the active exception first
   (`PyErr_Occurred` + `PyErr_GivenExceptionMatches` against
   `KeyboardInterrupt` / `SystemExit`) and returns `error.PythonError`
   WITHOUT touching the thread state — `failed_execution`'s
   re-installed fatal now reaches `Runner.start` and the loop stops,
   propagating out of `rus_until_complete`/`talyn.run`.

2. **`wakeup_task` exc decrefs (fixed)**: `defer
   python_c.py_decref(exc)` added to both catch blocks.

3. **`future_fast_set_exception` re-set hardening (fixed)**: the helper
   now rejects non-pending or released futures with `InvalidStateError` (CPython
   parity) instead of overwriting — the pre-fix re-set leaked the
   previous payload reference (`py_newref` overwriting without
   decref) and re-entered the done-callback machinery on an
   already-finished future. For intra-pending re-targets the new reference is
   taken before releasing the previous payload reference (`py_xdecref` / BUG-339
   discipline), and `set_future_exception` / `future_fast_set_result` guard
   against already-cancelled or released futures.
