# BUG-346 — `FDWatcher` (`add_reader`/`add_writer`) leaks `handle` references on cancel/error and leaves raised Python exceptions pending on thread state

- **Status**: 🟢 Fixed
- **Severity**: 🔴 Critical — leaks `PythonHandleObject` (and its captured callback, args, contextvars, and loop references) on watcher removal/cancellation or callback error, and corrupts the CPython thread exception state when a reader/writer callback raises
- **Category**: Reference Leak & CPython Exception State Corruption
- **Files**:
  - `src/loop/python/io/watchers.zig:45-100, 112-133`
  - `src/handle.zig:45-93`
- **Related**: [BUG-315](315.md), [Lesson 41](../lessons/05-python-c-api-correctness.md), [Lesson 47](../lessons/05-python-c-api-correctness.md)

## Overview & Root Cause

In `src/loop/python/io/watchers.zig`, an `FDWatcher` holds 1 baseline reference to `handle` (created by `Handle.fast_new_handle` at line 191 and released in `loop_watchers_cleanup_callback` at line 139 when the `io_uring` `PollFd` task is cleaned up).

When `PollFd` fires in `loop_watchers_callback` (lines 112–133), it dispatches `loop_watchers_soon_callback` to the `Soon` queue and calls `python_c.py_incref(@ptrCast(handle))` at line 132 so that `Handle.callback_for_python_generic_callbacks` (called inside `loop_watchers_soon_callback` at line 60) can consume that extra reference:

```zig
try Loop.Scheduling.Soon.dispatch(loop, &[_]CallbackManager.Callback{
    .{
        .func = &loop_watchers_soon_callback,
        .cleanup = &loop_watchers_cleanup_callback,
        .data = .{
            .user_data = ptr,
            .exception_context = .{
                .callback_ptr = handle.py_callback.?,
                .module_ptr = @ptrCast(handle),
                .exc_message = "Exception in callback",
            },
        },
    },
});
python_c.py_incref(@ptrCast(handle));
```

There are four bugs in this flow:

1. **Reference leak when `data.cancelled()` or `fd < 0` in `loop_watchers_soon_callback` (lines 50–52)**:
   ```zig
   if (data.cancelled() or fd < 0) {
       return;
   }
   ```
   If `remove_reader`/`remove_writer` is called after `loop_watchers_callback` has already queued `loop_watchers_soon_callback` into the `Soon` queue (setting `watcher.read_fd = -1` / `watcher.write_fd = -1`), `loop_watchers_soon_callback` sees `fd < 0` and returns early **without** calling `python_c.py_decref(@ptrCast(handle))` for the extra ref added at line 132! And if the `Soon` queue entry is cancelled during loop teardown (`data.cancelled() == true`), `loop_watchers_cleanup_callback` only decrefs `handle` once (freeing `watcher`), also leaking the extra ref from line 132.

2. **Reference leak AND CPython exception state corruption when the Python callback raises an exception (lines 60–63)**:
   ```zig
   Handle.callback_for_python_generic_callbacks(&handle_data) catch |err| {
       utils.handle_zig_function_error(err, {});
       return;
   };
   ```
   Inside `Handle.callback_for_python_generic_callbacks` (`src/handle.zig:76-92`), `defer if (success) python_c.py_decref(@ptrCast(handle));` only decrefs `handle` when `success == true`. When the Python callback raises an exception, `callback_for_python_generic_callbacks` returns `error.PythonError` with `success = false` (expecting `CallbackManager` to invoke `cleanup_for_python_generic_callbacks`, which decrefs `handle`).
   However, `loop_watchers_soon_callback` **catches** the error, calls `utils.handle_zig_function_error(err, {})`, and returns `void` (success) to `CallbackManager`!
   As a result:
   - `handle` is **never decref'd** for the extra reference from line 132 (leaking `handle`).
   - `CallbackManager`'s exception handler is **bypassed**, so `loop.call_exception_handler` is never called!
   - Worse still, the raised Python exception remains **active on the CPython thread state** (`PyErr_Occurred() != null`) while the event loop continues executing subsequent callbacks, causing unrelated C-API calls on the same tick to fail spuriously with the leftover exception!

3. **Mandate #5 initialization order violation at line 132**:
   `python_c.py_incref(@ptrCast(handle))` is called at line 132 **after** `Soon.dispatch` (line 118) has already published the callback into `ready_tasks_queues`.

## Trigger Scenario

1. Register a reader with `loop.add_reader(fd, cb)`.
2. Trigger readability on `fd` and call `loop.remove_reader(fd)` in an earlier callback on the same tick -> `loop_watchers_soon_callback` sees `fd < 0` and leaks `handle`.
3. Alternatively, have `cb` raise `ValueError("boom")` -> `loop_watchers_soon_callback` catches `error.PythonError`, leaks `handle`, skips `loop.call_exception_handler`, and leaves `ValueError` set on the Python thread state.

## Proposed Remediation

1. Increment `handle` **before** calling `Soon.dispatch` (with `errdefer python_c.py_decref(@ptrCast(handle))`).
2. Use a separate `cleanup` function for `loop_watchers_soon_callback` (that decrefs `handle` without destroying `watcher`, since `watcher` is owned by the `PollFd` task's `loop_watchers_cleanup_callback`).
3. In `loop_watchers_soon_callback`, if `data.cancelled() or fd < 0`, call `python_c.py_decref(@ptrCast(handle))` before returning; and propagate errors from `Handle.callback_for_python_generic_callbacks(&handle_data)` via `try` so `CallbackManager` routes the exception to `loop.call_exception_handler` and runs the cleanup function to decref `handle`.

## Applied Fix

1. In `loop_watchers_callback`, called `python_c.py_incref(@ptrCast(handle))` with `errdefer python_c.py_decref(@ptrCast(handle))` before `Soon.dispatch` to guarantee proper initialization order (Mandate #5).
2. In `loop_watcher_python_wrapper_cleanup` and early return when `data.cancelled() or fd < 0`, properly decreffed `watcher.handle` for the Soon queue invocation before invoking `loop_watchers_cleanup_callback`.
3. In `loop_watcher_python_wrapper_callback`, when `callback_for_python_generic_callbacks` raises:
   - Decref the Soon reference to `handle` (`python_c.py_decref(@ptrCast(watcher.handle))`).
   - Extract and clear the raised exception via `PyErr_GetRaisedException()`.
   - Propagate fatal exceptions (`KeyboardInterrupt`, `SystemExit`) while packaging normal callback exceptions into context dicts dispatched to `loop.call_exception_handler`.
   - Clear `blocking_task_id = 0` before any Python call (TALYN-017 / BUG-336).
   - Re-arm the watcher for subsequent events.
4. Added unit and regression tests in `tests/loop/test_loop_watchers.py` verifying exception dispatch to custom handler, proper re-arming on subsequent events, and zero handle leaks across multiple error cycles.
