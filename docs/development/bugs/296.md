# BUG-296 — `future_cancel` leaks the positional `msg` when both forms are supplied

- **Status**: 🔵 Open (2026-08-23)
- **Severity**: 🟢 Low — Refcount leak on malformed input
- **Files**:
  - `src/future/python/cancel.zig:34-36` (`cancel_msg_py_object = py_newref(args.?[0])` — owned)
  - `src/future/python/cancel.zig:39-47` (`parse_vector_call_kwargs(..., &.{&cancel_msg_py_object})`)
  - `src/python_c.zig:546-550` (commit loop does `py_obj.* = py_newref(v)` unconditionally — no release of prior value)
- **Lessons**: [Memory & Reference Counting §Lesson 37](../lessons/01-memory-and-reference-counting.md), [Python C API Correctness](../lessons/05-python-c-api-correctness.md)
- **Description**: All exits of `future_cancel` balance correctly (BUG-22 fix intact) except the both-forms case: the commit overwrites the already-owned positional reference. CPython raises TypeError for duplicate cancellation messages; talyn silently prefers the kwarg.
- **Trigger**: `fut.cancel("x", msg="y")`.
- **Consequences**: One leaked string object per offending call.
- **Fix (Proposed)**: Release the prior owned ref before invoking `parse_vector_call_kwargs`, or reject the duplicate form.
