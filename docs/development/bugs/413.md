# BUG-413 — dangling signal callback after a failed `link()`

- **Status**: 🟢 Fixed (2026-11-01)
- **Severity**: 🔴 Critical — use-after-free / double-decref on the next signal delivery
- **Category**: Unix Signals / Error Paths / Refcounting
- **Files**:
  - `src/loop/unix_signals.zig:156-192` — `link()`
  - `src/loop/python/unix_signals.zig:77-83` — caller errdefer frees the handle
  - `src/handle.zig:37-118` — callback/dealloc on a freed handle
- **Related**: [BUG-156](156.md) (hook handle cancel), [BUG-382](382.md) (UnixSignals cleanup)

## Overview

```zig
var prev_callback = self.callbacks.replace(@intCast(sig_idx), callback);
if (prev_callback) |*v| {
    v.data.set_cancelled(true);
    try Loop.Scheduling.Soon.dispatch_nonthreadsafe(self.loop, v);  // can fail
} else {
    try self.loop.reserve_slots(1);
}
```

`replace` has already committed the new callback to the BTree. If the dispatch returns an error, `link` propagates it; `z_loop_add_signal_handler` has `errdefer python_c.py_decref(py_handle)`, which frees the handle because it holds the only reference. The BTree entry is not rolled back. When the signal is delivered, `signal_handler` takes the callback from the BTree, increfs the dangling handle, and dispatches `callback_for_python_generic_callbacks`, which touches freed state and decrefs the object again.

Additionally, a failure after `sigprocmask(SIG_BLOCK)` / `signal(dummy_signal_handler)` can leave the signal blocked with the dummy handler installed; that is a separate robustness issue from the dangling BTree entry.

## Trigger Scenario and Evidence (confirmed 2026-11-01)

Environment: Apple `container` 1.6.1, Fedora 44 aarch64, Zig 0.16.0, ReleaseFast, Python 3.13.16.

Harness:
- `Loop(1)` makes the ready ring capacity 1.
- `loop.call_soon(lambda: None)` fills it.
- Allocation fault injection fails the grow performed while dispatching the replaced SIGINT callback.
- `add_signal_handler(SIGINT, cb)` raises `MemoryError`.
- A `call_later` sends SIGINT; the loop then dispatches the freed handle.

Repro: `h3_signal_link_uaf.py 0` (`n=0` and `n=1` both crash).

## Proposed Remediation

Make `link()` transactional:

- If dispatching the replaced callback fails, restore the previous callback entry or delete the new one before returning; do not leave the BTree pointing at a handle the caller will free.
- Alternatively, take an extra reference for the BTree entry and release it on unlink, so a caller error cannot free a stored callback.
- On any setup error after `sigprocmask`/`signal`, restore the previous handler/mask (block/unblock ordering) so the signal is not left swallowed.

Add a regression test with a capacity-1 ring plus allocation failure that then raises SIGINT and asserts no crash.

## Resolution (2026-11-01)

On dispatch failure, `link()` now un-cancels the replaced entry, restores it with `callbacks.replace()`, and returns the error. The caller's `errdefer` still frees the new handle, but the BTree no longer references it, so the next signal delivery cannot use freed memory.

Verification: fault-injection `h3_signal_link_uaf.py 0` survives, reports `MemoryError` from `add_signal_handler`, and later delivers zero callbacks without crashing; `tests/loop/test_loop_unix_signals.py` and `tests/loop/test_loop_watchers.py` pass.
