# BUG-231 — `timeout_from_secs` produces wrapped-around values for negative input

- **Status**: ✅ Fixed
- **Severity**: 🟡 Medium — Invalid syscall arguments / kernel -EINVAL
- **File**: `src/loop/dns/resolv.zig:38-45` (timeout_from_secs)
- **Lessons**: [io_uring §Lesson 185 — Kernel -EINVAL from unnormalized nanoseconds](../lessons/04-io-uring-and-kernel.md), [Security §Lesson 34 — Parser Strictness](../lessons/09-security-and-input-validation.md)
- **Description**: `timeout_from_secs` converts an `f64` seconds value to a `DnsTimeout` struct (`sec: u64, nsec: u32`). When given a negative input (e.g., `-0.5`), the function computes:
  - `sec = -1` (i64)
  - `frac = -0.5` (f64, since `-0.5 - (-1) = 0.5`... wait, actually: `@floor(-0.5) = -1.0`, so `frac = -0.5 - (-1.0) = 0.5`)
  - But for `-1.5`: `sec = -2`, `frac = -1.5 - (-2.0) = 0.5`, `nsec = 500_000_000`

  The real issue is that `@intCast(sec)` where `sec: i64 = -1` casts to `u64 = 18446744073709551615`, and `@intCast(nsec)` where the result could be negative also wraps. While most callers validate the input, `timeout_from_secs` itself has no guard.

  Additionally, the `dns_timeout` kwarg parsing in multiple locations (`create_connection.zig`, `create_server.zig`, `create_endpoint.zig`) checks `timeout_val == -1.0` but does not check for negative values generally.

- **Trigger**: Any caller passing a negative `dns_timeout` float value from Python.
- **Consequences**: `u64` overflow → enormous timeout value → io_uring timeout SQE with invalid timespec → kernel rejects with `-EINVAL` → DNS query hangs or fails silently.
- **Fix**: Add early validation: `if (timeout_secs < 0.0) return error.InvalidTimeout;` at the top of `timeout_from_secs`. Also add guards in all caller sites.
