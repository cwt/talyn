# BUG-446 — `handle_talyn_future_object` unwraps `future.py_loop.?` without a guard

- **Status**: 🟡 Open
- **Severity**: 🟡 Medium — unwrap panic / UB inside the task-stepping path (Mandate #4 family)
- **Category**: Null handling / GC safety
- **Files**: `src/task/callbacks.zig:392`, `src/future/python/constructors.zig:40-44`
- **Related**: [BUG-440](440.md) (same object state via `get_loop()`), [BUG-369](369.md) (the released fences), [BUG-213](213.md) (unchecked `.?` class)

## Description

```zig
inline fn handle_talyn_future_object(task: *Task.PythonTaskObject, future: *Future.Python.FutureObject, loop_data: *Loop) !void {
    ...
    const py_loop: *Loop.Python.LoopObject = @ptrCast(future.py_loop.?);   // :392 — no released/null guard
    if (loop_data != utils.get_data_ptr(Loop, py_loop)) { ... }            // intended error path
```

`future.py_loop` is only set by `future_init_configuration` (loop-bound futures). `z_future_new`
never calls it, so a `Future.__new__(Future)` object carries `py_loop == null` and `released == true`
(zeroed by `initialize_object_fields`). Awaiting such a future from a task dispatches here and
unwraps the null optional directly — a panic in Debug/ReleaseSafe and undefined behavior in
ReleaseFast — instead of reaching the "not in the same loop" error path at `:393-396`.

## Trigger

`await Future.__new__(Future)` from inside a task (or any `__new__`-only / `tp_clear`ed Future whose
`py_loop` was never bound).

## Consequences

Panic or undefined behavior in the task-stepping IO path rather than a Python exception
(Mandate #1/#4 family).

## Fix

Guard like the fences BUG-369 added elsewhere (e.g. `future_fast_cancel`, `cancel.zig:15`): if
`future.py_loop == null` (or `released`), raise the intended error
("Task got Future attached to a different loop"-class) instead of unwrapping.
