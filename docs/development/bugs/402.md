# BUG-402 — `connection_lost(None)` on an I/O error (notification ordering)

- **Status**: 🟢 Fixed (2026-11-01)
- **Severity**: 🟠 High — asyncio protocol receives the wrong exception on read errors; exception reference is stranded
- **Category**: Stream Transport Lifecycle / Error Semantics
- **Files**:
  - `src/transports/stream/lifecycle.zig:53-77` — `close_transports`
  - `src/transports/read_transport.zig:182-188` — read error sets `closed` before invoking the callback
  - `src/transports/write_transport.zig:104-122` — `close()` can synchronously call `maybe_close_fd`
- **Related**: [BUG-378](378.md) (at-most-once `connection_lost` design)

## Overview

`close_transports` is entered with the real failure exception, but stores it only after both transports are closed:

```zig
read_transport.close() ...;
write_transport.close() ...;          // may synchronously call maybe_close_fd()
transport.is_reading = false;
transport.is_closing = true;
...
if (transport.pending_lost_exc == null)
    transport.pending_lost_exc = py_newref(exception);
maybe_close_fd(transport);
```

On the read-error path, `read_transport.read_operation_completed` sets `read_transport.closed = true` before calling the stream callback. If the write side has no in-flight write and no buffered data, `write_transport.close()` sets `write_transport.closed = true` and calls `maybe_close_fd()`. Both sides are now closed, so `maybe_close_fd` marks the transport closed, tears down the fd, and calls `schedule_connection_lost_once()` while `pending_lost_exc` is still null. `connection_lost` therefore receives `Py_None` (or the stashed value from a previous close, never the current error). The real exception is stashed afterwards, but the once-guard is already tripped.

## Trigger Scenario

1. Establish a stream connection.
2. Make the peer reset the connection (for example `SO_LINGER(1, 0)` then abort), producing `ECONNRESET` on the read side.
3. Ensure the write side is idle (no buffered writes).
4. The client protocol's `connection_lost(exc)` receives `None` instead of an `OSError`.

## Evidence (confirmed 2026-11-01)

Environment: Apple `container` 1.6.1, Fedora 44 aarch64, Zig 0.16.0, ReleaseFast, Python 3.13.16 and 3.13.16t.

Repro: `c5_connection_lost_exc.py` (server sets `SO_LINGER(1,0)` and aborts).

```text
server on 38731
connection_lost args: ['None']
RESULT: FAIL connection_lost(None) on an I/O error (expected an OSError)
```

## Proposed Remediation

Stash the exception and `detach_server` **before** either `close()` can reach `maybe_close_fd`:

```zig
if (transport.pending_lost_exc == null)
    transport.pending_lost_exc = py_newref(exception);
detach_server(transport);
read_transport.close() ...;
write_transport.close() ...;
...
maybe_close_fd(transport);
```

Add a regression test that forces an RST and asserts `connection_lost` receives an `OSError` exactly once, and that the captured exception object is not retained after teardown.

## Resolution (2026-11-01)

`close_transports` now stores `pending_lost_exc` before calling `read_transport.close()`/`write_transport.close()`. Those calls can synchronously reach `maybe_close_fd()` and fire `connection_lost()`; the notify-once path now always observes the exception that triggered the shutdown instead of `None`.

Verification: `tests/test_review_regressions.py::test_connection_lost_receives_error_on_reset` (RST from a `SO_LINGER`-0 peer) observes an `OSError`; external repro `c5_connection_lost_exc.py` passes on Zig 0.16.0 and 0.17.0, GIL and free-threaded.
