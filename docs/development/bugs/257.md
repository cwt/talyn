# BUG-257 — `parseIp4` octet overflow (u16 wraps / Debug panic)

- **Status**: ✅ Fixed
- **Severity**: 🟠 Medium-High — Input validation / parser strictness (robustness + correctness/security)
- **Files**: `src/utils/address.zig`
- **Lessons**: [Security §Parser Strictness](../lessons/09-security-and-input-validation.md)
- **Description**: `parseIp4` (lines 102-132) accumulates each octet into `var val: u16 = 0;` via `val = val * 10 + (host[i] - '0');` (line 122), then only enforces `if (val > 255) return error.InvalidIPAddressFormat;` (line 125) **after** the accumulation loop. An over-long octet overflows `u16`: in a Debug/ReleaseSafe build Zig traps the integer overflow and **panics** (crash / DoS on malformed input); in ReleaseFast it wraps, so `4294967296 mod 65536 == 0` passes the `val > 255` check and is silently accepted as octet `0` (i.e. `1.2.3.4294967296` parses as `1.2.3.0`). This is the same parser-strictness class as BUG-69 (leading zeros) and the documented mandate to reject malformed input. Reachable from `Address.fromPyAddr` / `resolveIp` with user- or network-controlled host strings.
- **Trigger**: A malformed IPv4 literal whose octet exceeds 65535 passed to the address parser.
- **Consequences**: Debug build: crash on malformed input (denial of service). ReleaseFast: silent connection to the **wrong host** (spoofing / correctness / security).
- **Resolution**: Reject inside the loop — e.g. `if (val > 25 or (val == 25 and digit > 5)) return error.InvalidIPAddressFormat;` before multiplying — or accumulate into `u32`/`u64` and reject `val > 255`.
- **Verification**: Unit test asserting `parseIp4("1.2.3.4294967296")` returns `InvalidIPAddressFormat` in all build modes (no panic, no wrong parse); add a ReleaseFast-mode assertion for the wrapped-value case.
