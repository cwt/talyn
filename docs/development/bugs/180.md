# BUG-180 — CancelledError(None) vs standard CancelledError() argument mismatch on future cancellation

- **Status**: 🔴 Open
- **Severity**: 🟠 High — CPython asyncio protocol compatibility defect
- **Files**: `src/future/python/constructors.zig:18`, `src/future/python/result.zig:15-20`, `src/future/python/cancel.zig:67-77`
- **Lessons**: [Python C API §Lesson 21](../lessons/021-python-c-api.md)
- **Description**: In `src/future/python/constructors.zig`, `self.cancel_msg_py_object` is initialized to `Py_None`. In `raise_cancel_exception` (`result.zig:15-20`), the check `if (self.cancel_msg_py_object)` is always non-null, executing `PyErr_SetObject(cancelled_error_exc, Py_None)` on standard cancellation. This raises `CancelledError(None)` whose `args` is `(None,)`, rather than standard `CancelledError()` whose `args` is `()`. Similarly, `future_make_cancelled_error` in `cancel.zig` passes `Py_None` directly to `PyObject_CallFunctionObjArgs`.
- **Trigger**: Any normal future/task cancellation without an explicit string message (`fut.cancel()`).
- **Consequences**: Breaks Python code that checks `exc.args == ()` or formatting cancelled error exceptions.
- **Fix**: Check `if (self.cancel_msg_py_object != null and !python_c.is_none(self.cancel_msg_py_object.?))` before raising with argument.
