# BUG-155 — `TimerHandle` missing GC payload initialization and `Py_TPFLAGS_HAVE_GC` flag

- **Status**: 🔴 Open
- **Severity**: 🟠 High — garbage collector blindness / memory leak
- **Files**: `src/timer_handle.zig:17-42, 107`, `src/loop/python/scheduling.zig:233`
- **Lessons**: [Memory Safety §Lesson 01](../lessons/01-memory-safety-and-pointers.md), [Event Loop §Lesson 03](../lessons/03-event-loop-lifecycle.md)
- **Description**: In `src/timer_handle.zig`, `fast_new_timer_handle` initializes `PythonTimerHandleObject` without setting `instance.handle.python_payload` (unlike `fast_new_handle` in `src/handle.zig`). When `call_later` or `call_at` registers the timer callback into the loop's ring buffer with `CallbackData.init_python(py_timer_handle, &py_timer_handle.handle.python_payload)`, `python_payload.traverse` is null/garbage. Consequently, `RingBuffer.traverse` skips the timer handle during GC cycles, rendering reference cycles uncollectible. Furthermore, `thread_safe` and `blocking_task_id` are left uninitialized on the struct, and `PythonTimerHandleType.tp_flags` omits `Py_TPFLAGS_HAVE_GC` even though its base type specifies it.
- **Trigger**: Creating cyclic references involving `TimerHandle` instances (e.g., a timer callback holding a reference to the loop or an object that references the handle).
- **Consequences**: Permanent memory leaks of Python objects trapped in reference cycles across timer handles.
- **Proposed Fix**: Set `.python_payload` with `.module_ptr`, `.callback_ptr`, and `.traverse = &Handle.traverse_python_generic_callback`, explicitly set `thread_safe = false` and `blocking_task_id = 0`, and add `python_c.Py_TPFLAGS_HAVE_GC` to `PythonTimerHandleType.tp_flags`.
