# BUG-363 — `dispatch_completion_batch` calls CPython APIs with a live exception set and aborts `Runner.start` before releasing buffers or re-arming reads

- **Status**: ✅ Fixed
- **Severity**: 🔴 High — corrupts CPython exception state across batched transport completions, loses exceptions from earlier transports in the batch, and aborts `Runner.start` before `call_once` can release `parent_transport` references or re-arm reads
- **Category**: Logic Bug (CPython Exception State Corruption & Event Loop Abort)
- **Files**:
  - `src/loop/runner.zig:124-189, 390`
- **Related**: [BUG-18](018.md), [BUG-321](321.md), [Lesson 47](../lessons/05-python-c-api-correctness.md)

## Overview & Root Cause

In `src/loop/runner.zig:124-189`, `dispatch_completion_batch` iterates over `batch.slice()` and calls `protocol.data_received(py_bytes)` (for `.stream_read`) or `protocol.buffer_updated(nbytes_obj)` (for `.buffered_read`):

```zig
const ret = python_c.PyObject_CallOneArg(data_received, py_bytes);
if (ret) |r| {
    python_c.py_decref(r);
} else {
    had_error = true;
}
```

And at the end of `dispatch_completion_batch` (line 188):

```zig
if (had_error) return error.PythonError;
```

Which is called in `Runner.start` at line 390:

```zig
try dispatch_completion_batch(loop);
```

This design causes three severe bugs whenever a protocol's `data_received` or `buffer_updated` callback raises a Python exception:

1. **Calling CPython APIs with a live exception on the thread state**:
   When `PyObject_CallOneArg` returns `null`, CPython has an active exception set on the current thread state. Instead of fetching the exception and routing it to `loop.call_exception_handler` (or `connection_lost`), `dispatch_completion_batch` sets `had_error = true` and **continues the `for (batch.slice())` loop**, calling `PyBytes_FromStringAndSize`, `PyLong_FromUnsignedLongLong`, and `PyObject_CallOneArg` on all remaining records in the batch while the prior exception is still set on the thread state! Calling into Python C-API functions with an uncleared exception violates CPython's C-API contract (`SystemError` in debug builds, overwritten/chained exceptions in release builds).

2. **Aborting `Runner.start` (`loop.run_forever()`) on a protocol callback exception**:
   In `asyncio`, an unhandled exception in `protocol.data_received()` or `protocol.buffer_updated()` must be passed to `loop.call_exception_handler(...)` (or close the transport via `connection_lost(exc)`) and **must not** crash `loop.run_forever()`!
   Instead, `try dispatch_completion_batch(loop)` at line 390 returns `error.PythonError` directly out of `Runner.start`, aborting `loop.run_forever()` **before** `try call_once(loop)` (line 395) even executes!

3. **Skipping `ReadTransport.read_operation_completed` in `call_once`**:
   Because `Runner.start` aborts at line 390 before `call_once` runs:
   - `ReadTransport.read_operation_completed` (queued in `ready_tasks_queues`) does not run on that tick.
   - All healthy transports in the same batch never have their next read queued (`queue_read_operation`).
   - Buffered protocols in the same batch do not have their `protocol_buffer` (`Py_buffer`) released.

## Trigger Scenario

1. Two active TCP connections receive data in the same `io_uring` CQE batch.
2. Connection 1's `data_received` raises `ValueError("bad frame")`.
3. `dispatch_completion_batch` leaves `ValueError` set on the CPython thread state while invoking Connection 2's `data_received`, then returns `error.PythonError`, crashing `loop.run_forever()` instead of calling `loop.call_exception_handler`.

## Proposed Remediation

In `dispatch_completion_batch` (`src/loop/runner.zig:147-186`), when `PyObject_CallOneArg` returns `null`, immediately fetch the raised exception via `PyErr_GetRaisedException()` (clearing the thread state for subsequent records in the batch) and report it via `loop.call_exception_handler` (unless it is `SystemExit` or `KeyboardInterrupt`), rather than returning `error.PythonError` to abort `Runner.start`.


## Resolution (2026-10-18)

Line numbers in the report had drifted (dispatch loop now at
runner.zig ~161, the `Runner.start` call site at ~402); all three stated
defects still reproduced:

1. **Live-exception C-API calls inside the batch (fixed)**: every
   post-dispatch failure path now routes through a new
   `dispatch_protocol_callback_exception(loop_obj, message)` helper,
   which FIRST fetches the exception with `PyErr_GetRaisedException()`
   (clearing the thread state for the remaining records of the batch)
   and reports it through `loop_obj.call_exception_handler` with a
   `{message, exception}` context (same pattern as `exception_handler`
   in this file and `child_watcher.zig`'s dispatcher). The helper mirrors
   `BaseEventLoop.handle_exception`: only `SystemExit` /
   `KeyboardInterrupt` propagate (`error.PythonError` with the inner
   exception live, stopping the loop); every other failure — including
   the allocation failures of `PyBytes_FromStringAndSize` /
   `PyLong_FromUnsignedLongLong` — is swallowed so the batch and the
   loop continue.

2. **`Runner.start` abort (fixed)**: the trailing
   `if (had_error) return error.PythonError` — which aborted the
   `run_forever` loop on any protocol callback exception — is removed
   (`had_error` no longer exists; the function now only fails for
   SystemExit/KeyboardInterrupt, which *should* stop run_forever, the
   same way a callback exception in asyncio's `_run_once` does).

3. **Skipped `call_once` / read re-arm (fixed by 2)**: with the batch
   dispatch no longer aborting, the ready queue runs
   `ReadTransport.read_operation_completed` on the same tick, re-arming
   reads and releasing buffered protocole buffers as designed.
