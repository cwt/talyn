# BUG-301 — Five duplicated lifetime-critical accounting blocks in `process_dns_response`

- **Status**: 🔵 Open (2026-08-23)
- **Severity**: 🟢 Low today — Latent High blast radius
- **Files**:
  - `src/loop/dns/resolv.zig` (~:428-435 QR/OPCODE/RCODE reject, ~:447-454 TC bit, ~:464-472 qdcount != 1, ~:481-489 short question, ~:495-502 question mismatch)
- **Lessons**: [Defensive Programming](../lessons/10-defensive-programming-and-code-quality.md), [Data Structures & Algorithms §Lesson 83](../lessons/07-data-structures-and-algorithms.md)
- **Description**: Each rejection case repeats:
  ```zig
  server_data.responses_received += 1;
  if (server_data.responses_received < server_data.queries.len and !control_data.resolved) {
      try queue_next_response_read(server_data);
  } else {
      try mark_resolved_and_execute_user_callbacks(server_data);
      server_data.release();
  }
  ```
  The whole `ControlData` arena lifetime depends on each `ServerQueryData` calling `release()` exactly once and counters staying exact. Any future divergence between the copies (forgetting release, double-counting, adding a sixth case without the block) silently produces either premature arena destruction while sibling-server ops are pending (UAF) or a permanent leak of socket fd + ServerQueryData + ControlData.
- **Trigger**: Maintenance divergence; no runtime trigger today.
- **Consequences**: High-risk refactor hazard around a use-after-free class.
- **Fix (Proposed)**: Extract a single `reject_response(server_data)` helper taking the decision as input.
