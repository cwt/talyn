# BUG-415 — watchdog self-unblock spins the runner and starves foreign GIL threads (wormhole ad-block update freeze)

- **Status**: 🟢 **Fixed** (2026-11-04, rev 1238 — *after* the v0.11.3 tag cut at rev 1237; ships with the next patch release)
- **Severity**: 🔴 High — a fully-idle loop burns 100% of one core while starving every foreign Python thread; real-world effect = indefinite freeze of the final DB write in wormhole's `--update-ad-block-db`
- **Category**: Runner / io_uring blocking wait / GIL interplay with foreign threads
- **Files**: `src/loop/runner.zig` (`poll_blocking_events`), regression gate `tests/test_foreign_thread_yield.py`
- **Related**: [BUG-399](399.md), [BUG-410](410.md) (the watchdog rewrite that introduced this), [BUG-267](267.md) (persistent eventfd wake), P23 ring_blocked release/acquire audit
- **Introduced**: between v0.10.0 (rev 1173) and v0.11.x — era wheels prove it: v0.10.0 completes the wormhole flow in ~2 s; the v0.11.0/v0.11.2/v0.11.3 content freezes. `hg diff -r 1173 -r tip src/loop/runner.zig` shows exactly one functional change in the wait path: the BUG-399/BUG-410 watchdog rewrite (`submit_and_wait(1)` → arm-timeout + wait + `timeout_remove` per entry).

## Report (user's environment, 2026-11-04)

```
wormhole --update-ad-block-db ads.sqlite3 --allowlist allowlist.txt
...
wormhole.ad_blocker[...]: Writing 150014 domains to database...
^C (no progress for 90+ s)
```

The user's talyn wheel: published v0.11.3 (rev 1236 content). Wormhole's flow: 5 blocklist URLs (aiohttp/aiodns/pycares), parse/optimize in-Python, then ONE `aiosqlite.executemany` of ~150k rows (~10 MB DB) on the aiosqlite worker thread.

## Evidence trail (frozen process, v0.11.3 content)

- py-spy: MainThread at `talyn/loop.py:459` (`run_until_complete`), aiosqlite worker "active" in native sqlite code, second aiosqlite worker idle, pycares shutdown thread idle.
- DB-file growth probe: 6.68 MB by t+6 s, then **+16 KB over the next 30 s** — the write was effectively parked (~2/3 through) — the executemany runs at ~1/700 of its standalone speed (0.09 s standalone, wheel or asyncio).
- strace (12 s): main thread ~42.7k iterations (identifiable via the per-iteration `getpid` fork-guard), **2× `io_uring_enter(fd, 1, 0, 0)` per iteration** (= submit the watchdog timeout, then submit its cancellation), an intense futex exchange with the sqlite worker (GIL save/restore per iteration), `pwrite64` continuing at ~2.5k/s on the worker (the SQL itself flows whenever it can win a GIL window).
- gdb on the hung loop: MainThread parked inside `copy_cqes(..., 1)` → `io_uring_enter(0, 1, IORING_ENTER_GET_EVENTS)` — while the callbacks pushed by `call_soon_threadsafe` sat undelivered.
- Diagnostic wheel (`TALYN_SPIN_DEBUG`, temp): idle shape = `iters≈143k, cb_sum=0, wait=1, reserved=5, idle=0, check=0, readyA=B=0` — **wait=true and the blocking branch entered ~3.2k times/s without ever blocking**.

## Root cause (two failures, one freeze)

1. **Watchdog self-unblock** (the actual freeze driver). From the BUG-399/BUG-410 rewrite, every blocking entry: `ring.timeout(watchdog_user_data, 100 ms)` → `submit()` → `copy_cqes(cqes, 1)` … → *after* the wait, `ring.timeout_remove(0, watchdog_user_data, 0)` → `submit()`. The cancellation itself produces a CQE that lands in the CQE ring and is **skipped by `fetch_completed_tasks` (user_data == 0) but unblocks the NEXT `copy_cqes(, 1)` instantly**. Net: from the second blocking entry onward the ring never empties; "blocking" returns immediately; the loop cycles at full speed — 2 enters + 1 CQE consumed per iteration, `reserved_slots` and queues permanently unchanged (`reserved=5`, `cb=0`).
2. **The `reserved_slots == 0` downgrade** (pre-existing since the v0.9.x era, co-suspect of the earlier spin hypothesis): when nothing native is in flight, the wait was downgraded to a non-blocking poll — same burial for truly-idle loops, with no GIL release at all between iterations.

Both share the same failure class: **the blocking branch never actually blocks** — the GIL is hand-cycled at thousands of Hz, and any foreign thread whose work needs the GIL per step (pysqlite's per-row `Py_BEGIN/END_ALLOW_THREADS`, resolver helpers) is starved. Under plain asyncio the analogous idle wait is `epoll_wait` **with the GIL released**, which is what makes the same wormhole flow complete.

## Fix (this session)

In `poll_blocking_events`'s blocking branch:

1. **Drain first**: harvest every completed CQE non-blockingly (`copy_cqes/tasks)` before deciding to park; only when the ring is truly empty enter the blocking wait. SignalInterrupt retries with NO Python call inside the dropped-GIL window (delivery stays in the post-Restore `PyErr_CheckSignals`).
2. **Cancel after the wait, never before** (the submit that previously unblocked its own park): the watchdog `timeout_remove` is submitted only after wait completion, so its CQE can never satisfy the current wait.
3. **Bounded waits retained**: the BUG-410 watchdog (100 ms) still bounds every park; a watchdog-arm or submit failure falls back to the bounded 10 ms nanosleep + non-blocking poll, unchanged.
4. **Drop the `reserved_slots == 0` downgrade**: idling with zero native IO parks on the (bounded) blocking wait. Cross-thread wakes keep working through the persistent eventfd read (`io.wakeup_eventfd` from the audited push sites — Soon.dispatch/dispatch_guaranteed/IO.queue/handle_cancel/call_soon_threadsafe, all mutex-first). Timers are WaitTimer ring SQEs (reserved slots), so deadline wakes are untouched. The busy shape (callbacks executed this round → `wait == false`) retains the full-speed non-blocking polling the P23 Task Spawn benchmark relies on.

## Hypotheses rejected on the way (for future archaeologists)

- **"The down-conversion at `reserved_slots == 0` is the freeze"** — removing it alone did NOT fix wormhole (A/B: still exit 124 frozen at 6.8 MB). It was a real, secondary defect, but wormhole's shape has 5 ops in flight, so `should_wait` was already `true`.
- **"It is a GIL-fight introduced by P23's ring_blocked release/acquire demotion"** — the fight is real, but it is the *symptom* of the never-parking spin; P23's demotion (rev 1229) is orthogonal (era wheels v0.10.0 with the old seq_cst behave identically well).
- **"The bind is a NEW v0.11.x regression of the task machinery"** — no: `hg diff -r 1173` isolates the watchdog rewrite; the task-registration stages (revs 1224..1229) are contract-preserving and unrelated.
- During the chase, the third trace (test 3 in the new gate file) initially hung — that was a **test defect** (`counter["n"].__setitem__` bound to an int), not a runner defect; py-spy + gdb on that hang also proved the *park* worked and the parked loop honestly waited with nothing arriving.

## Deferred observations (not bugs today)

- `reserved_slots = 5` persisted through the freeze windows (2 persistent reads + what looks like 3 dormant registrations). Completions still wake the loop correctly; recording here in case a future accounting bug lands.
- The loop's per-iteration fork-guard (`std.os.linux.getpid()` every iteration) showed up as the iteration-rate fingerprint; consider caching once the Fork-safety design revisits this file.
