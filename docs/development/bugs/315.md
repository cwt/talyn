# BUG-315 — File watcher leak on Soon.dispatch exhaustion in loop_watchers_callback

- **Status**: 🔴 Open (2026-09-07)
- **Severity**: 🔴 High — Watcher handle and callback leak on Soon dispatch failure
- **Files**:
  - `src/loop/python/io/watchers.zig` (`loop_watchers_callback`: lines 121–127)
- **Lessons**: [Event Loop Lifecycle](../lessons/03-event-loop-lifecycle.md), [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md)
- **Description**:
In `loop_watchers_callback`:
```zig
Loop.Scheduling.Soon.dispatch(
    self,
    watcher.handle,
    &.{python_c.Py_None},
) catch |err| {
    log.err("failed to dispatch watcher callback: {s}", .{@errorName(err)});
    return;
};
```
If `Soon.dispatch` fails (ring exhaustion or OOM), the function returns without cleaning up the watcher handle. The watcher entry remains in the B-tree in an inconsistent state, stranding its allocated resources and handle object.
- **Root Cause**: Early return without cleanup on dispatch error.
- **Trigger Scenario**: High loop load saturating the `Soon` ring buffer while file descriptor watchers fire.
- **Proposed Remediation**: Handle the error by scheduling watcher cleanup or invoking the loop exception handler to notify user space.

- **Validation (2026-09-07)**: Confirmed still present.
  - `loop_watchers_callback` (`src/loop/python/io/watchers.zig:121-127`): `try Loop.Scheduling.Soon.dispatch(...)` at line 122 propagates the error with no cleanup — the watcher stays in the reader/writer B-tree with `blocking_task_id` already zeroed (line 121), stranding the handle and its callback state.
  - Contrast the `io_uring_err != .SUCCESS` branch (`watchers.zig:124-127`), which routes through `loop_watchers_cleanup_callback`; the dispatch-failure path has no equivalent.
