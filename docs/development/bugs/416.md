# BUG-416 — missing `Loop.get_exception_handler` is a boot blocker for any exception-handler-driven consumer

- **Status**: 🟢 **Fixed** (2026-11-06 — see the validation section below; fix + canary + regression gate `tests/test_exception_handler_api.py`)
- **Severity**: 🟠 High — prompt_toolkit `Application.run()` (any TUI: pyvim, ptpython family, your own editors) failed on its **first statement inside `run_async`**; other consumers that snapshot/restore an exception handler crashed the same way
- **Category**: ABI/`asyncio` conformance — single missing abstract override (plus one attribute-level sibling found by the canary, below)
- **Files**: `talyn/loop.py` (`Loop`; sibling methods at `loop.py:267-334`), method surface in `src/loop/python/main.zig` (`PythonLoopMethods`)
- **Amendment (consumer canary)**: with only the getter shimmed, a bare pyvim boot stops at the *next* PTK loop-member gap — `loop.slow_callback_duration` (`AttributeError: 'Loop' object has no attribute 'slow_callback_duration'`, prompt_toolkit `set_callback_duration`, application.py:840). The "getter is the only blocker" reading held only for the getter; resolved by adding the mirror attribute in the same fix pass.

## What happens

On Python 3.15 every method in `asyncio.events.AbstractEventLoop` is an abstract stub raising `NotImplementedError` (verified by `inspect.getsource` — the "concrete helpers" era is over). talyn's `Loop` subclasses **`AbstractEventLoop` directly** and implements the surface in Zig + the Python `loop.py` layer — which works for almost everything, but three exception-handler accessors were implemented while the fourth was left off:

| Method | Lives at (talyn 0.11.4 wheel) | Status |
|---|---|---|
| `set_exception_handler` | `talyn/loop.py` (`Loop`) | ✅ works |
| `default_exception_handler(context)` | `talyn/loop.py:319` | ✅ works |
| `call_exception_handler(context)` | `talyn/loop.py:333` | ✅ works |
| **`get_exception_handler`** | **`asyncio.events.AbstractEventLoop`** | ❌ **abstract → `NotImplementedError`** |

`prompt_toolkit` (3.0.53) calls exactly this at boot:

```python
previous_exc_handler = loop.get_exception_handler()   # application.py:827 → crash
```

Traceback (full boot of a minimal TUI):

```text
File ".../prompt_toolkit/application/application.py", line 876, in run_async

File ".../prompt_toolkit/application/application.py", line 827, in set_exception_handler_ctx
```

## Repro 2 — runtime proof that this is the only blocker

Monkey-patch just `get_exception_handler` onto `Loop`, then boot a **full pyvim Editor** (edit → `:q` exit) under talyn. It runs and exits cleanly — so the abstract gap is *the only* incompatibility on the prompt_toolkit surface that pyvim exercises (add_reader, executor, timers, loop close all pass):

```python
import asyncio, talyn
from talyn.loop import Loop

handler_state = {"current": None}
_orig_set = Loop.set_exception_handler

def _patched_set(self, handler):
    handler_state["current"] = handler
    return _orig_set(self, handler)

def _patched_get(self):
    return handler_state["current"]

Loop.set_exception_handler = _patched_set
Loop.get_exception_handler = _patched_get

# ... full pyvim Editor with PosixPipeInput(':q\n') then editor.run() ...
# → "Editor exited cleanly under talyn"
```

## Fix (shipped)

- `talyn/loop.py` `Loop.__init__` now records the *user* handler separately (`self._user_exception_handler = None` at construction; `set_exception_handler` records exactly what it was given, `Callable | None`). The dispatch field `self._exception_handler` keeps its pre-bound `default_exception_handler` shape — `_call_exception_handler` and the Zig layer stay untouched.
- `get_exception_handler()` added next to the siblings, honoring `asyncio.BaseEventLoop` semantics: returns the handler previously set via `set_exception_handler`, **`None`** while the default handler is in use. PTK's pattern (get → None ⇒ set own → finally set previous) requires the callable-not-None return after the first set, which this provides.
- Consumer-canary sibling: `self.slow_callback_duration: float = 0.1` — prompt_toolkit's `set_callback_duration` reads AND writes it (`application.py:840/841/846`); AttributeError on the read stopped the pyvim boot immediately after the getter fix. The native slow-callback reporter (`runner.zig` `call_once` → `DebugState`) keeps its own threshold; this attribute is the consumer-facing surface (single source of truth for the native knob remains native).

## Fix direction

Add the method to `talyn/loop.py`'s `Loop` (next to the siblings it already has), honoring `BaseEventLoop` semantics that consumers rely on:

- `get_exception_handler()` returns the handler previously set via `set_exception_handler`, or **`None`** when the loop is running on the default handler.
- talyn currently initializes `self._exception_handler = self.default_exception_handler` (`loop.py:269-270`) rather than `None`. Two options, both fine: (a) keep that field for dispatch and add a separate `self._user_handler: Callable | None = None` that `set_exception_handler` records and `get_exception_handler` returns; or (b) store `None` by default and dispatch on explicit-default in `_call_exception_handler`. (a) is the smaller diff: `_call_exception_handler` (`loop.py:317`) keeps using `_exception_handler` unchanged.
- PTK's pattern is get → (None ⇒ set own handler) → finally set(previous); returning a `Callable` from the first `set` call is therefore *required* — returning `None`-instead-of-handler or raising both break every consumer.

## Regression guard

`tests/test_exception_handler_api.py` (shipped with the fix) covers the quartet dynamically, the None-by-default contract, PTK's snapshot shape, custom dispatch, and the TypeError guard. To preempt future abstract-stub regressions, extend the enumeration to the full `asyncio.events.AbstractEventLoop` method list as more consumers report gaps.
