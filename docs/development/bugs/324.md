# BUG-324 — Unchecked 64-bit integer narrowing panics across socket and transport APIs

- **Status**: 🟢 Fixed (2026-09-07)
- **Severity**: 🟢 Low — Unchecked @intCast on 64-bit Python values causing runtime integer cast panics
- **Files**:
  - `src/utils/pseudosocket.zig` (lines 120, 127); `src/loop/python/io/socket/ops.zig` (line 340); `src/loop/python/io/subprocess/exec.zig` (line 43); `src/utils/address.zig` (lines 353–356)
- **Lessons**: [Security & Input Validation](../lessons/09-security-and-input-validation.md), [Zig Specific Patterns](../lessons/08-zig-specific-patterns.md)
- **Description**:
Across several files:
- `pseudosocket.zig:120, 127`: `level` and `optname` cast from `c_long` to `u32` with `@intCast`.
- `ops.zig:340`: `nbytes` in `loop_sock_recv` cast from `isize` to `usize` with `@intCast(nbytes_long)`.
- `exec.zig:43`: `pid` cast from `c_long` to `i32` with `@intCast`.
- `address.zig:353–356`: `flowinfo` and `scope_id` cast to `u32` with `@intCast`.
If negative or out-of-range values are passed from Python, `@intCast` panics in Debug/ReleaseSafe builds instead of raising `ValueError` or `OverflowError`.
- **Root Cause**: Direct `@intCast` without prior range validation.
- **Trigger Scenario**: Passing negative `nbytes`, out-of-range socket options, or invalid scope IDs from Python.
- **Proposed Remediation**: Use `std.math.cast` or explicit `if (val < 0 or val > max) return PyErr(ValueError);`.

- **Fix (Applied — 2026-09-07)**:
  - `pseudosocket.zig` `setsockopt`: `level`/`optname` (after the existing negative check) and the integer `value` now use `std.math.cast` with `ValueError("... out of range")` on failure instead of raw `@intCast`.
  - `ops.zig` `loop_sock_recv` AND `loop_sock_recvfrom` (the filing only cited recv; recvfrom had the identical pattern): negative `nbytes` now raises `ValueError("nbytes must be non-negative")` before the `usize` cast.
  - `exec.zig` `z_subprocess_exec`: non-positive pids raise `ValueError("pid must be a positive integer")`; pids beyond `pid_t` range raise `ValueError("pid out of range")` via `std.math.cast`.
  - `address.zig` `fromPyAddr`: out-of-range `flowinfo`/`scope_id` raise `error.InvalidAddress` via `std.math.cast` instead of truncating into a different destination address.
- **Regression tests**: `tests/test_pseudosocket.py::test_pseudosocket_setsockopt_out_of_range_raises` (level/optname/value), `tests/test_sock.py::test_sock_recv_negative_nbytes_raises`, `tests/test_subprocess.py::test_subprocess_exec_pid_out_of_range_raises` (drives the NATIVE method directly — the Python wrapper always passes a real `popen.pid`), `tests/test_datagram.py::test_datagram_sendto_scope_id_out_of_range_raises` (4-tuple flowinfo/scope_id).
  - Harness note: the datagram tests were written as `talyn.run`-based sync tests on purpose — the pre-existing `@pytest.mark.asyncio` datagram tests run on STOCK asyncio (no policy install; there is no conftest), so async-marked additions there exercise nothing talyn-specific.
- **Validation (2026-09-07)**: Confirmed still present at all four cited sites (minor naming drift only).
  - `src/utils/pseudosocket.zig:116-121`: `raw_level`/`raw_optname` are only checked `< 0`; `@intCast(c_long → i32/u32)` still panics on values above the target width. `pseudosocket.zig:127`: `@intCast(c_long → c_int)` for the option value has no range check at all.
  - `src/loop/python/io/socket/ops.zig:338-340`: `nbytes_sz` (`PyLong_AsSsize_t`, isize) → `@intCast` to usize panics on negative input.
  - `src/loop/python/io/subprocess/exec.zig:41-43`: `PyLong_AsLongLong` → `@intCast` to `pid_t` (i32) panics outside i32 range.
  - `src/utils/address.zig:351-356`: `PyLong_AsUnsignedLong` (u64) → `@intCast` to u32 for `flowinfo`/`scope_id` panics above u32 max.
