# BUG-209 — Leaked PythonHandleObject on Callback Exception in callback_for_python_generic_callbacks

- **Status**: ⚪ False Positive (Invalid)
- **Severity**: 🟡 Medium — Reference Leak on Exception
- **Files**: `src/handle.zig:72-77`
- **Lessons**: [BUG-177](177.md), [Memory & Refcounting §Lesson 2](../lessons/01-memory-and-reference-counting.md), [Lifecycle & Error Handling §Lesson 4](../lessons/03-event-loop-lifecycle.md)
- **Description**: Initial audit flagged `if (success) python_c.py_decref(handle)` as a potential leak on Python callback exception. However, generic Python callbacks registered in the ready ring buffer have `.cleanup = &Handle.release_python_generic_callback`. When `callback_for_python_generic_callbacks` returns `error.PythonError`, `execute_dynamic_ring_buffer` catches the error, passes `callback.data.callback_ptr()` (which is stored inside the handle) to the loop's `exception_handler`, and then invokes `callback.cleanup` (which calls `py_decref(handle)`). An unconditional decref inside the callback causes immediate deallocation of `handle`, producing a dangling pointer when constructing the exception handler dictionary (causing a segfault in Python runtime), followed by a double-decref. The success guard is correct and required.
- **Trigger**: Any scheduled Python callback that raises an exception.
- **Consequences**: Memory leak of `PythonHandleObject` instances on callback errors.
- **Fix**: Make handle decref unconditional via `defer python_c.py_decref(@ptrCast(handle));` once the callback execution scope is entered.
