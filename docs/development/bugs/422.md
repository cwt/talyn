# BUG-422 — BTree split OOM leaves an overfull node (next insert out-of-bounds)

- **Status**: 🟢 Fixed
- **Severity**: 🟠 High — panic (Debug/ReleaseSafe) / UB (ReleaseFast) on the next insert
- **Category**: Data structure / OOM rollback
- **Files**: `src/utils/btree.zig:253-308`
- **Related**: [BUG-368](368.md) (split OOM leak + child-shift alias), [BUG-1](001.md), [BUG-23](023.md), [BUG-448](448.md) (same swallow via `replace()`)

## Description

`insert_in_node` commits the insertion before it allocates the split node:

```zig
inline fn insert_in_node(...) !void {
    try do_insertion(node, key, value, null);   // may raise nkeys to Degree
    try split_nodes(allocator, node);           // try create_node may OOM
}
```

`do_insertion` appends at `keys[nkeys]` (arrays are `[Degree]Key` / `[Degree+1]?*Node`), so a node
with `nkeys == Degree` makes the *next* `keys[nkeys]` / `childs[nkeys+1]` out-of-bounds.
`split_nodes` allocates `new_node1` **after** `do_insertion` committed, and `insert` swallows the
error (`insert_in_node(...) catch return false`), leaving the overfull node in the tree.

BUG-368 fixed the *leak* (errdefers) and the child-shift alias, but not this "overfull node survives
a failed split" state.

## Trigger

Allocation failure (OOM) while splitting a full node, followed by any later insert that descends
into that node.

## Consequences

`keys[Degree]` / `childs[Degree+1]` write past the array → panic in safe modes, heap corruption in
ReleaseFast. Violates Architectural Mandate #1 (no panics in IO path — this tree backs watchers/timers).

## Fix

Allocate the split node(s) *before* `do_insertion` (so an OOM aborts before mutating), or roll the
insertion back with an `errdefer`, or reject `nkeys == Degree` in `do_insertion`.

## Resolution (2026-11-12)

`insert_in_node` now commits the insertion and then **simulates the split cascade exactly**
(every reached ancestor is evaluated with the nkeys it will have when the real cascade reaches it —
`p.nkeys + 1 == Degree` decides whether it splits too), pre-allocates every node the cascade needs,
and only then runs the now allocation-free split. If pre-allocation fails, the committed insertion
is undone (`undo_insertion` — the exact inverse of `do_insertion`'s shift, memory-safe within the
committed span) and the error propagates, leaving the tree unchanged. `do_insertion` now returns the
insertion index; `split_nodes` receives a preallocated node pool instead of allocating. Both the
`insert()` and `replace()` swallow paths (`BUG-448`) are covered by the same fix.

Unit tests added in `src/utils/btree.zig`:
`BUG-422: failed split leaves no overfull node and the tree unchanged` and
`BUG-448: replace() survives split OOM the same way` — both sweep every `FailingAllocator` fail
index, assert no node sits at `nkeys == Degree` after the OOM, verify sorted readback of everything
loaded, and complete the load through a working allocator.

Validation: `zig build test` green on Zig 0.16.0 and 0.17.1;
`./scripts/test_all.sh --python=3.15,3.15t --starburst --verbose` green (499 pytest passed on
py3.15, 498 + 1 skipped on py3.15t; stdlib asyncio green on both).
