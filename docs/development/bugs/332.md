# BUG-332 — Cancelled `getnameinfo` future aborts at loop close (double-dispatched DNS callback UAF)

- **Status**: ✅ Fixed (2026-09-22)
- **Severity**: 🔴 High — a normal asyncio API sequence (`getnameinfo` + `cancel` + `await`) aborts the host Python process with SIGABRT (core dumped) during `loop.close()`.
- **Files**:
  - `src/loop/dns/resolv.zig` (`ControlData.release` dispatches `user_callbacks`; `ServerQueryData.release`/`cancel` run from both `dns.deinit` and io_uring cancel completions)
  - `src/loop/main.zig:136,142-144,169-174` (`release()` order: `dns.deinit` → first ring release → `io.deinit` → second ring release)
  - `src/loop/python/io/socket/getnameinfo.zig:33-45` (`getnameinfo_callback` calls `get_data_ptr` before the `cancelled()` check and frees `GetNameInfoData` in a `defer`)
- **Discovered by**: BUG-331 regression-test development (the original `test_getnameinfo_accepts_keyword_arguments` used `cancel()` and aborted the pytest process).

## Reproduction

```python
import asyncio

import talyn


async def main():
    loop = asyncio.get_running_loop()
    fut = loop.getnameinfo(("127.0.0.1", 443), 0)
    fut.cancel()
    try:
        await fut
    except asyncio.CancelledError:
        pass


talyn.run(main())
```

## Observed variants

| Sequence | Result |
|---|---|
| `fut.cancel()` + `await fut` + loop close | **SIGABRT / core dump** (panic in `get_data_ptr2`) |
| `fut.cancel()` without `await` | `warning: queue cancel failed: LoopDeinitialized`, no abort (cancel silently lost) |
| `fut.cancel()` + `await fut` + `await asyncio.sleep(0.1)` before close | Clean exit |

The `sleep` variant lets the cancelled DNS callback run to completion before teardown, which masks the race — the abort depends on the callback still being queued when `loop.close()` runs.

## Root Cause (analysis)

1. `getnameinfo` registers `getnameinfo_callback` as the DNS user callback. On
   invocation it frees `GetNameInfoData` (`gnid`) in a `defer`, and it calls
   `utils.get_data_ptr(Loop, gnid.loop)` **before** checking
   `data.cancelled()`.
2. During `Loop.release()` (`src/loop/main.zig`):
   - `dns.deinit()` (line 136) finalizes pending queries; for unresolved
     records `ControlData.release()` marks each user callback cancelled and
     dispatches it into the ready ring (via
     `Soon.dispatch_nonthreadsafe`, because `initialized` is already false).
   - The first `release_dynamic_ring_buffer` pass (lines 142-144) invokes the
     callback, which frees `gnid` and returns early on `cancelled()`.
   - `io.deinit()` (line 169) cancels in-flight io_uring ops; the DNS
     `ServerQueryData.release()`/`cancel()` path can dispatch the *same* user
     callback again (this is also where
     `warning: queue cancel failed: LoopDeinitialized` originates — a
     `CancelByFd` is queued after the ring is gone).
   - The second `release_dynamic_ring_buffer` pass (lines 172-174) invokes the
     duplicate callback entry, which reads `gnid.loop` from the already-freed
     `GetNameInfoData` — the misaligned pointer panics in `get_data_ptr2`.
3. The stack confirms the crash is on the second pass
   (`loop/main.zig:173`), after the first pass already ran the callback.

Confirmed mechanism (debugged after the initial filing):

- `dns.deinit()` iterates `pending_queries` and calls **`ControlData.release()`
  directly** — it does not go through `ServerQueryData.release()`, so the
  per-query `finished` flag is never set.
- `ControlData.release()` (the old code) destroyed the control data and its
  arena — which owns the `ServerQueryData` slice — while the query's
  `PerformWrite`/`PerformRead` ops were still queued in io_uring.
- `io.deinit()` → `cancel_all` pushes those op callbacks into the ready ring.
  The post-`io.deinit` drain invokes them with `cancelled = true`, but
  `on_query_sent`/`process_dns_response` first call `server_data.release()`:
  the freed `finished` flag now reads `false`, so it calls `cancel()` (hence
  `queue cancel failed: LoopDeinitialized`), bumps `tasks_finished` on freed
  memory, and reaches `ControlData.release()` again — which re-dispatches the
  user callback whose `GetNameInfoData` was already freed by the first pass.
- The re-dispatched `getnameinfo_callback` reads `gnid.loop` from freed memory
  → `panic: incorrect alignment` in `get_data_ptr2` (SIGABRT, core dumped).

So: teardown destroyed DNS query state before its io_uring completions ran,
and `ControlData.release()` had no single-shot guard.

## Fix (implemented)

1. **Single-shot release**: `ControlData.released` makes `release()` a no-op on
   re-entry, so the user callbacks can only ever be dispatched once.
2. **Deferred destruction**: `ControlData.destroy()` is split out; during
   teardown (`loop.initialized == false`) `release()` parks the control data on
   `DNS.deferred_release_head` (intrusive `next_deferred` list) instead of
   destroying it. `Loop.release()` calls `DNS.release_deferred()` after the
   post-`io.deinit()` callback drain, so late cancel completions always operate
   on valid memory and exit through the `finished`/`released` guards.
3. **No redundant cancels during teardown**: `ServerQueryData.cancel()` only
   queues `CancelByFd` while `loop.initialized` — `io.deinit()`'s `cancel_all`
   has already cancelled every in-flight op, so the late cancel attempt (and
   its `LoopDeinitialized` warning) is gone.

Files: `src/loop/dns/resolv.zig` (`released`, `next_deferred`, `destroy`,
`release`, `cancel`), `src/loop/dns/main.zig` (`defer_release`,
`release_deferred`), `src/loop/main.zig` (`Loop.release` drain point).
