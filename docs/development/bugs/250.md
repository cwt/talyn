# BUG-250 — Double-decref on exception_handler during failed loop_init in constructors.zig

- **Status**: ✅ Fixed
- **Severity**: 🟠 High — Memory safety / use-after-free
- **Files**: `src/loop/python/constructors.zig`
- **Lessons**: [Python §Lesson 76 — Reference Cleanup on Early Exit](../lessons/05-python-c-api-correctness.md), [Defensive §Lesson 46 — Allocation & Initialization Order](../lessons/10-defensive-programming-and-code-quality.md)
- **Description**: In `src/loop/python/constructors.zig:215`, `self.exception_handler` is assigned via `python_c.py_newref(exception_handler.?)` followed by `errdefer python_c.py_decref(exception_handler.?)`. If the subsequent `ready_tasks_queue_capacity > std.math.maxInt(usize)` check or `loop_data.init` fails, the `errdefer` decrefs `exception_handler.?` but does not null out `self.exception_handler`. When Python cleans up the failed `LoopObject`, `loop_dealloc` invokes `loop_clear` -> `deinitialize_object_fields`, which sees `self.exception_handler != null` and decrefs it a second time.
- **Trigger**: Initializing `talyn.Loop(ready_tasks_queue_capacity=...)` with an invalid capacity or failing allocator initialization.
- **Consequences**: Premature deallocation / use-after-free of the user-provided exception handler callable object.
- **Resolution**: Move `ready_tasks_queue_capacity` validation before assigning `self.exception_handler`, and null out `self.exception_handler` in the error cleanup block (`errdefer { python_c.py_decref(self.exception_handler.?); self.exception_handler = null; }`).
- **Verification**: Test initializing `talyn.Loop` with invalid capacity and verify no reference count corruption.
