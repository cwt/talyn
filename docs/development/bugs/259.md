# BUG-259 — hook GC traversal gap (`HookHandle.callback` not visited)

- **Status**: ✅ Fixed
- **Severity**: 🟡 Medium — Garbage collection correctness (ghost reference / uncollectable cycle)
- **Files**: `src/loop/python/control.zig`, `src/loop/python/constructors.zig`
- **Lessons**: [Memory §GC Traversal](../lessons/01-memory-and-reference-counting.md)
- **Description**: `z_loop_add_hook` registers the hook as `.data = .{ .user_data = handle }` with **no `python_payload`** (`control.zig:229-233`). Consequently `CallbackData.traverse()` / `module_ptr()` / `callback_ptr()` all return `null` for hooks, so `traverse_hooks` (`constructors.zig`) visits **nothing** for hooks. The `HookHandle` holds a `callback: ?PyObject` (and the loop `py_incref`s the handle), but that `PyObject*` is never reported to the GC visitor — unlike FD watchers (`watchers.zig:198`) and signals (`unix_signals.zig:74`), which populate `python_payload` and are traversed. A reference cycle involving `loop ↔ HookHandle ↔ user callback` (e.g. a hook closure capturing the loop) becomes an **uncollectable GC cycle**. This is distinct from BUG-218/219 (which fixed `callback_ptr` skips when `module_ptr` is null in `traverse_hooks`/`BlockingTasksSet`) — here the hook has no `python_payload` at all.
- **Trigger**: A registered loop hook whose callback forms a reference cycle with the loop.
- **Consequences**: Uncollectable GC cycle → leaked loop / hook / callback for the process lifetime.
- **Resolution**: Give `HookHandle` a `python_payload: ?*CallbackManager.PythonPayload` field; register with `CallbackData.init_python(handle, &handle.python_payload)`, setting `module_ptr` to the loop object, `callback_ptr` to `handle.callback`, and a `traverse` visitor — mirroring `io/watchers.zig` and `unix_signals.zig`.
- **Verification**: Register a self-referential hook, drop all external references, force `gc.collect()`, and assert the hook (and its callback) is reclaimed.
