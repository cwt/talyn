# BUG-233 — Datagram `close()` and `dealloc` duplicate resource cleanup and fd close

- **Status**: ✅ False Positive
- **Severity**: 🟢 Medium-Low — Code quality / Fragile teardown
- **File**: `src/transports/datagram/main.zig:~136-165` (dealloc), `src/transports/datagram/main.zig:~177-200` (close)
- **Lessons**: [Defensive §Lesson 79 — Silent Failure](../lessons/10-defensive-programming-and-code-quality.md), [Event Loop §Lesson 2 — Shutdown ordering](../lessons/03-event-loop-lifecycle.md)
- **Description**: Both `datagram_close` and `datagram_dealloc` perform nearly identical teardown:

  1. `datagram_close` (Python API): sets `closed = true`, queues io_uring cancels, closes `fd`, calls `cleanup_resources(instance)` which releases fixed-file slots and buffer pool entries.
  2. `datagram_dealloc` (GC finalizer): calls `cleanup_resources(instance)`, then if `!closed and fd >= 0` does a debug warning, then closes `fd` again, sets `closed = true`, and decrefs Python objects.

  While the `closed` flag provides some protection against actual double-close (Linux `close()` on an already-closed fd returns `-EBADF` safely), the duplicated logic is fragile. If `cleanup_resources` is called twice (once from `close`, once from `dealloc` before `closed` is set), the fixed-file slot release and buffer pool release could both attempt to operate on already-released resources.

  More critically, `datagram_close` does NOT decref `protocol`, `protocol_datagram_received`, `protocol_error_received`, or `protocol_connection_lost` — these are only decref'd in `datagram_dealloc`. If `close()` is called from Python and the object is later garbage collected, `dealloc` will run and decref them (correct). But if `close()` is called and then the loop closes before GC, the references are still held until `dealloc` runs.

- **Trigger**: Any sequence where `transport.close()` is called from Python followed by garbage collection.
- **Consequences**: Potential double-release of fixed-file slots or buffer pool entries; duplicated teardown logic is hard to audit for correctness.
- **Fix**: Extract the Python-object cleanup (decrefs) into a shared helper function. Move `cleanup_resources` call to only `dealloc` and have `close()` just mark state and queue cancellations. Or vice versa — have `close()` do the full teardown and have `dealloc` be a no-op if already closed.
