# BUG-328 — create_connection(sock=) leaves the caller's socket open after transport close

- **Status**: 🟢 Fixed (2026-09-07)
- **Severity**: 🔴 High — Leaked connection after transport close: peers wedged waiting for EOF, cascading into accept-queue exhaustion and connect hangs
- **Files**:
  - `src/loop/python/io/client/create_connection.zig` (sock path of `z_loop_create_connection`; `TransportCreationData`; `z_create_transport_and_set_future_result`)
- **Lessons**: [Network Protocols & IO](../lessons/06-network-protocols-and-io.md), [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md), [Event Loop Lifecycle](../lessons/03-event-loop-lifecycle.md)
- **Description**:
  CPython hands the wrapped socket object to the transport and closes it at teardown:
  ```python
  # asyncio/selector_events.py - _SelectorTransport._call_connection_lost
  finally:
      self._sock.close()   # closes even user-provided (sock=) sockets
  ```
  Talyn's sock path set `owns_fd = false` ("caller owns the fd"), so the transport never closed the connection. After `transport.close()` (and even after dropping every Python reference), the socket stayed ESTAB. With a peer that waits for EOF (any recv-until-close loop), the cascade is:
  1. The peer's receive loop never ends → its `accept()` never runs again.
  2. New connects pile into the listen backlog until it overflows; the kernel drops SYNs.
  3. Subsequent `create_connection` calls sit in SYN-SENT with SYN retransmission backoff (~2 minutes with default `tcp_syn_retries`) and **no connect timeout** → the loop's `create_connection` future appears to hang forever.
  Diagnosed live with gdb (`io_uring_enter(min_complete=1)`, 0% CPU) + `ss` (`SYN-SENT` to a listener with a full accept queue, `ESTAB` socket still open after close).
- **Root Cause**: Ownership divergence from CPython: the sock-path transport treated the caller's fd as permanently caller-owned instead of adopting the connection at transport creation.
- **Trigger Scenario**: `loop.create_connection(protocol, sock=s)` followed by `transport.close()` while the peer waits for EOF — or any reuse pattern where the closed transport's connection lingers.
- **Proposed Remediation**: Adopt the connection the way CPython does: dup the caller's fd into the transport (its own descriptor number) and close the CALLER'S SOCKET OBJECT at adoption. Closing only the raw fd number is NOT enough: the caller's socket object would keep the connection open (no FIN until the object is GC'd — for the last sock= cycle it never is), and closing the raw number alone would leave the object wrapping a descriptor that may later be REUSED by an unrelated socket (its eventual close would kill that socket — observed as `EBADF` from a fresh `connect()` during the fix's first attempt).

## Fix (Applied — 2026-09-07)

- `TransportCreationData` gained `py_sock: ?PyObject` (owned ref, GC-visited in `traverse`, released in the dispatch-failure errdefer and the callback cleanup defer).
- `z_create_transport_and_set_future_result`: on the sock path the fd is adopted via `dup()` into the transport (`owns_fd = true` — its teardown closes the dup, delivering EOF), and the caller's socket OBJECT is closed immediately after (CPython semantics; close errors swallowed). The errdefer disarms once the transport takes ownership so no double-close exists. Pre-adoption error paths still leave the caller's socket untouched (a failed `create_connection` does not close the caller's socket — matching CPython).
- `create_server(sock=...)` already used the dup pattern (BUG-53 comment); the datagram endpoint already transfers ownership — only the stream sock path diverged.

## Regression test

`tests/test_create_connection.py::test_create_connection_sock_close_eof_reaches_peer` — a sock= connection is closed and the test waits for the peer (a threaded recv-until-EOF server) to observe EOF WITHOUT the caller touching the socket, then verifies the server still accepts a fresh host-path connection. On the unfixed code the EOF never arrives (bounded-wait assertion fails).

## Validation (2026-09-07)

Discovered while investigating the reported pre-existing hang in `test_create_connection.py`'s threaded-echo rapid connect/close pattern; the original reproduction (gdb + `ss` evidence above) completes after the fix. The hang reproduction's Python-side pattern (a sock= socket object outliving its closed transport) is itself the trigger — no talyn-internal wedge remains.
