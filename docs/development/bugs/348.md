# BUG-348 — `loop_close` unlocks `loop_data.mutex` before calling `loop_data.release()` and lacks `loop_data.initialized` guard

- **Status**: 🔴 Open
- **Severity**: 🔴 Critical — data race and use-after-free during `loop.close()` when background threads call `call_soon_threadsafe` or free-threaded GC runs `loop_traverse`, plus uninitialized mutex access if `Loop.__new__` was called without `Loop.__init__`
- **Category**: Race Condition / Use-After-Free
- **Files**:
  - `src/loop/python/control.zig:396-415`
  - `src/loop/python/constructors.zig:55-60`
  - `src/loop/python/scheduling.zig:84-93`
- **Related**: [Lesson 19](../lessons/01-event-loop-and-lifecycle.md), [Architectural Mandate #3](../architectural-mandates.md)

## Overview & Root Cause

In `src/loop/python/control.zig:396-415`, `loop_close` releases `loop_data.mutex` **before** calling `loop_data.release()`:

```zig
pub fn loop_close(self: ?*LoopObject) callconv(.c) ?PyObject {
    const instance = self.?;

    if (Loop.Python.check_thread(instance)) return null;

    const loop_data = utils.get_data_ptr(Loop, instance);
    loop_data.mutex.lock();

    if (loop_data.running) {
        loop_data.mutex.unlock();
        python_c.raise_python_runtime_error("Cannot close a running event loop\x00");
        return null;
    }

    loop_data.mutex.unlock();
    loop_data.release();

    return python_c.get_py_none();
}
```

Compare this with `loop_clear` in `src/loop/python/constructors.zig:55-60`, which correctly checks `if (loop_data.initialized)` and holds `loop_data.mutex` across `loop_data.release()`:

```zig
if (loop_data.initialized) {
    loop_data.mutex.lock();
    defer loop_data.mutex.unlock();

    loop_data.release();
}
```

Because `loop_close` unlocks `loop_data.mutex` before `loop_data.release()` (and `loop_data.initialized` is only set to `false` at the very end of `Loop.release()` in `src/loop/main.zig:242`):
1. A concurrent thread calling `loop.call_soon_threadsafe(...)` (`src/loop/python/scheduling.zig:84-93`) acquires `loop_data.mutex`, sees `loop_data.initialized == true`, and appends to `loop_data.ready_tasks_queues` at the exact same moment `loop_data.release()` is draining and freeing `ready_tasks_queues`!
2. On free-threaded Python (3.13t/3.14t), `loop_traverse` (`src/loop/python/constructors.zig:21-46`) acquires `loop_data.mutex` to traverse `ready_tasks_queues`, `blocking_tasks`, and `dns`, racing directly with `loop_data.release()` freeing those structures without holding `loop_data.mutex`.
3. If `Loop.__new__(Loop)` is instantiated without `__init__` (or after `loop.close()`), `loop_data.initialized` is `false`, yet `loop_close` still calls `loop_data.mutex.lock()` and `loop_data.release()`.

## Trigger Scenario

1. Thread A calls `loop.close()` while Thread B calls `loop.call_soon_threadsafe(cb)` (or GC runs `loop_traverse` in free-threaded mode).
2. `loop_close` unlocks `loop_data.mutex` and enters `loop_data.release()` while `loop_data.initialized` is still `true`.
3. Thread B acquires `loop_data.mutex`, sees `loop_data.initialized == true`, and mutates `ready_tasks_queues` concurrently with `ready_tasks_queues.deinit()`.

## Proposed Remediation

In `loop_close`, check `if (!loop_data.initialized) return python_c.get_py_none();` first, and keep `loop_data.mutex` locked via `defer loop_data.mutex.unlock();` across `loop_data.release()`:

```zig
const loop_data = utils.get_data_ptr(Loop, instance);
if (!loop_data.initialized) {
    return python_c.get_py_none();
}

loop_data.mutex.lock();
defer loop_data.mutex.unlock();

if (loop_data.running) {
    python_c.raise_python_runtime_error("Cannot close a running event loop\x00");
    return null;
}

loop_data.release();
return python_c.get_py_none();
```
