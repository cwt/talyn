# BUG-411 — `create_connection` leaks future/protocol_factory on error

- **Status**: 🔴 Open (confirmed, unfixed)
- **Severity**: 🟡 Medium — per-call reference leaks under allocation pressure; futures can outlive their caller indefinitely
- **Category**: Reference Counting / Error Paths
- **Files**:
  - `src/loop/python/io/client/create_connection.zig:142` — `errdefer ... &.{"future", "protocol_factory"}`
  - `src/loop/python/io/client/create_connection.zig:247-263` — assignments and fallible calls
- **Related**: [BUG-312](312.md) (dispatch-failure leak), [BUG-354](354.md)

## Overview

```zig
errdefer python_c.deinitialize_object_fields(&creation_data, &.{ "future", "protocol_factory" });
...
creation_data.loop = python_c.py_newref(self);
creation_data.future = python_c.py_newref(fut);
creation_data.protocol_factory = python_c.py_newref(protocol_factory);

const creation_data_ptr = try allocator.create(SocketCreationData);
...
try Loop.Scheduling.Soon.dispatch(loop_data, &callback);
```

The exclusion was written for the `sock=` path, which never assigns `future`/`protocol_factory`. On the normal path both are assigned *before* `allocator.create` and `Soon.dispatch`, so an allocation or dispatch failure skips their decref. The stack `creation_data` is abandoned without releasing them.

## Trigger Scenario and Evidence (confirmed 2026-11-01)

Environment: Apple `container` 1.6.1, Fedora 44 aarch64, Zig 0.16.0, ReleaseFast, Python 3.13.16.

Harness: `LD_PRELOAD=libmalloc_fail.so` fails the n-th heap allocation after `malloc_fail_reset(n)`. Calling the native `create_connection` directly makes the failure land in `z_loop_create_connection`.

Repro: `h12_create_connection_leak.py`.

```text
n=0 before=2 after=3 err=MemoryError
RESULT: FAIL leak at n=0 (+1 factory refs)
```

`sys.getrefcount(factory)` grows by one (and the `creation_data.future` reference is likewise stranded) on the error path.

## Proposed Remediation

Track ownership explicitly: either do not exclude the fields once they have been assigned, or set a flag when ownership is transferred to the heap copy and only then exclude them. A simpler shape is to deinitialize the three fields in a single `errdefer` before the transfer and use a transfer flag:

```zig
var transferred = false;
errdefer if (!transferred) python_c.deinitialize_object_fields(&creation_data, &.{});
...
creation_data_ptr.* = creation_data;
transferred = true;
```

Add a fault-injection regression test that fails the heap-copy allocation and asserts `sys.getrefcount(factory)` is unchanged.
