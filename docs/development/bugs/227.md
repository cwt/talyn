# BUG-227 — ReadTransport `cleanup_resources_callback` double-decref risk on completion path

- **Status**: 🔴 Open
- **Severity**: 🔴 High — Memory corruption / Reference count underflow
- **File**: `src/transports/read_transport.zig:93-107` (cleanup), `src/transports/read_transport.zig:120-160` (read_operation_completed)
- **Lessons**: [Memory §Lesson 107 — Balancing Reference Increments in Asynchronous Completion Callbacks](../lessons/01-memory-and-reference-counting.md), [Zig §Lesson 77 — errdefer After Every Resource Acquisition](../lessons/08-zig-specific-patterns.md)
- **Description**: In `read_transport.zig`, `perform()` increments the parent transport refcount (`python_c.py_incref(self.parent_transport)`) before queuing the io_uring read. The callback chain has two release paths:

  1. **`cleanup_resources_callback`** (the `cleanup` function registered on the callback) always calls `python_c.py_decref(parent_transport)` unconditionally when invoked.
  2. **`read_operation_completed`** (the main completion function) also explicitly calls `python_c.py_decref(parent_transport)` at line ~155 on its success and error paths before returning.

  The `execute_ring_buffer` / `execute_dynamic_ring_buffer` machinery calls `callback.cleanup(data.user_data)` via a `defer` when the callback function returns an error. On the **error path**, both the explicit `py_decref` inside `read_operation_completed` and the deferred `cleanup_resources_callback` fire, causing a double-decref and potential use-after-free. On the **success path**, only `read_operation_completed`'s explicit decref fires (cleanup is not deferred because the callback returned Ok), which is correct.

- **Trigger**: Any io_uring read completion that returns a non-SUCCESS error (ECONNRESET, EPIPE, etc.) on a stream transport's read transport.
- **Consequences**: Reference count underflow → premature deallocation of `StreamTransportObject` → use-after-free → segfault or memory corruption.
- **Fix**: Remove the explicit `python_c.py_decref(parent_transport)` from `read_operation_completed`'s success/error paths, letting `cleanup_resources_callback` be the single release point. Or, restructure so `read_operation_completed` does not call cleanup and cleanup is only invoked on cancellation/error.
