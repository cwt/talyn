# BUG-329 — WriteTransport double-releases consumed Py_buffers on deinit; write_in_flight stuck on cancellation

- **Status**: 🟢 Fixed (2026-09-07)
- **Severity**: 🔴 High — Refcount underflow of exported bytes objects under write pressure: premature free, heap corruption, SIGSEGV
- **Files**:
  - `src/transports/write_transport.zig` (`WriteTransport.deinit`: `for (pending_py_buffers.items)`; `write_operation_completed`: cancelled early-return before `write_in_flight = false`)
- **Lessons**: [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md), [Defensive Programming](../lessons/10-defensive-programming-and-code-quality.md)
- **Description**:
  The WriteTransport buffers caller data as `(pending_buffers: iovec list, pending_py_buffers: Py_buffer list)` pairs; as each chunk completes, the consumed entry's `Py_buffer` is released one-by-one while its (never removed) list entry stays at the consumed index. Two defects interact:
  1. **`deinit` released ALL entries** — `for (self.pending_py_buffers.items) |*v| PyBuffer_Release(v)` — including the consumed prefix `[0..pending_buffer_index)` that had already been released during completion processing. Every consumed buffer was therefore released TWICE. Since `PyBuffer_Release` decrefs the exporter, the exported bytes objects were decref'd past their real refcount → premature free → use-after-free → heap corruption.
  2. **Cancelled completions left `write_in_flight` stuck true** — `write_operation_completed` returned early on `data.cancelled()` BEFORE `self.write_in_flight = false`, so a write cancelled by `close()` wedged the transport's drain: the prepare hook never resubmitted, the buffers were never cleared, and a transport destroyed in that state guaranteed the double-release of part 1.
- **Root Cause**: The release-once invariant was enforced at the completion path but not mirrored by `deinit` (which re-released the consumed prefix), and the in-flight flag reset was placed after an early return.
- **Trigger Scenario**: Any transport destroyed with partially-consumed pending writes — concretely reproduced by the SQ-pressure regression (`test_writev_sq_pressure_no_double_free`, `writelines` under a never-reading peer, followed by close/cancel): SIGSEGV inside `ArrayList(Py_buffer).append` on a neighbouring transport (identified via coredumpctl backtrace), flaky `MemoryError` at Python call boundaries with an empty write buffer, interpreter aborts.
- **Proposed Remediation**: `deinit` releases only the UNCONSUMED suffix `[pending_buffer_index..]` (the consumed prefix was released exactly once at completion); `write_in_flight = false` moves to the top of `write_operation_completed` (before the cancelled early-return) so the in-flight bookkeeping clears on every outcome.

## Fix (Applied — 2026-09-07)

- `deinit`: release loop bounded to `pending_py_buffers.items[pending_buffer_index..]`.
- `write_operation_completed`: `self.write_in_flight = false` executes before the cancelled early-return (the rest of the cancelled path is unchanged — the resubmission machinery resumes draining the remaining data through the still-open fd, matching the graceful-flush close design).
- Verified: the SIGSEGV class is eliminated — the previously-crashing 3.13 SQ-pressure binary now completes its rounds and `test_connection_memory_safety.py` passes 3/3 on python3.13 (previously flaky with segfaults and MemoryError exits).

## Residual (separate bug — BUG-330)

The corruption investigation surfaced a SECOND, pre-existing defect: under the same SQ pressure, `append_new_buffer_to_write` can fail with `error.OutOfMemory` while the target ArrayList's `items.len` holds garbage (a corrupted-pointer-shaped value, `capacity` intact) — an iovec-shaped (16-byte, ptr+len) overwrite onto a neighbouring transport's list struct. Requires multiple transports (single-transport 200-round variant is clean), is load/layout sensitive (base-vs-tip A/B flipped with system state; DebugAllocator build hides it), and needs a dedicated deep-dive of the PerformWrite slot lifecycle. Tracked as [BUG-330](330.md) (Open).

## Validation (2026-09-07)

Discovered while investigating the flaky `test_writev_sq_pressure_no_double_free` failure: coredumpctl backtrace pinned the crash to `ArrayList(Py_buffer).append` called from `transport_write_lines`; the double-release was established by reading the deinit/completion ownership flow.
