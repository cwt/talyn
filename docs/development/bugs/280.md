# BUG-280 — `remove_child_handler` vs pending `on_child_exit` dispatch UAF

- **Status**: 🔵 Open (2026-08-23)
- **Severity**: 🟠 High — Use-after-free / race condition
- **Files**:
  - `src/loop/child_watcher.zig:79-93` (`remove_child_handler`: fetchRemove → queue Cancel → close pidfd → decref → destroy)
  - `src/loop/scheduling/io/cancel.zig` (per-op cancel of a completed task is an ENOENT no-op)
  - `src/loop/runner.zig` (batch reap pushes completions into ready queue before execution)
- **Lessons**: [Memory & Reference Counting §Lesson 50](../lessons/01-memory-and-reference-counting.md), [Concurrency & Thread Safety §Lesson 59](../lessons/02-concurrency-and-thread-safety.md)
- **Description**: Once the exit CQE has been reaped, the queued `on_child_exit` copy carries `user_data = handler`. If removal happens between reap and execution (an earlier callback in the same batch calling `remove_child_handler`, or cross-thread under free-threading where the binding takes no mutex), the Cancel targets an already-finished io task and cannot set the cancelled bit; the handler's pidfd is closed and struct destroyed anyway. Execution then reads freed memory (`handler.pidfd`) and calls an already-decref'd callback object. Lesson 99 fixed self-removal *during* dispatch, not removal *between reap and dispatch*.
- **Trigger**: Timeout/cleanup callbacks removing child handlers concurrently with process exit events.
- **Consequences**: UAF / wild Python call; possible double-close of reassigned fd numbers.
- **Fix (Proposed)**: Defer destruction to the pending callback itself (mark removed + let `on_child_exit` observe it), or apply the generation-counter pattern from BUG-32.
