# BUG-408 — datagram `buffer_size` leaks on cancelled/closed/error completions

- **Status**: 🔴 Open (confirmed, unfixed)
- **Severity**: 🟡 Medium — flow-control state corruption; `get_write_buffer_size()` never returns to zero
- **Category**: Datagram Transport / Accounting
- **Files**:
  - `src/transports/datagram/write.zig:26-65` — `sendto_completed`
  - `src/transports/datagram/write.zig:67-78` — `buffer_watermark_check`
  - `src/transports/datagram/write.zig:167-185` — `z_datagram_sendto`
- **Related**: [BUG-34](034.md), [BUG-320](320.md)

## Overview

`buffer_watermark_check` does `self.buffer_size += len` before queueing. `sendto_completed`:

```zig
if (data.cancelled() or self.closed) { success = true; return; }        // no decrement
if (io_uring_err != .SUCCESS) { ... success = true; return; }           // no decrement
...
self.buffer_size -= written;                                            // success only
```

After `close()`, the pending completion takes the `self.closed` branch and leaves `buffer_size` incremented. Errors and cancellations do the same. A caller that asks for `get_write_buffer_size()` after close sees the stale value forever, and any later `buffer_watermark_check`/`is_writing` calculations start from the wrong baseline.

## Trigger Scenario and Evidence (confirmed 2026-11-01)

Environment: Apple `container` 1.6.1, Fedora 44 aarch64, Zig 0.16.0, ReleaseFast, Python 3.13.16 and 3.13.16t.

Repro: `h17_datagram_size.py`.

```text
initial write buffer: 0
after send: 512
after close+completion: 512
RESULT: FAIL (buffer_size leaked)
```

## Proposed Remediation

Make completion accounting unconditional before the early returns, for example:

```zig
const len = sd.buf.len;
...
self.buffer_size -= @min(self.buffer_size, len);  // once, on every terminal outcome
```

or track the outstanding bytes in the SendToData and subtract exactly that amount on success, cancellation, close, and error. Add a test that sends, closes, awaits completion, and asserts `get_write_buffer_size() == 0`.
