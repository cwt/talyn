# BUG-355 — Memory/reference leaks, missing Python exception before `set_future_exception`, and unresolved `Future` (infinite hang) in `create_endpoint.zig` DNS resolution callbacks

- **Status**: ✅ Fixed (2026-10-18)
- **Severity**: 🔴 High — causes `await loop.create_datagram_endpoint(...)` to hang forever on DNS failure or cancellation and leaks `DatagramCreationData`
- **Category**: Memory/Ref Leak & Logic Bug (Infinite Hang)
- **Files**:
  - `src/loop/python/io/datagram/create_endpoint.zig:131-219, 305-313`
- **Related**: [BUG-354](354.md), [Lesson 41](../lessons/05-python-c-api-correctness.md)

## Overview & Root Cause

In `src/loop/python/io/datagram/create_endpoint.zig:131-219`, the asynchronous DNS resolution chain (`resolve_local_addr` -> `local_addr_resolved_callback` -> `resolve_remote_addr` -> `remote_addr_resolved_callback` -> `create_endpoint`) has three compounding bugs:

1. **No `dcd.deinit()` on any error path in `resolve_local_addr`, `local_addr_resolved_callback`, `resolve_remote_addr`, or `remote_addr_resolved_callback`**:
   `dcd.deinit()` is only called in `create_endpoint` (line 307) or `cleanup_dcd` (lines 48–51, which only runs if a `CallbackManager` callback returns a Zig error). None of the `return set_future_exception(...)` paths in lines 131–219 return a Zig error or call `dcd.deinit()`, leaking `DatagramCreationData` (including `local_addresses`/`remote_addresses` slices and all `PyObject` refs) whenever address parsing or DNS resolution fails.

2. **`set_future_exception(error.PythonError, dcd.future)` called without a Python exception set when `dns.lookup` returns `null` (lines 171 and 211)**:
   In `local_addr_resolved_callback` (lines 163–173) and `remote_addr_resolved_callback` (lines 204–213):
   ```zig
   if (loop_data.dns.lookup(host, &.{ .func = &local_addr_resolved_callback, .cleanup = &cleanup_dcd, .data = .{ .user_data = dcd } }, dcd.dns_timeout) catch null) |addresses| {
       ...
   } else {
       return set_future_exception(error.PythonError, dcd.future);
   }
   ```
   When an async DNS lookup finishes with no records (`NXDOMAIN` / timeout), `dns.lookup` in the callback returns `null` **without** setting any CPython exception on the thread state. Calling `set_future_exception(error.PythonError, dcd.future)` then calls `utils.handle_zig_function_error(error.PythonError, {})` (a no-op) followed by `PyErr_GetRaisedException()`, which returns `null`! `set_future_exception` returns early without setting any exception on `dcd.future`, so `await loop.create_datagram_endpoint(...)` **hangs forever**!

3. **Silent return on `if (data.cancelled()) return;` leaves `dcd.future` unresolved (lines 154, 195, and 308)**:
   In `local_addr_resolved_callback` (line 154), `remote_addr_resolved_callback` (line 195), and `create_endpoint` (line 308):
   ```zig
   if (data.cancelled()) return;
   ```
   When a DNS lookup fails to send on all nameservers (`on_query_sent` error in `src/loop/dns/resolv.zig:373`), `ControlData.release()` dispatches user callbacks with `data.cancelled() == true`. Returning early without calling `set_future_exception` or `dcd.deinit()` (in lines 154 and 195) leaks `dcd` and leaves `dcd.future` pending forever.

## Trigger Scenario

1. Call `await loop.create_datagram_endpoint(factory, remote_addr=("nonexistent.invalid", 53))`.
2. When DNS resolution completes with `NXDOMAIN`, `remote_addr_resolved_callback` sees `dns.lookup(...) == null` and calls `set_future_exception(error.PythonError, dcd.future)` with no Python exception set.
3. `set_future_exception` does nothing, `dcd` is leaked, and the caller awaiting `dcd.future` hangs forever.

## Proposed Remediation

1. In `local_addr_resolved_callback` and `remote_addr_resolved_callback`, call `python_c.raise_python_runtime_error("DNS resolution failed\x00");` (or `OSError`) before `set_future_exception(error.PythonError, dcd.future)`.
2. When `data.cancelled()` is true in `local_addr_resolved_callback`, `remote_addr_resolved_callback`, or `create_endpoint`, set an exception on `dcd.future` (if not already done/cancelled) and call `dcd.deinit()`.
3. Ensure every failure path in `resolve_local_addr`, `local_addr_resolved_callback`, `resolve_remote_addr`, and `remote_addr_resolved_callback` calls `dcd.deinit()`.

## Resolution (2026-10-18)

Two helpers were added to `src/loop/python/io/datagram/create_endpoint.zig`:

- `ensure_exception(err)` — raises if no Python exception is pending: a bare `error.PythonError` becomes `RuntimeError("DNS resolution failed")`, everything else maps through `handle_zig_function_error`. Called before every `set_future_exception`, which silently no-ops without a pending exception (leaving the future pending forever).
- `fail_endpoint(err, dcd)` — resolves the future if still `.pending` (cancelled/resolved futures are left alone), releases `dcd`, and sets the future exception. All failure/cancel paths of `resolve_local_addr`, `local_addr_resolved_callback`, `resolve_remote_addr`, `remote_addr_resolved_callback` route through it (allocation and dispatch failures included). The `dns.lookup(..., null)` synchronous-failure `orelse` branches now raise before setting the future exception.
- `create_endpoint` keeps its `defer dcd.deinit()` ownership; its cancelled branch and `z_create_endpoint` error path set the exception inline (a `fail_endpoint` call would deinit twice).

Verified: `create_datagram_endpoint(remote_addr=("nonexistent.invalid", 53))` resolved the future in ~0.00s with the fix (previously hung until the wait_for timeout, printing `NoneType: None` from the cancellation path).

Test (`tests/test_datagram.py::test_bug355_dns_failure_resolves_future_no_leak`): 5 warmup + 50 failing `remote_addr` resolutions must raise (never hang) and leave `sys.getrefcount(remote_addr)` unchanged. Passes on 3.13/3.13t/3.14/3.14t; verified to hang on the unfixed build.
