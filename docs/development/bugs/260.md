# BUG-260 — Talyn clamps RLIMIT_NOFILE to `TotalTasksItems+64`, exhausting fds under proxy load

- **Status**: 🟢 Fixed (2026-08-20; see Resolution)
- **Severity**: 🟠 High (production-breaking for high-concurrency servers using Talyn as the event loop; misdiagnosed because the real errno was masked)
- **File**: `src/loop/scheduling/io/main.zig` — `IO.init` fd-limit clamp; symptom surfaced in `src/loop/python/io/client/create_connection.zig`, `src/loop/dns/resolv.zig`, and `src/loop/python/io/datagram/create_endpoint.zig`; consumer: wormhole proxy (`../wormhole/wormhole/server.py:24`).
- **Description**: At loop init, `IO.init` raised the process fd limit based on the io_uring SQE depth, not on expected socket concurrency:
  ```zig
  // src/loop/scheduling/io/main.zig (BEFORE)
  const nr_files: u32 = TotalTasksItems;          // = 1024
  var rlim: std.os.linux.rlimit = undefined;
  _ = std.os.linux.getrlimit(.NOFILE, &rlim);
  _ = std.os.linux.setrlimit(.NOFILE, &.{ .cur = nr_files + 64, .max = rlim.max });
  ```
  `TotalTasksItems = 1024` is the io_uring submission-queue depth and has **no relationship** to how many sockets a proxy opens. This `setrlimit` forced the process's soft fd limit to **`1088`** at most — and actually *lower* if the prior hard limit was below 1088, because the `_ =` discarded the `EINVAL` and left the limit at the OS default (typically `1024`). So the entire host process (including wormhole) could never hold more than ~1088 fds.

  A forward proxy keeps **≈2 fds per tunnel** (one client socket + one backend socket) plus DNS/eventfd fds. wormhole derives its concurrency cap from this same limit: `MAX_TASKS = int(0.9 * resource.getrlimit(resource.RLIMIT_NOFILE)[0])` (`wormhole/wormhole/server.py:24`). It reads the limit at *import time*, before Talyn's loop exists and lowers it, and it counts **tasks, not fds**. With Talyn in place the ceiling collapsed to ~1088 while wormhole still admitted ~921 tasks, each needing ≥2 fds → ~1842 fds demanded. Once load was sustained (e.g. a high-traffic asset host like `github.githubassets.com`), the process was permanently fd-starved.

  When fds ran out, every new outbound `socket()` returned `EMFILE`/`ENFILE`. Talyn's connect path **blindly collapsed every socket() failure to `error.SystemResources`**:
  ```zig
  // src/loop/python/io/client/create_connection.zig (BEFORE)
  if (utils.getSyscallErrno(socket_ret) != .SUCCESS) return error.SystemResources;
  ```
  (`src/loop/dns/resolv.zig` and `src/loop/python/io/datagram/create_endpoint.zig` did the same.) `error.SystemResources` is normally reserved for io_uring registered-buffer / `RLIMIT_MEMLOCK` failures (see [BUG-117](../117.md)), so the name pointed operators at the wrong subsystem. The future was then set with a generic `OSError: SystemResources` and wormhole retried 3× (`MAX_RETRY = 3`, `wormhole/server.py:12`) before returning `502`.
- **Trigger**: Run wormhole (or any Talyn-backed proxy keeping many concurrent client+backend sockets) under sustained load. The failure was deterministic and persistent (not burst-only) once steady-state fd usage exceeded the ~1088 ceiling. Observed: `CONNECT 502 github.githubassets.com:443 (All connection attempts failed after 3 retries. Last error: SystemResources)`.
- **Why it looked Talyn-specific**: The default asyncio loop imposes no such 1088 cap (it inherits whatever the OS/hard limit allows), so the same proxy "worked" on the stock loop and only broke once Talyn artificially lowered the fd ceiling at loop init.
- **Consequences**:
  - All outbound connects failed with a misleading `SystemResources` (actually `EMFILE`/`ENFILE`) once fd usage was sustained.
  - The proxy returned `502` for otherwise-reachable destinations; retries could not help because the ceiling was structural, not transient.
  - Diagnosis was obscured by the errno masking (related to the accept-side `EMFILE`/`ENFILE` handling in [BUG-33](../033.md) and the fixed-file-slot accounting in [BUG-26](../026.md)/[BUG-27](../027.md)).
- **Root cause (two coupled defects)**:
  1. **Design flaw**: fd limit coupled to io_uring SQE depth (`TotalTasksItems`). The SQE depth and the fd ceiling are independent quantities; clamping `RLIMIT_NOFILE` to `TotalTasksItems + 64` was both too low and, when the prior hard limit was lower, silently ineffective.
  2. **Diagnostic flaw**: `socket()` failures were reported as `error.SystemResources` instead of the real `EMFILE`/`ENFILE`, hiding the true cause.
- **Resolution (implemented 2026-08-20)**: Both defects fixed; `TotalTasksItems` is left untouched (still the correct SQE depth / fixed-file-table size) — only the unrelated fd-limit logic changed.
  1. **`src/loop/scheduling/io/main.zig` (`IO.init`)**: the soft `RLIMIT_NOFILE` is now raised up to the *existing hard limit* instead of being clamped to `TotalTasksItems + 64`. Talyn no longer shrinks the process fd budget and the process can use as many fds as the system allows:
     ```zig
     // src/loop/scheduling/io/main.zig (AFTER)
     const nr_files: u32 = TotalTasksItems;
     var rlim: std.os.linux.rlimit = undefined;
     _ = std.os.linux.getrlimit(.NOFILE, &rlim);
     if (rlim.cur < rlim.max) {
         _ = std.os.linux.setrlimit(.NOFILE, &.{ .cur = rlim.max, .max = rlim.max });
     }
     ```
  2. **`src/utils/main.zig`**: added `socketSyscallError(err: std.posix.E)` which maps `.MFILE` → `error.ProcessFdQuotaExceeded`, `.NFILE` → `error.SystemFdQuotaExceeded`, else → `error.SystemResources`. Applied at the three `socket()` call sites (`create_connection.zig`, `resolv.zig`, `datagram/create_endpoint.zig`) and the DNS `connect()` path. Added `ProcessFdQuotaExceeded`/`SystemFdQuotaExceeded` to the `OSError` branch in `handle_zig_function_error` so the future's exception is now a clear `OSError` (not the misleading `SystemResources`).
  3. **wormhole follow-up (recommended, out of tree)**: account for ≈2 fds per task and read `RLIMIT_NOFILE` *after* the loop is created. Talyn no longer imposes the artificial 1088 cap, but the proxy should still size its concurrency to the real fd budget.
  - **Regression test**: `test "socketSyscallError surfaces EMFILE/ENFILE distinctly (BUG-260)"` in `src/utils/main.zig` asserts `.MFILE`→`ProcessFdQuotaExceeded`, `.NFILE`→`SystemFdQuotaExceeded`, and other errnos (`.NOMEM`, `.AGAIN`)→`SystemResources`.
  - **Verification**: full suite green — `3.13`/`3.14`/`3.13t`/`3.14t` each **313 passed, 1 skipped**, plus the standard `asyncio` suite (all PASS) and **60 Zig unit tests passed**; AST linter **0 violations**. `=== Results: 4 passed, 0 failed ===`, `EXITCODE=0`.
- **Reproduction**: Run wormhole with Talyn on a host whose `RLIMIT_NOFILE` hard limit is ≤ 1088 (common default `1024`), drive sustained concurrent CONNECT traffic, and observe `socket()` returning `EMFILE`. Before the fix this surfaced as `SystemResources`; after the fix the soft limit is raised to the hard limit and `EMFILE`/`ENFILE` surface as distinct, diagnosable `OSError`s.
