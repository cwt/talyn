# BUG-267 — `run_forever` from a non-creator thread fails: io_uring ring thread-affinity

- **Status**: 🟢 Fixed (2026-08-21)
- **Validation**: 2026-08-21 — CONFIRMED REAL. Reproduced on v0.9.1 (fresh clone build) and on the current tree: running a freshly-created loop from a different thread ("loop in a background thread", a documented asyncio pattern) raises `RuntimeError: InvalidThread` in the run_forever thread, which dies silently; any thread blocked on `run_coroutine_threadsafe(...).result()` then hangs forever. NOT a regression from BUG-261..266 — the trigger is environmental: a dnf update on 2026-08-21 02:56 UTC upgraded Python 3.14.6 → 3.14.7, whose test suite newly ships the gh-152020 test `test_all_tasks_from_other_thread_includes_eager_tasks` (runs `loop.run_forever()` in a fresh thread). 3.13/3.13t skip the module (it doesn't exist there).
- **Severity**: High — RuntimeError + Permanent Hang on a documented asyncio pattern
- **Files**:
  - `src/loop/scheduling/io/main.zig:497` (`IO.init` creates the ring with `IORING_SETUP_COOP_TASKRUN | IORING_SETUP_SINGLE_ISSUER`)
  - `src/loop/runner.zig:280` (`ring.submit_and_wait(1)` in the wait path)
  - `src/loop/runner.zig:311` (`copy_cqes_eintr_safe` → `ring.copy_cqes` → `enter(0, wait_nr, IORING_ENTER_GETEVENTS)`)

## Description

The ring is created at loop construction with `COOP_TASKRUN | SINGLE_ISSUER`, binding it to the thread that created the loop object. When `loop.run_forever()` executes in a different thread, the first poll hits `io_uring_enter(IORING_ENTER_GETEVENTS)` from that thread; the kernel returns **EEXIST** ("the submitting thread is not the thread that initially created the ring"), which `std.os.linux.IoUring.enter` maps to `error.InvalidThread` (std/os/linux/IoUring.zig:207). The error propagates through `copy_cqes_eintr_safe` → `poll_blocking_events` → `Runner.start` → `z_loop_run_forever`, where `handle_zig_function_error` converts it to `RuntimeError("InvalidThread")` raised in the run_forever thread (visible only as "Exception in thread" on stderr). The loop never runs, so the caller's `concurrent.futures.Future.result()` blocks forever → the stdlib harness reports a 60s TIMEOUT.

CPython's `BaseEventLoop.run_forever()` has no thread restriction; running the loop in a dedicated thread with `run_coroutine_threadsafe` from others is a supported pattern.

## Trigger

```python
loop = asyncio.new_event_loop()          # ring created here (main thread)
threading.Thread(target=loop.run_forever).start()   # poll from foreign thread → EEXIST
asyncio.run_coroutine_threadsafe(setup(), loop).result()  # hangs forever
```

## Consequences

- `RuntimeError: InvalidThread` in the run_forever thread; thread dies silently.
- Indefinite hang of any thread waiting on `run_coroutine_threadsafe(...).result()`.
- `test.test_asyncio.test_free_threading` TIMEOUT on Python 3.14/3.14t (harness result is ignored by `test_all.sh`, but the hang is real).

## Fix (Applied — 2026-08-21)

`IO.ensure_ring_for_current_thread()` (called from `Runner.start` under the loop mutex):

- Same thread as ring owner → no-op.
- Different thread and no SQE ever submitted, and the SQ holds only the two persistent reads (eventfd wake-up + signalfd) → recreate the ring in the current thread (`init_ring()` with the same flag fallback chain), re-register the fixed file table and buffers (per-ring state), release the old reads' `BlockingTask` slots (`discard()`, keeping `reserved_slots` balanced), re-queue the eventfd read and the signalfd read (`enqueue_signal_fd(cancel_old=false)`) on the new ring, update `ring_owner_tid`.
- Different thread and SQEs were already submitted, or any other SQE is pending (e.g. a timer queued before the first run) → raise a clear `RuntimeError` (the ring may hold in-flight work or orphanable operations).

New IO fields: `ring_owner_tid` (PyThread ident at ring creation), `ring_has_submitted` (set on every successful submit: `flush_pending_sqes` and the `submit_and_wait` wait path), `eventfd_read_user_data` (used to identify the wake-up read among pending SQEs).

Supporting changes: `register_eventfd_callback` split into a mutex-holding wrapper and `register_eventfd_callback_unlocked` (the ensure path holds the mutex already; the previous code self-deadlocked on the non-recursive spinlock in multi-threaded builds); `IO.deinit` skips `unregister_buffers` when called from a non-owner thread (kernel registration ops are issuer-restricted on SINGLE_ISSUER rings).

Verified: `test.test_asyncio.test_free_threading` no longer hangs on 3.14/3.14t (remaining failures are BUG-268, the task-registry gap). Regression tests in `tests/test_loop_run_forever_thread.py`: background-thread run_forever with `run_coroutine_threadsafe` round-trip; pre-used loop re-run in another thread raises a clear `RuntimeError` and stays usable in its original thread.
