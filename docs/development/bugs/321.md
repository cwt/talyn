# BUG-321 — Exception swallowing and traceback destruction in Python loop protocol callbacks

- **Status**: 🔴 Open (2026-09-07)
- **Severity**: 🟡 Medium — Destruction of real exception type and traceback in protocol dispatch error handlers
- **Files**:
  - `talyn/loop.py` (`_dispatch_data_received`, `_dispatch_eof_received`, `_dispatch_buffer_updated`, `_dispatch_connection_lost`: lines 406–456)
- **Lessons**: [Defensive Programming](../lessons/10-defensive-programming-and-code-quality.md), [Python C-API Correctness](../lessons/05-python-c-api-correctness.md)
- **Description**:
In `talyn/loop.py`:
```python
def _dispatch_data_received(self, transport, data):
    try:
        transport._protocol.data_received(data)
    except Exception:
        self.call_exception_handler({
            'message': 'Fatal error on transport protocol.data_received()',
            'exception': Exception("protocol.data_received() failed"),
            'transport': transport,
            'protocol': transport._protocol,
        })
```
By creating a fresh `Exception("protocol.data_received() failed")` rather than passing the caught exception instance, the real exception type, error message, and Python stack traceback are destroyed, preventing debugging.
- **Root Cause**: Fabricating a new generic `Exception` instance instead of capturing and forwarding the actual caught exception.
- **Trigger Scenario**: Any unhandled exception raised inside a protocol callback (`data_received`, `eof_received`, `connection_lost`).
- **Proposed Remediation**: Use `except Exception as exc:` and pass `'exception': exc` in all dispatch wrappers.
