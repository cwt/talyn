# BUG-426 — Stream transport init error paths miss `PyObject_GC_UnTrack`

- **Status**: 🟡 Open
- **Severity**: 🟠 High — GC traverses freed memory on init failure
- **Category**: GC / init error path
- **Files**: `src/transports/stream/constructors.zig:220-242`
- **Related**: [BUG-283](283.md) (datagram does untrack), [BUG-284](284.md)

## Description

```zig
const instance = @ptrCast(Stream.StreamType.tp_alloc.?(Stream.StreamType, 0) orelse return error.PythonError);
errdefer Stream.StreamType.tp_free.?(instance);   // no PyObject_GC_UnTrack
...
try stream_init_configuration(instance, protocol, loop, fd, zero_copying);   // may fail
```

`PyType_GenericAlloc` tracks GC objects; `stream_dealloc` correctly calls
`PyObject_GC_UnTrack(instance)` before `tp_free` (`constructors.zig:370`). The datagram constructor's
errdefer also untracks first (`datagram/constructors.zig:144-149`). The stream init errdefers
(`constructors.zig:222` and `:240`) do not — so a failure inside `stream_init_configuration`
(fixed-file registration, first read arm, etc.) frees a still-tracked object.

## Trigger

Any failure in `stream_init_configuration` (e.g. fixed-file exhaustion, arm-read failure).

## Consequences

GC may traverse a freed `StreamTransportObject` → UAF / crash.

## Fix

Add `python_c.PyObject_GC_UnTrack(instance);` before each errdefer `tp_free` (or centralize an
errdefer that mirrors `stream_dealloc`).

## 2026-11-12 Validation

- Both errdefer sites confirmed (`constructors.zig:222` and `:240`), neither untracks;
  `stream_dealloc` does (`:370`), and the datagram errdefer untracks first
  (`datagram/constructors.zig:145`).
- Type confirmed: `Py_TPFLAGS_HAVE_GC` (`stream/main.zig:128`), heap type via
  `PyType_FromSpecWithBases` (`:135`), no `tp_alloc` override → `PyType_GenericAlloc` GC-tracks the
  instance at allocation.
- Scope: the reachable site is `:222` (failures inside `stream_init_configuration`); the `:240` site
  in `z_stream_new` is currently dormant (nothing fallible after `tp_alloc`).
