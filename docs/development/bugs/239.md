# BUG-239 — `ServerQueryData.release` lacks atomic guard against concurrent cancel+release

- **Status**: ✅ False Positive
- **Severity**: 🟡 Medium — Double-free / Race condition
- **File**: `src/loop/dns/resolv.zig:~115-135` (ServerQueryData.release, cancel)
- **Lessons**: [Concurrency §Lesson 1 — Atomic sleep races](../lessons/02-concurrency-and-thread-safety.md), [Concurrency §Lesson 17 — Recursive mutex deadlocks](../lessons/02-concurrency-and-thread-safety.md)
- **Description**: `ServerQueryData` has two methods that can run concurrently:

  1. **`cancel()`** — Called when the DNS resolver is shut down or the query is superseded. Sets `socket_fd = -1` and queues a `CancelByFd`.
  2. **`release()`** — Called when the query completes (successfully or with error). Sets `finished = true`, calls `cancel()`, increments `control_data.tasks_finished`, and if all tasks are done, calls `control_data.release()`.

  The race: if `cancel()` is called (e.g., from loop shutdown) while `release()` is concurrently running (e.g., from a completion callback), both paths may reach `control_data.release()` after incrementing `tasks_finished`. The `finished` flag is not atomic, and there is no mutex protecting the transition from `!finished` to `finished`.

  Additionally, `release()` calls `self.cancel()` which closes the pidfd and queues cancellation. If `cancel()` was already called externally, the pidfd is already `-1` and the cancel queue is a no-op — this part is safe. But `control_data.release()` calls `arena.deinit()` and `allocator.destroy(self)` on the `ControlData`. If two threads reach `control_data.release()` simultaneously, the arena is double-deinitialized.

- **Trigger**: DNS query completion racing with loop shutdown or another DNS query cancellation on the same `ControlData`.
- **Consequences**: Double-free of `ControlData` arena and allocator → heap corruption → crash.
- **Fix**: Use an atomic compare_exchange on `finished` in `release()` to ensure only one thread performs the teardown. Add `@atomicCompareExchangeStrong` with `.monotonic` ordering.
