# BUG-401 — `Future.__init__` double-decrefs the loop reference

- **Status**: 🟢 Fixed (2026-11-01)
- **Severity**: 🔴 Critical — reference-count corruption / premature free (use-after-free class)
- **Category**: Python C API / Reference Counting
- **Files**:
  - `src/future/python/constructors.zig:127-131` — second `py_decref`
  - `src/future/python/constructors.zig:51-71` — `future_clear`
  - `src/python_c.zig:648-700` — `deinitialize_object_fields` decrefs `?PyObject` fields
- **Related**: [BUG-386](386.md) (repeated `__init__` handling introduced the extra decref)

## Overview

```zig
if (self.py_loop) |l| {
    _ = future_clear(self);       // deinitialize_object_fields decrefs self.py_loop
    python_c.py_decref(l);        // second decref of the same object
    self.py_loop = null;
}
```

`future_clear` ends with `deinitialize_object_fields(py_future, &.{})`, which visits `py_loop` (an optional `PyObject`) and calls `py_decref_and_set_null`. The extra `py_decref(l)` therefore drops a reference the future no longer owns.

Python permits `obj.__init__(...)` on an existing instance (including subclass `super().__init__` calls), so this is reachable through normal Python code.

## Trigger Scenario

```python
f = loop.create_future()
f.__init__(loop=loop)
```

Measured with `sys.getrefcount(loop)`:

```text
refcount before=4  with_future=5
re-init returned
refcount after=4        # expected 5
```

## Evidence (confirmed 2026-11-01)

Environment: Apple `container` 1.6.1, Fedora 44 aarch64, Zig 0.16.0, ReleaseFast, Python 3.13.16 and 3.13.16t.

Repro: `c2_future_reinit.py` (external review harness).

```text
loop created
refcount before=4 with_future=5
re-init returned
refcount after=4
create_future after re-init ok
call_soon after re-init ok
RESULT: FAIL (stolen loop reference)
```

The object survived the simple case because the loop has other references (including the exception-handler self-cycle), but one real owner reference is gone. A future/self-cycle teardown ordering can free the loop while another pointer still believes it has a reference.

## Proposed Remediation

Remove the extra `python_c.py_decref(l)`:

```zig
if (self.py_loop) |_| {
    _ = future_clear(self);
    self.py_loop = null;
}
```

Add a regression test that asserts `sys.getrefcount(loop)` is unchanged across `future.__init__(loop=loop)` and that the loop remains usable after the future is collected. Review the sibling `z_loop_init`/`z_task_init`/`z_handle_init`/`z_timer_handle_init` paths for the same pattern.

## Resolution (2026-11-01)

`z_future_init` now calls `future_clear(self)` only; the extra `python_c.py_decref(l)` after it was removed. `future_clear` already releases `py_loop`, so re-initializing a Future no longer steals a caller reference.

Verification: `tests/test_review_regressions.py::test_future_reinit_does_not_steal_loop_reference` asserts that `sys.getrefcount(loop)` is unchanged across `Future.__init__` and that the loop still creates futures; external repro `c2_future_reinit.py` passes on both toolchains.
