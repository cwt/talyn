# BUG-330 — glibc tcache UAF corrupts WriteTransport ArrayList header

- **Status**: 🟢 Fixed (2026-09-07)
- **Severity**: 🔴 High — Heap corruption under write pressure: garbage list headers, OutOfMemory from a healthy allocator, pre-existing flaky SIGSEGV/MemoryError in the SQ-pressure regression
- **Files**:
  - `src/transports/write_transport.zig` (`pending_buffers` / `pending_py_buffers` inlined)
  - `src/transports/stream/constructors.zig` (`stream_traverse` borrowed references removed)
  - `tests/test_connection_memory_safety.py` (removed xfail guard and MemoryError suppression)
- **Lessons**: [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md), [io_uring & Kernel](../lessons/04-io-uring-and-kernel.md)
- **Description**:
  Under the `test_writev_sq_pressure_no_double_free` pressure profile (300 transports × 20 rounds of 8×4KB `writelines` into a peer that accepts but never reads), `append_new_buffer_to_write` intermittently failed with `error.OutOfMemory` while the failing list showed:
  - `items.len` = a corrupted-pointer-shaped value (observed `0x6f785a0ba2a8dbfe` — an ~8 Exabyte length), and
  - `capacity` intact.
  An initial audit report misidentified this 16-byte write as an "iovec-shaped `{base, len}` overwrite" from `BlockingTask` slot recycling (`write_iov` / `msg_storage`).
- **Real Root Cause**:
  The 16-byte overwrite is **glibc's `tcache_entry`** structure (`{ uintptr_t next; uintptr_t key; }`).
  On glibc 2.32+:
  - `offset 0..7` (`items.ptr`): safe-linking mangled next pointer `(chunk_addr >> 12) ^ real_next`.
  - `offset 8..15` (`items.len`): 64-bit random cookie `tcache_key` generated per-thread to detect double-free (the observed `0x6f785a0ba2a8dbfe`).
  - `offset 16..23` (`capacity`): untouched by glibc, as `tcache_entry` is only 16 bytes.
  
  In `WriteTransport`, `pending_buffers` and `pending_py_buffers` were defined as heap pointers (`*BuffersArrayList` and `*PyBuffersArrayList`), allocated via `allocator.create()` as separate 24-byte heap chunks.
  When a transport was closed or cleaned up (via `stream_clear` / lifecycle unwind), or subjected to GC collection because `stream_traverse` was incorrectly visiting borrowed self-references (`parent_transport` and `exception_handler`) causing Python cycle collector reference count miscalculations, these 24-byte chunks were returned to glibc's 32-byte tcache bin.
  Subsequent access to the transport (e.g. from `writelines` during multi-transport load) read the tcache chunk's `key` as `items.len`. In `append`, `ensureTotalCapacityPrecise` saw `len = 0x6f785a0ba2a8dbfe` and immediately raised `error.OutOfMemory` (surfacing as `MemoryError`) or dereferenced the mangled `items.ptr` leading to `SIGSEGV`.
- **Fix**:
  1. Inlined `pending_buffers: BuffersArrayList = .empty` and `pending_py_buffers: PyBuffersArrayList = .empty` directly into `WriteTransport`. Because `WriteTransport` is already embedded directly in `StreamTransportObject`, this completely eliminates the separate 24-byte heap allocations and their glibc tcache free/reuse cycles.
  2. Updated `init` and `deinit` in `src/transports/write_transport.zig` to manage inlined list instances without heap allocation/destruction, resetting them to `.empty` and marking `initialized = false` and `closed = true`.
  3. Added `if (!self.initialized or self.closed) return error.TransportClosed;` guard to `append_new_buffer_to_write`.
  4. Removed borrowed references (`parent_transport` and `exception_handler`) from `stream_traverse` in `src/transports/stream/constructors.zig` so Python GC does not treat borrowed backpointers as cyclic child references.
  5. Removed `pytest.xfail` workaround and `MemoryError` suppression from `tests/test_connection_memory_safety.py`.

## Validation (2026-09-07)

- Verified empirical glibc tcache layout matching the exact 16-byte corruption signature (`tcache_key` cookie at offset 8).
- Validated with `test_writev_sq_pressure_no_double_free` passing cleanly with zero `MemoryError` and zero `SIGSEGV` exits.
