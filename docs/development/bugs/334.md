# BUG-334 — `link_timeout` stores a pointer to a dead stack frame (deferred submission arms the timeout from reclaimed memory)

- **Status**: ✅ Fixed (2026-09-25)
- **Severity**: 🔴 High — every read/write that carries an io_uring timeout is mis-armed. The failure is silent and data-dependent: a garbage `tv_sec` of realistic magnitude turns the timeout into a no-op, so the operation never completes and its `BlockingTask` slot, registered-buffer lease and transport references are never released; a garbage value `<= 0` cancels the operation instantly.
- **Files**:
  - `src/loop/scheduling/io/read.zig:40,125` (copy into `data_ptr.timer_storage` before `ring.link_timeout`)
  - `src/loop/scheduling/io/write.zig:33,102,164` (same)
  - `src/loop/main.zig:367-484` (regression test `BUG-334: link_timeout timespec must be heap-resident, not a dead stack pointer`)
- **Related**: [BUG-333](333.md) (the `IOSQE_ASYNC` fix removed the *async offload* from these very same `link_timeout` calls but left the *deferred-submission* hazard), [BUG-30](030.md) (the same rule applied to iovecs), [BUG-02](002.md) (the adjacent `link_timeout` failure-rollback path)
- **Discovered by**: Reading [BUG-333](333.md) and auditing every other `link_timeout` site for the same kernel/user-space visibility assumption.

## Symptoms & Impact

`DNS` is the only subsystem that currently sets `.timeout` on a read or write, so the observed blast radius is name resolution:

1. `queue_next_response_read` (`src/loop/dns/resolv.zig:333`) queues a `PerformRead` with the configured `dns_timeout`. If the timeout is mis-armed, the read on a dead UDP socket never expires, `process_dns_response` never runs, and the `ServerQueryData` — including the `ControlData` reference holding the user's callbacks — is never released. `getaddrinfo`/`getnameinfo` then hang until the caller gives up, and the resolver accumulates one unreleased query per attempt.
2. `on_query_sent` and `send_all_queries` (`src/loop/dns/resolv.zig:369,923`) queue `PerformWrite` with a `link_timeout`. A mis-armed timeout either aborts the send with `-ETIME` (resolution fails spuriously against a perfectly healthy resolver) or never fires.

The corruption is non-deterministic in exactly the way a use-after-free is: the value the kernel reads is whatever the next call chain happened to write over the reclaimed frame, so symptoms vary with optimisation level, stack depth and call sequence.

## Root Cause

`ring.link_timeout()` takes a `*const kernel_timespec` and stores the raw pointer in `sqe.addr`:

```zig
// std/os/linux/io_uring_sqe.zig
pub fn prep_link_timeout(sqe: *linux.io_uring_sqe, ts: *const linux.kernel_timespec, flags: u32) void {
    sqe.prep_rw(.LINK_TIMEOUT, -1, @intFromPtr(ts), 1, 0);
    sqe.rw_flags = flags;
}
```

The kernel dereferences `sqe.addr` when the SQE is *submitted*, not when it is queued. `IO.queue()` defers submission: `queue_unlocked` only flushes for cancel operations or when the SQ is near full (`src/loop/scheduling/io/main.zig:926-929`); otherwise the SQE sits in the local `sq.sqes` array until `poll_blocking_events` calls `flush_pending_sqes()` / `submit_and_wait` (`src/loop/runner.zig:293,308`).

Every `link_timeout` site derived its pointer from the by-value `data` parameter:

```zig
// WRONG — `timeout` points into this function's stack frame
pub fn perform(ring: *std.os.linux.IoUring, set: *IO.BlockingTasksSet, data: PerformData) !usize {
    const data_ptr = try set.push(.PerformRead, &data.callback);
    ...
    if (data.timeout) |*timeout| {
        sqe.flags |= std.os.linux.IOSQE_IO_LINK;
        _ = ring.link_timeout(0, timeout, 0) catch |err| { ... };
    }
```

`data` is a stack copy threaded through `queue` → `queue_unlocked` → `perform`. Once those return, the address in `sqe.addr` is dead. The three live callers make this unambiguous because their timespec is a plain named local:

- `src/loop/dns/resolv.zig:922` — `const timeout = ...` → `.PerformWrite.timeout`
- `src/loop/dns/resolv.zig:362` — `const timeout_val = ...` → `.PerformWrite.timeout`
- `src/loop/dns/resolv.zig:344` — an inline `if/else` temporary → `.PerformRead.timeout`

`Timer.wait` was already immune because it had been taught this lesson (and says so at `src/loop/scheduling/io/timer.zig:21-24`): it copies the duration into `data_ptr.timer_storage` — a field of the heap-resident `BlockingTask` inside `task_data_pool` (`src/loop/scheduling/io/main.zig:50`) — and passes that. `timer_storage` was written from `timer.zig` and nowhere else, so all five `link_timeout` sites were the sole remaining violators of the rule.

## Fix

Copy the timespec into the `BlockingTask`'s persistent `timer_storage` before building the SQE, at all five sites:

```zig
// RIGHT — heap-resident; valid until the CQE arrives
if (data.timeout) |*timeout| {
    data_ptr.timer_storage = timeout.*;
    sqe.flags |= std.os.linux.IOSQE_IO_LINK;
    _ = ring.link_timeout(0, &data_ptr.timer_storage, 0) catch |err| {
        ring.sq.sqe_tail -%= 1;
        return err;
    };
}
```

`data_ptr` is already guaranteed to outlive submission — the `sqe_tail` rollback on failure and `errdefer data_ptr.discard()` (BUG-02) keep the slot alive until the operation either completes or unwinds — so no new ownership or teardown work is needed. The existing `sqe_tail -%= 1` rollback is preserved on every path.

## Regression test

`src/loop/main.zig:367` — `BUG-334: link_timeout timespec must be heap-resident, not a dead stack pointer` exercises all five call sites (`Read.wait_ready`, `Read.perform`, `Write.wait_ready`, `Write.perform`, `Write.perform_with_iovecs`) and asserts for each that:

1. the last SQE is `IORING_OP.LINK_TIMEOUT`;
2. `sqe.addr` lies inside `set.task_data_pool` — i.e. heap-resident, never a stack address;
3. `sqe.addr == @intFromPtr(&task.timer_storage)`;
4. reading the timespec back through `sqe.addr` still yields the requested `sec`/`nsec`.

Each case then rolls the SQE back out of the submission queue and discards the task, so the test never submits to the kernel and leaves the ring, the set and `reserved_slots` pristine.

## Prevention

This is the third instance of one rule in this codebase (BUG-30 for iovecs, BUG-333 for the async offload, BUG-334 for the timeout timespec). The invariant is consolidated in [Lesson 60](../lessons/04-io-uring-and-kernel.md): *anything the kernel dereferences from an SQE must live in storage owned by the `BlockingTask`, because the kernel reads it at submit time and submission is deferred.* Any new `ring.*` call that takes a pointer must satisfy that before it ships.
