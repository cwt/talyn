# BUG-305 — Free-threaded builds skip `release_python_imports()` at module cleanup

- **Status**: 🟡 Open (documented deliberate trade-off)
- **Severity**: 🟢 Medium-Low — Refcount leak scoped to extension unload / subinterpreter restart cycles under free-threading
- **Files**:
  - `src/lib.zig:24-36` (`module_cleanup`: cleanup gated on `builtin.single_threaded`)
  - `src/utils/python_imports.zig:122-134` (`release_python_imports` — never invoked in free-threaded builds)
- **Lessons**: [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md), [Concurrency & Thread Safety](../lessons/02-concurrency-and-thread-safety.md)
- **Description**: `module_cleanup` guards ALL teardown with `if (builtin.single_threaded)`. In free-threaded mode (`!single_threaded`) neither `deinitialize_talyn_types()` nor `release_python_imports()` runs, so every entry of the ~25-slot `Atomic(?PyObject)` cache (`asyncio_module`, `sys_module`, `socket_class`, protocols, transports, exception classes, task registry functions, asyncgen hooks, AF/SOCK constants) retains its owned reference until process exit.
- **Not covered by**: BUG-106 fixed read-side thread-safety of these globals via atomics; BUG-154 fixed uninitialized storage on partial init failure. Neither addresses the skip of teardown itself.
- **Trigger**: `importlib.reload(talyn_zig)`, subinterpreter re-initialization, or repeated embed/init-shutdown cycles with a free-threaded CPython build. Single-shot standard applications reclaim everything at process exit (the code comment acknowledges this).
- **Consequences**: One full reference-set leak per load/unload cycle (~25 objects plus their transitive modules); leaked-at-exit sets are untracked by Python's allocator during shutdown diagnostics.
- **Proposed fix**: Gate cleanup scope, not existence: in free-threaded builds either (a) defer import-cache teardown to a single `PyThread_tss`-registered once-callback trusted for both modes, or (b) perform `release_python_imports()` there but leave type-object decref disabled (the segfault the comment guards against comes from type/GC machinery, not plain ref drops). Re-evaluate once 3.14t finalizes module-finalization guarantees.
- **Related rationale**: see inline comment at `src/lib.zig:25-27`.
