# BUG-309 — Premature decref and use-after-free on custom socket create_connection

- **Status**: 🔴 Open (2026-09-07)
- **Severity**: 🔴 Critical — Python C-API refcount underflow and use-after-free on protocol factory callback
- **Files**:
  - `src/loop/python/io/client/create_connection.zig` (`z_loop_create_connection`: lines 176–177; `create_transport_and_set_future_result`: line 913)
- **Lessons**: [Python C-API Correctness](../lessons/05-python-c-api-correctness.md), [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md)
- **Description**:
In `z_loop_create_connection` on the pre-existing socket path:
```zig
transport_creation_data.protocol_factory = protocol_factory; // BORROWED
```
Later, when connection succeeds and dispatches `create_transport_and_set_future_result`:
```zig
defer python_c.py_decref(transport_creation_data.protocol_factory);
```
The cleanup defer unconditionally decrefs `protocol_factory`. Because `z_loop_create_connection` never acquired an owned reference via `python_c.py_newref(protocol_factory)`, this decref drops the caller's reference count. When the caller's scope exits or garbage collection runs, `protocol_factory` is prematurely deallocated while still in use.
- **Root Cause**: Asymmetric ownership: borrowed reference stored during setup but owned reference decremented during transport creation cleanup.
- **Trigger Scenario**: Invoking `loop.create_connection(protocol_factory, sock=pre_existing_socket)`.
- **Proposed Remediation**: Acquire an owned reference in line 176: `transport_creation_data.protocol_factory = python_c.py_newref(protocol_factory);`.
