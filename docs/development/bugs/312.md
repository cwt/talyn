# BUG-312 — Leaked future reference on create_connection dispatch failure

- **Status**: 🟢 Fixed (2026-09-07, together with BUG-309)
- **Severity**: 🔴 High — Leaked Future reference on Soon.dispatch failure in create_connection(sock=...)
- **Files**:
  - `src/loop/python/io/client/create_connection.zig` (`z_loop_create_connection`: lines 178–199)
- **Lessons**: [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md), [Python C-API Correctness](../lessons/05-python-c-api-correctness.md)
- **Description**:
In `z_loop_create_connection` handling `sock`:
```zig
transport_creation_data.future = python_c.py_newref(fut);
...
errdefer python_c.py_decref(@ptrCast(self));
try Loop.Scheduling.Soon.dispatch(
    ...
);
```
If `Loop.Scheduling.Soon.dispatch` returns an error, the `errdefer` decrefs `@ptrCast(self)`, but `transport_creation_data.future` is not decref'd. The reference acquired via `py_newref(fut)` is permanently leaked.
- **Root Cause**: Missing decref of `transport_creation_data.future` on the dispatch failure path.
- **Trigger Scenario**: Calling `loop.create_connection(..., sock=s)` when the loop's `Soon` callback ring buffer is full or allocation fails.
- **Proposed Remediation**: Add `python_c.py_decref(transport_creation_data.future);` to the `errdefer` block before returning.

- **Fix (Applied — 2026-09-07)**:
  - `z_loop_create_connection` sock path (`src/loop/python/io/client/create_connection.zig`): the `TransportCreationData` init now carries a full cleanup `errdefer` releasing `protocol_factory`, `loop`, and `future` when `Soon.dispatch` fails — previously only the loop object and the struct itself were released, leaking the `py_newref`'d future (and, after the BUG-309 fix, the owned protocol_factory) forever.
  - Grouped with BUG-309: identical errdefer gap, same 30-line span, and the BUG-309 owned-reference change makes the release of all three fields mandatory on this path.
  - Covered by the same regression tests as BUG-309 (leak paths are not Python-triggerable — Soon ring exhaustion — the differential refcount test guards the success path; the errdefer is verified by construction).
- **Validation (2026-09-07)**: Confirmed still present.
  - `transport_creation_data.future` takes `py_newref(fut)` (`src/loop/python/io/client/create_connection.zig:178`) and `.loop` takes `py_newref(self)` (`:179`); on `Soon.dispatch` failure (`:198`) the errdefers (`:191` decref loop object, `:174` destroy struct, `:149` decref fut) never release the `future`/`loop` references → both leak.
  - This is the same errdefer-gap class as BUG-310 on the `create_connection(sock=...)` path.
