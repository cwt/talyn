# BUG-306 — `link()` loses one signal occurrence if it arrives before the mask blocks it

- **Status**: 🟢 Fixed (2026-08-27)
- **Severity**: 🟢 Medium-Low — Single-event loss through a narrow setup window; worst case was a lost Ctrl+C (SIGINT) once per `add_signal_handler` call
- **Files**:
  - `src/loop/unix_signals.zig` (`link()`: block→handler→siginterrupt→signalfd→enqueue; `unlink()`: signalfd re-mask→default handler→unblock-last)
  - Distinct from fixed BUG-57 (`unlink()` failing to restore default disposition/mask)
- **Lessons**: [Concurrency & Thread Safety](../lessons/02-concurrency-and-thread-safety.md), [Defensive Programming](../lessons/10-defensive-programming-and-code-quality.md)
- **Description**: POSIX delivery semantics require the disposition to exist BEFORE the signal is blocked; otherwise a signal raised by an unblocked thread between handler installation and `sigprocmask(SIG_BLOCK)` executes the just-installed no-op `dummy_signal_handler` and disappears. The event neither raised Python's KeyboardInterrupt nor landed on the signalfd. For SIGINT specifically, Python owned the disposition prior to talyn linking, so pre-link behavior was working — making the silent drop user-visible rather than theoretical.
- **Fix (Applied — 2026-08-27)**:
  - `link()` reordered to: add-to-mask + `sigprocmask(SIG.BLOCK)` FIRST → install dummy handler → `siginterrupt(...)` (must follow the install; glibc patches the currently-installed action) → `signalfd()` re-mask → enqueue read. With block-first, any occurrence arriving during setup becomes a PENDING signal that signalfd reports once its mask covers it — nothing can slip through between setup steps.
  - `unlink()` reordered to drop the signal from the signalfd mask and restore the default disposition BEFORE `sigprocmask(SIG.UNBLOCK)` runs last, eliminating the reverse window where an arriving signal hit the still-installed no-op dummy after already leaving signalfd coverage.
  - Error-path note: if `signalfd()` re-masking fails mid-transition, the partial state matches the pre-fix failure shape (signal blocked + dummy installed); unchanged class of behavior, now confined to the true error path instead of the happy path.
- **Regression tests**:
  - Zig canary `loop.unix_signals.test."BUG-306: link blocks before dummy handler; unlink disarms before unblocking"` (`src/loop/unix_signals.zig`) — structural guard asserting via this module's own embedded source that in `link()` the `SIG.BLOCK` step precedes the dummy-handler install, and in `unlink()` both the signalfd re-mask and default-handler restore precede `SIG.UNBLOCK`. Fails at build time on any reintroduced ordering swap (deterministic complement to a race that cannot be triggered reliably from user space, mirroring the precedent set by BUG-289's structural regression).
  - `tests/loop/test_loop_unix_signals.py::test_bug306_no_signal_loss_across_register_send_deliver_cycles` — single-session churn driver over 9 add→kill→deliver cycles (every third also remove→send-silent→assert-zero-delta→re-register), proving losslessness and correct disarm semantics under repeated relink windows on every variant build.
  - `tests/loop/test_loop_unix_signals.py::test_bug306_kill_immediately_after_add_is_never_lost` — tightest external approximation of the link-window race: kill issued synchronously right after `add_signal_handler` returns across 5 fresh loops, asserting exactly-one delivery and unblocked pipeline afterwards.
- **Validation**: `zig fmt` clean; `zig build lint` 0 violations (104 Zig files); full suite green via `scripts/test_all.sh --starburst --verbose` on python3.13, 3.14, 3.13t, 3.14t (341 passed / variant + all stdlib asyncio suites) plus All 62 zig unit tests.
