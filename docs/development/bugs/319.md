# BUG-319 — Inotify event buffer over-read & permanent watcher disarm on callback error

- **Status**: 🟢 Fixed (2026-09-07)
- **Severity**: 🟡 Medium — Buffer over-read and permanent filesystem watcher stall on event dispatch error
- **Files**:
  - `src/loop/fs_watcher.zig` (`on_inotify_event`: lines 80–122)
- **Lessons**: [io_uring & Kernel](../lessons/04-io-uring-and-kernel.md), [Defensive Programming](../lessons/10-defensive-programming-and-code-quality.md)
- **Description**:
In `on_inotify_event`:
1. Buffer Over-read:
```zig
while (pos < n) {
    const event: *const std.os.linux.inotify_event = @ptrCast(@alignCast(&self.read_buf[pos]));
    pos += @sizeOf(std.os.linux.inotify_event) + event.len;
    ...
    const name = self.read_buf[name_start..pos];
```
If a read returns a partial event where `pos + @sizeOf(...) + event.len > n`, `pos` exceeds `n`, slicing uninitialized or stale buffer memory.

2. Permanent Watcher Disarm:
```zig
try self.dispatch_event(watch, event.mask, name);
```
Line 102 uses `try`. If Python callback execution returns `error.PythonError`, the function returns immediately. It bypasses lines 114–122 (`self.loop.ring.read(...)`), so the reader SQE is never re-queued, permanently disabling the inotify watcher.
- **Root Cause**: Missing buffer slice bounds check and premature return with `try` prior to io_uring re-arming.
- **Trigger Scenario**: Partial inotify event delivery or Python exception inside a filesystem watch callback.
- **Proposed Remediation**: Validate `pos + @sizeOf(...) + event.len <= n` before indexing, and catch errors from `self.dispatch_event` so `ring.read` always re-arms.

- **Validation (2026-09-07)**: Confirmed still present, with one precision note.
  - Over-read: `src/loop/fs_watcher.zig:80-110` — no `pos + @sizeOf(inotify_event) + event.len <= n` bounds check; the name slice at `fs_watcher.zig:83` and the `pos` advance at `:109` trust `event.len` unconditionally.
  - Disarm: `fs_watcher.zig:105` `try self.dispatch_event(...)` returns before the re-arm at `:114-121`, permanently disabling the inotify watcher.
  - Precision: Python callback exceptions do NOT propagate — `dispatch_event` (`fs_watcher.zig:124-153`) routes them to `call_exception_handler` internally. The errors escaping the `try` are Python C-API allocation failures (e.g. `PyLong_FromUnsignedLong`, `PyTuple_Pack` returning null). The structural hazard is unchanged.

- **Fix (Applied — 2026-09-07)**:
  - `on_inotify_event` (`src/loop/fs_watcher.zig`): the event loop now bounds-checks before touching an event — a truncated header (`remaining < @sizeOf(inotify_event)`) or an event spanning past the read (`total > remaining`) logs a warning and stops parsing the buffer instead of slicing past the valid bytes.
  - `try self.dispatch_event(...)` became a `catch` that warns and continues: the read pass always completes and the re-arm at the end of the function always runs, so a dispatch failure can no longer permanently disarm the watcher. (The errors escaping here are Python C-API allocation failures — Python callback exceptions are already routed to `call_exception_handler` inside `dispatch_event`.)
  - Neither the truncated-buffer nor the allocation-failure condition is deterministically triggerable from Python (the kernel never delivers partial inotify events; allocation failure needs memory pressure) — the fix is structural.
- **Regression test**: `tests/test_fs.py::test_fs_watcher_survives_raising_callback` — a callback that raises on the first event must not disarm the watcher; a second filesystem event must still be delivered (guards the re-arm contract at the Python-observable level).
