# BUG-268 — Default-factory tasks invisible to `asyncio.all_tasks()`

- **Status**: 🟠 Open (confirmed real — 2026-08-21)
- **Validation**: 2026-08-21 — CONFIRMED REAL. Verified empirically: under talyn, `loop.create_task(...)` with no factory creates `talyn.Task` and `asyncio.all_tasks()` returns an **empty set** — the task is missing from both the C registry (used by `_c_all_tasks`) and the pure-Python `_scheduled_tasks` WeakSet (used by `_py_all_tasks`). `utils.PythonImports.register_task_func` (imported from `asyncio.tasks._register_task`) is never called anywhere. Exposed by the new Python 3.14.7 stdlib test `test_all_tasks_from_other_thread_includes_eager_tasks` (gh-152020), which asserts that a factory-None task created on a background-thread loop is visible in `all_tasks()`; it sees the factory-created eager task but not the default-factory task. Pre-existing; previously masked because no stdlib test exercised the default-factory path across threads (BUG-267 was the first blocker for that test).
- **Severity**: Medium-High — Broken task introspection / leak risk (Runner can't cancel leftover tasks it can't see)
- **Files**:
  - `src/loop/python/utils/task.zig:85` (`z_loop_create_task` default path → `Task.Constructors.fast_new_task`)
  - `src/utils/python_imports.zig:30,72` (`register_task_func` imported but unused)
- **Lessons**: [Python C API Correctness](../lessons/05-python-c-api-correctness.md), [Task & Coroutine Execution](../lessons/02-task-and-coroutine-execution.md)

## Description

CPython registers every task in the asyncio task registry so `asyncio.all_tasks()`, `Runner` shutdown (`_cancel_all_tasks`), and introspection work. In 3.14 the registry is dual: the C `_asyncio._register_task(task)` registry (default `all_tasks`) and the pure-Python `_scheduled_tasks` WeakSet (`_py_all_tasks`, used when `_asyncio` is absent or by tests that explicitly switch back). Talyn's `z_loop_create_task` with `task_factory == null` creates its own `PythonTaskObject` and never calls either registry:

```zig
const task = try Task.Constructors.fast_new_task(self, coro, context.?, name);
return task;   // never registered
```

Tasks created through a user `task_factory` are unaffected (the factory-created stdlib Task registers itself), which is why the eager task in the stdlib test appears while the default-factory task does not.

## Trigger

```python
async def main():
    t = asyncio.get_running_loop().create_task(asyncio.sleep(10))
    assert t in asyncio.all_tasks()   # FAILS under talyn
```

## Consequences

- `asyncio.all_tasks()`/`current_task()`-adjacent bookkeeping misses all default-factory tasks (misreported state, broken debugging, `TaskGroup` introspection gaps).
- `asyncio.Runner` cannot cancel leftover tasks it cannot see → orphaned tasks at loop shutdown.
- 4 failures in `test.test_asyncio.test_free_threading` (`test_all_tasks_from_other_thread_includes_eager_tasks` across Py/C × normal/eager classes).

## Fix (In Progress)

Register talyn tasks at creation and unregister at completion:

- After `fast_new_task`, call both registries when available: `asyncio.tasks._py_register_task(task)` (WeakSet) and `asyncio.tasks._c_register_task(task)` (C registry) — covering both `all_tasks` variants; the unused `register_task_func` import is wired up.
- Unregister (`_py_unregister_task` / `_c_unregister_task`) when the task completes (done-callback finalization path) and on dealloc, mirroring CPython's `_unregister_task` behavior.
