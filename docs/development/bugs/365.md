# BUG-365 — Allocator mismatch in `DNS.lookup` (freed via `DNS.arena` in `Cache.evict_record`) and unbounded `DNS.arena` memory growth across cache evictions and `ControlData` lifecycles

- **Status**: ✅ Fixed
- **Severity**: 🔴 High — leaks GPA-allocated `Address` slices on every IP-literal cache eviction/update, leaks `DNS.arena` if `DNS.init` fails, and causes unbounded memory growth in `DNS.arena` for every DNS query performed over the life of the loop
- **Category**: Memory Leak / Allocator Mismatch
- **Files**:
  - `src/loop/dns/main.zig:40-50, 115-119`
  - `src/loop/dns/cache.zig:25-27, 47-55, 67-79`
  - `src/loop/dns/resolv.zig:215-225, 812-823`
- **Related**: [Lesson 28](../lessons/02-zig-and-memory.md)

## Overview & Root Cause

1. **Allocator mismatch between `DNS.lookup` (`self.loop.allocator`) and `Cache.evict_record` (`self.dns.arena.allocator()`)**:
   In `src/loop/dns/main.zig:115-119`, when `DNS.lookup` parses an IPv4 or IPv6 literal, it allocates a 1-element `[]Address` slice using `self.loop.allocator` (the loop's general-purpose allocator) and inserts it into `self.cache`:

   ```zig
   const slice = try self.loop.allocator.alloc(Address, 1);
   slice[0] = addr;
   try self.cache.new_record(hostname, .{
       .resolved = slice,
   });
   ```

   However, in `src/loop/dns/cache.zig:47-55, 67-79`, `Cache.update_record` and `Cache.evict_record` free `.resolved` slices using `self.dns.arena.allocator()`!

   ```zig
   fn evict_record(self: *Cache, hostname: []const u8, record: *Record) void {
       const allocator = self.dns.arena.allocator();
       switch (record.state) {
           .resolved => |addrs| allocator.free(addrs),
           ...
       }
       allocator.free(hostname);
   }
   ```

   Calling `ArenaAllocator.allocator().free(addrs)` on a slice allocated by `self.loop.allocator` does **not** return the memory to `self.loop.allocator` — it is a complete no-op in `ArenaAllocator.free`, permanently leaking `slice` from `self.loop.allocator`!

2. **Unbounded `DNS.arena` growth across `ControlData` lifecycles and `Cache` evictions (`src/loop/dns/resolv.zig:812-823` & `src/loop/dns/cache.zig`)**:
   `DNS.arena` (`std.heap.ArenaAllocator`) is never reset until `DNS.deinit()` (`loop.close()`).
   - Every async DNS query in `Resolv.prepare_data` (`src/loop/dns/resolv.zig:812`) uses `const allocator = loop.dns.arena.allocator();` to allocate `user_callbacks`, `hostnames_array`, `servers`, `queries_buffer`, `query_lengths`, `transaction_ids`, `recv_buf` (512 bytes per server), and `addr_storage`, and then calls `allocator.free(...)` in `ControlData.release()` / `ServerData.release()`.
   - Likewise, `Cache` allocates `hostname` keys, `Record` values, `LRUCache` hash map storage, and `Address` slices from `self.dns.arena.allocator()` and calls `allocator.free(...)` on cache eviction/expiry.
   - Because `std.heap.ArenaAllocator.free` only reclaims the **most recently allocated** object at the very tip of the current bump buffer and is a no-op for everything else, all per-query `ControlData`/`ServerData` buffers and evicted cache entries accumulate indefinitely in `DNS.arena` for the entire lifetime of the event loop!

3. **Missing `errdefer self.arena.deinit()` in `DNS.init` (`src/loop/dns/main.zig:40-50`)**:
   In `DNS.init`, `self.arena = std.heap.ArenaAllocator.init(allocator)` is initialized at line 41 without `errdefer self.arena.deinit();`. If `parse_resolv_conf` (line 45), `parse_hosts` (line 46), or `self.cache.init()` (line 49) fails, all allocations made in `self.arena` are leaked.

## Trigger Scenario

1. Call `await loop.getaddrinfo("127.0.0.1", 80)` followed by >1024 distinct hostnames (or wait 60s for the TTL to expire) -> `Cache.evict_record` calls `self.dns.arena.allocator().free(addrs)` on the GPA-allocated `slice`, leaking `slice`.
2. Perform thousands of async DNS lookups in a long-running server -> `DNS.arena` grows without bound because `ControlData`/`ServerData` buffers cannot be reclaimed out-of-order by `ArenaAllocator.free`.

## Proposed Remediation

1. Use `self.loop.allocator` (GPA) instead of `self.dns.arena.allocator()` for dynamic, short-lived allocations (`ControlData`, `ServerData`, `Cache` records, and `DNS.lookup` slices), reserving `self.arena` strictly for loop-lifetime configuration data (`/etc/resolv.conf` and `/etc/hosts`) — or remove `DNS.arena` altogether and free `/etc/resolv.conf` and `/etc/hosts` entries in `DNS.deinit()`.
2. Add `errdefer self.arena.deinit();` in `DNS.init`.


## Resolution (2026-10-18)

The allocator architecture had drifted since the report (everything in
`Cache` and the `ControlData` lifecycle now flows through
`cache_slot.allocator`, which pointed at the DNS arena), so the fixes
land on the *wiring*:

1. **Allocator mismatch (fixed)**: `DNS.lookup` seeded IP-literal cache
   records with `self.loop.allocator.dupe(...)` slices (GPA) while
   `Cache.evict_record` freed `.resolved` slices via the DNS arena's
   allocator — `ArenaAllocator.free` is a no-op for foreign pointers, so
   every literal entry's slice leaked from the GPA on
   eviction/update. The seed now dupes from `cache_slot.allocator`, the
   same allocator the cache evicts with; allocation and final free are
   balanced.

2. **Unbounded arena growth (fixed by the remediation's option 1)**: the
   cache records — hostname keys, `Record` structs, resolved Address
   slices, per-slot LRU hash-map storage — and every `ControlData` /
   `ServerQueryData` allocation (they inherit `cache_slot.allocator` in
   `prepare_data`) now live on the loop's general-purpose allocator,
   where evictions and control-data releases perform real frees. The
   DNS arena is reserved for loop-lifetime configuration data
   (`/etc/resolv.conf` parse output, loaded once at init). `DNS.deinit`
   now drains every cache entry (the LRUs' evict callbacks free the
   GPA-owned hostnames/records/slices) BEFORE releasing pending queries
   and deiniting the arena — pending-first would have written
   `record_evicted` into already-destroyed ControlDatas.

3. **Missing `errdefer` in `DNS.init` (fixed)**: `errdefer
   self.arena.deinit()` added right after the arena is created.

## Bonus defect found while fixing (same commit)

`utils.LRUCache.evict_last()` and `put()`'s overwrite branch fired the
evict callback BEFORE removing the map entry — and the only key-owning
callback (the DNS cache's) frees the key. The previous order hashed
freed key bytes for `map.remove`, stranding the entry in the string map;
the real GPA free (vs. the arena's no-op free) turned the latent
time-bomb into a hard crash on the next rehash
(`putAssumeCapacityNoClobberContext` assert). Both sites now detach the
entry and the node before invoking the callback; `put` falls through to
the fresh-insert path so BUG-40's overwrite semantics (old value's
evict callback, new value cached) are preserved.
