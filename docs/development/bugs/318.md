# BUG-318 — Uninitialized stack memory read in IPv4 address parser

- **Status**: 🟢 Fixed (2026-09-07)
- **Severity**: 🟡 Medium — Uninitialized stack memory read when parsing malformed IPv4 host strings in create_server
- **Files**:
  - `src/loop/python/io/server/create_server.zig` (`z_loop_create_server`: lines 160–168)
- **Lessons**: [Security & Input Validation](../lessons/09-security-and-input-validation.md), [Zig Specific Patterns](../lessons/08-zig-specific-patterns.md)
- **Description**:
In `z_loop_create_server`:
```zig
var ip_bytes: [4]u8 = undefined;
var ip_parts = std.mem.splitScalar(u8, host_slice, '.');
var idx: usize = 0;
while (ip_parts.next()) |part| : (idx += 1) {
    if (idx >= 4) break;
    ip_bytes[idx] = std.fmt.parseInt(u8, part, 10) catch 0;
}
addr = utils.Address.initIp4(ip_bytes, @intCast(port));
```
If `host_slice` has fewer than 4 dot-separated parts (e.g. `"127.1"` or malformed user input), the loop finishes with `idx < 4`. The remaining elements of `ip_bytes` remain uninitialized stack garbage (`undefined`), resulting in non-deterministic address binding.
- **Root Cause**: Array declared `undefined` and populated by variable-length split without validating element count.
- **Trigger Scenario**: Calling `loop.create_server(..., host='10.0.1')` with non-standard dotted IP strings.
- **Proposed Remediation**: Zero-initialize `ip_bytes: [4]u8 = [_]u8{0} ** 4;` and verify `idx == 4` before calling `initIp4`.

- **Validation (2026-09-07)**: Confirmed still present, with one detail drift.
  - `z_loop_create_server` (`src/loop/python/io/server/create_server.zig:160-168`): `ip_bytes: [4]u8 = undefined` with no `idx == 4` validation — a host with fewer than 4 dot-separated parts leaves the tail bytes uninitialized before `utils.Address.initIp4`, exactly the hazard described.
  - Drift: the loop now uses `try std.fmt.parseInt(u8, part, 10)` instead of the quoted `catch 0`, so malformed (non-numeric) parts propagate an error; short-but-numeric hosts (e.g. `"127.1"`) still trigger the uninitialized-stack read.

- **Fix (Applied — 2026-09-07)**:
  - `z_loop_create_server` (`src/loop/python/io/server/create_server.zig`): the IPv4 parse loop now tracks a `malformed` flag and validates `i == 4` before `initIp4` — short dotted-quads (`"127.1"`, `"10.0.1"`), empty strings, non-numeric parts, and >4-octet strings all raise `error.InvalidAddress` instead of binding a non-deterministic address (previously short-but-numeric hosts left `ip_bytes[i..4]` holding uninitialized stack bytes; malformed parts propagated a generic parse error).
  - Grouped in the same commit: **BUG-327** — the first-ever `create_server(sock=...)` error-path exercise (this fix's test) exposed a pre-existing double-decref between the stack `creation_data` errdefer and the heap copy's deinit (abort inside `PyObject_GC_Del`); fixed by transferring ownership to the heap copy. See [BUG-327](327.md).
- **Regression test**: `tests/test_create_server.py::test_create_server_sock_malformed_ipv4_rejected` — a `FakeSock` whose `getsockname()` returns malformed hosts (`"127.1"`, `"10.0.1"`, `"1"`, `"1.2.3.4.5"`, `"a.b.c.d"`, `""`) must raise for every case. On the unfixed code the numeric short hosts bound a garbage address (no error) and the error unwind aborted (BUG-327).
