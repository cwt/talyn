# BUG-232 — `pidfd_exit_callback` accesses uninitialized `siginfo_t` on non-EINTR `waitid` error

- **Status**: ✅ Fixed
- **Severity**: 🟠 Medium-High — Undefined behavior / crash
- **File**: `src/transports/subprocess/transport.zig:~200-230` (pidfd_exit_callback)
- **Lessons**: [io_uring §Lesson 109 — Undefined Behavior Optimization on Syscall Integer Casts](../lessons/04-io-uring-and-kernel.md), [Defensive §Lesson 79 — Silent Failure](../lessons/10-defensive-programming-and-code-quality.md)
- **Description**: In `pidfd_exit_callback`, `waitid` is called in a loop that only handles `EINTR`:

  ```zig
  var siginfo: std.os.linux.siginfo_t = undefined;
  const res = res: {
      while (true) {
          const r = std.os.linux.waitid(.PIDFD, transport.pidfd, &siginfo, ...);
          if (r != 0) {
              const errno: u32 = @truncate(~r + 1);
              if (errno == @intFromEnum(std.os.linux.E.INTR)) continue;
          }
          break :res r;
      }
  };
  ```

  If `waitid` returns any error other than `EINTR` (e.g., `ECHILD` when the process has already been reaped, `EBADF` on invalid pidfd, `EFAULT` on bad pointer), the code falls through to the `if (res != 0)` block. At that point, `siginfo` is **undefined** (never populated by the failed syscall). The subsequent code at line ~235 reads `siginfo.code`:

  ```zig
  const rc: i32 = switch (siginfo.code) { ... }
  ```

  This is reading uninitialized stack memory — undefined behavior. In Debug builds Zig fills with `0xaa`; in Release builds it reads whatever happened to be on the stack.

- **Trigger**: Race condition where the child process is reaped by another handler before `waitid` runs, or pidfd becomes invalid.
- **Consequences**: Uninitialized memory read → unpredictable process exit code → wrong `returncode` set on transport → potential crash.
- **Fix**: Initialize `siginfo` to zeros, or better: return an error immediately on non-EINTR `waitid` failures instead of falling through to the success path. Add an explicit `else => return error.SystemResources` in the error handling block.
