# BUG-412 — use-after-free when `task_ids.append` fails after queueing a connect

- **Status**: 🔴 Open (confirmed, unfixed)
- **Severity**: 🔴 Critical — use-after-free in the connect completion path on OOM
- **Category**: io_uring Ownership / Error Paths
- **Files**:
  - `src/loop/python/io/client/create_connection.zig:631-653` — queue then append
  - `src/loop/python/io/client/create_connection.zig:921-939` — completion dereferences `socket_data`
  - `src/loop/python/io/client/create_connection.zig:748-770` — `mcs.pending`/abort teardown
- **Related**: [BUG-118](118.md) (double-free in the same helper), [BUG-359](359.md)

## Overview

```zig
errdefer allocator.destroy(socket_data);

const task_id = create_socket_and_submit_connect_req(address, socket_data, loop) catch |err| return err;
// ^ the SocketConnect SQE is now queued with user_data = socket_data

try mcs.task_ids.append(allocator, task_id);   // may fail
mcs.pending += 1;
```

If `append` fails, `socket_data` is destroyed by the errdefer, and `mcs.pending` is still 0. `z_create_socket_connection`'s errdefer sees `pending == 0` and calls `mcs.deinit()`, freeing `MultiConnectState` and `SocketConnectionData` as well. The SQE was already queued, so `socket_connected_callback` later runs with `socket_data` pointing into freed memory and calls `removeTaskId(mcs, completed_id)` on a freed `mcs`.

## Trigger Scenario and Evidence (confirmed 2026-11-01)

Environment: Apple `container` 1.6.1, Fedora 44 aarch64, Zig 0.16.0, ReleaseFast, Python 3.13.16.

Harness: `LD_PRELOAD=libmalloc_fail.so` fails the n-th heap allocation; `MALLOC_PERTURB_=165` poisons freed memory. With `n=9`, the failing allocation is `mcs.task_ids.append`.

Repro: `c3_connect_append_oom.py 9`.

```text
gdb: SIGSEGV in socket_connected_callback at create_connection.zig:931
     removeTaskId(mcs, completed_id);
```

Every other n either returns a clean MemoryError or succeeds; n=9 crashes deterministically. The callback also does `mcs.pending -= 1` on a zero counter if `mcs` were still alive, causing usize underflow.

## Proposed Remediation

Do not let the queue and the bookkeeping diverge:

1. Reserve capacity / append the task id **before** queueing the SQE.
2. Or, if append fails after queueing, mark the round aborted and keep `socket_data`/`mcs` alive until the completion returns; cancel the SQE and let the completion perform the final teardown.
3. On append failure, increment `pending` before returning the error so the errdefer does not free an mcs that the SQE still references.

Add a fault-injection test that fails this exact allocation and runs the loop long enough for the connect CQE to arrive.
