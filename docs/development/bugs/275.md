# BUG-275 — WriteTransport resurrects cancelled writes after `force_close`

- **Status**: 🔵 Open (2026-08-23)
- **Severity**: 🟠 High — Use-after-close / cross-connection data corruption
- **Files**:
  - `src/transports/write_transport.zig:111-124` (`force_close`: closes fd via `maybe_close_fd`, queues `.Cancel`)
  - `src/transports/write_transport.zig:237-240` (`if (data.cancelled())` — only true for shutdown cancel_all)
  - `src/transports/write_transport.zig:268` (`io_uring_err != .SUCCESS and != .CANCELED` — CANCELED falls through)
  - `src/transports/write_transport.zig:292-295` (`submit_next_chunk()` resubmit — no `closed`/`is_closing` guard)
  - `src/transports/stream/read.zig:83` (read side correctly gates on `!is_closing` — asymmetry)
- **Lessons**: [Network Protocols & I/O §Lesson 45](../lessons/06-network-protocols-and-io.md), [io_uring & Kernel Interaction §Lesson 48](../lessons/04-io-uring-and-kernel.md)
- **Description**: Per-op cancels deliver `err == .CANCELED` with the CallbackData `cancelled()` bit clear. After `force_close`, `cancel_and_close_fd` has closed the fd and unregistered the fixed-file slot, but `WriteTransport.fd`/`.fixed_file_index` are never invalidated; the completion handler then resubmits the remaining buffer via `IOSQE_FIXED_FILE` against a table entry that is reset to -1 or re-leased by a new connection.
- **Trigger**: `transport.abort()`/`force_close` while a vectored/plain write is in flight and buffered data remains.
- **Consequences**: EBADF at best; writing into another connection's socket at worst.
- **Fix (Proposed)**: Guard the :293 resubmission (and `flush_buffered_writes`) with `!self.closed`, mirroring the read path.
