# BUG-400 — `loop_clear` holds the loop mutex across `Loop.release()`

- **Status**: 🟢 Fixed (2026-11-01)
- **Severity**: 🔴 Critical — deterministic deadlock during GC/deallocation under free-threading
- **Category**: Event Loop Lifecycle / Locking
- **Files**:
  - `src/loop/python/constructors.zig:52-59` — `loop_clear` locks and calls `release()`
  - `src/loop/main.zig:128-180` — `release()` and `release_claimed()`
  - `src/loop/fs_watcher.zig:28-31` — `deinit()` calls `IO.queue()`
  - `src/loop/child_watcher.zig:54-55` — `deinit()` calls `IO.queue()`
- **Related**: [BUG-348](348.md) (same self-deadlock in `loop_close`, fixed there only)

## Overview

`loop_clear` is the `tp_clear`/dealloc teardown path:

```zig
if (loop_data.initialized) {
    const mutex = &loop_data.mutex;
    mutex.lock();
    defer mutex.unlock();
    loop_data.release();          // teardown with the lock held
}
```

`release()` delegates to `release_claimed()`, which calls `fs_watcher.deinit()` and `child_watcher.deinit()`. Both deinit functions call `self.loop.io.queue(...)` when a task is still armed; `IO.queue` acquires the same non-recursive `lock.Mutex` (`SpinMutex` when `!builtin.single_threaded`). The loop is already held by `loop_clear`, so the thread spins forever.

`docs/development/bugs/348.md:100` documents that holding this mutex across `release()` "self-deadlocked 100% reproducibly under free-threading"; the fix was applied only to `loop_close`, not to the GC/dealloc path.

## Trigger Scenario

1. Run on a free-threaded Python build (`python3.13t` / `python3.14t`).
2. Create a loop and an FS watcher (or a child handler).
3. Drop the watcher handle and the loop, then run `gc.collect()` (or let the loop be deallocated).

With an FS watcher, `PathWatcherHandle.tp_clear` only decrefs `loop`/`callback`; it does not remove the inotify watch. `fs_watcher.inotify_task_id` therefore remains non-zero and `deinit()` tries to queue a `CancelIO` while `loop_clear` holds the lock.

## Evidence (confirmed 2026-11-01)

Environment: Apple `container` 1.6.1, Fedora 44 aarch64, Zig 0.16.0, Python 3.13.16t, ReleaseFast.

- GIL build (`python3.13`): `RESULT: SURVIVED (no deadlock)` (`DummyLock`).
- Free-threaded build (`python3.13t`): process hung and was killed after 40 s.
- `ChildWatcher` variant (`add_child_handler(os.getpid(), ...)` then drop the loop) also hung and was killed after 40 s.
- gdb backtrace while hung:

## Proposed Remediation

Mirror `loop_close`:

1. Under `loop_data.mutex`, validate `initialized` and claim teardown (`initialized = false`).
2. Release the mutex.
3. Call `release_claimed()` without the lock held.

Also make `FSWatcher.deinit`/`ChildWatcher.deinit` use the already-unlocked variant they need, or document/assert that `release_claimed` is only entered without the lock. Add a regression test that drops an FS watcher and a child handler, then forces GC under `python3.13t`.

## Resolution (2026-11-01)

`loop_clear` now claims teardown the same way `loop_close` does: under `loop_data.mutex` it checks `running`, sets `initialized = false`, unlocks, and only then calls `release_claimed()`. The teardown no longer runs with the non-recursive lock held, so `FSWatcher.deinit`/`ChildWatcher.deinit` can queue their `CancelIO` operations.

Verification:
- New regression `tests/test_review_regressions.py::test_loop_clear_with_armed_fs_watcher_does_not_deadlock`.
- Original repros (`c1_loop_clear_deadlock.py`, `c1a_child_watcher_deadlock.py`) print `SURVIVED (no deadlock)` under Python 3.13.16t with Zig 0.16.0 and 0.17.0, ReleaseFast.
- GIL builds and the loop/watcher test subsets remain green.
