# BUG-418 — chained `run_in_executor` round-trips 2.4× stdloop; pipelined batches parity-fast

- **Status**: 🟡 Open
- **Severity**: ⚪ Low — off-the-critical-path for most consumers (pyflakes-style reporter runs debounced in a worker); visible only in executor-latency-sensitive patterns (rapid one-shot executor hops per event)
- **Category**: Latency / executor-completion drive integration
- **Files**: executor completion/wake (`src/loop/runner.zig`, executor plumbing in `src/loop/scheduling/`)
- **Related**: [BUG-417](417.md) (reader-wake ~100 µs tick — same symptom family, likely one root cause), [BUG-410](410.md) (fine: the 10 ms idle nanosleep is fixed; this bug is its ≈100 µs cousin in the executor path)

## Symptom (isolated via three probes)

Metrics on identical workloads, medians of interleaved rounds (Python 3.15.2, talyn 0.11.4, uvloop 0.23.0):

| Probe | stdloop | uvloop | talyn |
|---|---:|---:|---:|
| `call_soon` (µs/op) | 0.95 | 0.39 | **0.30** |
| `call_soon_threadsafe` hop (µs) | 2.4 | 0.9 | **0.38** |
| executor **pipelined batch** (ms/op) | 0.028 | 0.029 | 0.029 (parity ✅) |
| executor **chained** hand-off (ms/hop) | 0.032 | 0.023 | **0.077 (2.4×)** ⚠️ |

Diagnosis by elimination:

- The pure thread→loop hop (`call_soon_threadsafe`) is talyn's *fastest* relative metric (0.16× std) → **not** a cross-thread wake problem in the callback scheduling path.
- Pipelined batches (all submitted upfront, awaited as a group) are parity-fast → submission/scheduling of executor *work* is not the problem either.
- Chained execution (every iteration: await executor → done → main loop → next `run_in_executor`) is 2.4× stdloop → the cost sits in the **executor completion → loop wake**条款 integration — the step when a worker thread hands a completed future back and the loop must resume the waiter. talyn ≈77 µs per hop while uvloop does the same in ~23 µs.
- 77 µs is the wakeup quantum echoed in [BUG-417](417.md)'s reader-wake median (~100 µs) → same root cause plausible: a tick-style wake (batched/pulled completion wait) instead of prompt first-CQE wake on the executor's completion cv/notification path.

Also note for context: talyn currently rides `asyncio.AbstractEventLoop.run_in_executor` through the Python binding layer (`talyn/loop.py:472`), i.e. the executor *call* itself is base-class code — a Zig fast path here would additionally shave the per-hop Python overhead independent of the wake issue.

## Repro

```python
# executor_chain_probe.py — sequential executor hops (latency view)
import asyncio, talyn, time

async def chain(n=300):
    loop = asyncio.get_running_loop()
    done = asyncio.Event(); state = {"i": 0}
    def worker():
        def work():
            state["i"] += 1
            if state["i"] >= n: done.set()
            else: loop.run_in_executor(None, work)
        loop.call_soon_threadsafe(lambda: loop.run_in_executor(None, work))
    t = threading.Thread(target=worker); t0 = time.perf_counter(); t.start()
    await done.wait(); total = time.perf_counter() - t0; t.join()
    return total / n * 1000

talyn.install()
print("talyn:", asyncio.run(chain()), "ms/hop")        # ~0.077 ms
# stdloop and uvloop record ~0.032 / ~0.023 ms on the same host
```

## Fix direction

Mirror the fix	for [BUG-417](417.md): on the executor-completion path, wake the drive on the awaited completion (first-CQE semantics / completion immediately flush after `worker_done` signals), rather than laying a periodic wait timeout under it. If executor completions are already signaled — then the tick must live somewhere shared (timer-wheel re-arm, ring flusher) and both bugs collapse into "audit every `io_uring_wait_cqetimeout` with a constant timeout under ~1 ms". A regression canary mirroring BUG-417's (`median chained hop < 40 µs`) would keep both honest.
