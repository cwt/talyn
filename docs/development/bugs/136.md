# BUG-136 — `WriteTransport.queue_eof` silently drops EOF request when write buffer is non-empty

- **Status**: 🔴 Open
- **Severity**: 🟠 High — TCP half-close / shutdown data loss
- **Files**: `src/transports/write_transport.zig:384-387`
- **Lessons**: [Event Loop §Lesson 57](../lessons/03-event-loop-lifecycle.md), [Network Protocols §Lesson 40](../lessons/06-network-protocols-and-io.md)
- **Description**: In `src/transports/write_transport.zig`, `queue_eof` is implemented as:
  ```zig
  pub fn queue_eof(self: *WriteTransport) !void {
      if (self.buffer_size > 0) return;
      ...
  }
  ```
  If any bytes remain queued in the write buffer, `queue_eof` simply returns without setting a `pending_eof` flag or scheduling EOF submission after buffer drainage.
- **Trigger**: Calling `transport.write_eof()` or `transport.close()` while data is still being flushed over the socket.
- **Consequences**: The EOF request is completely lost; the connection remains open on the write side and the peer never receives FIN.
- **Proposed Fix**: Add a `pending_eof: bool` flag to `WriteTransport`. When `buffer_size > 0`, set `pending_eof = true`; in `write_operation_completed`, check `pending_eof` when `buffer_size == 0` and queue the EOF shutdown.
