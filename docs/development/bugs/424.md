# BUG-424 — `stream_clear` frees the loop reference before unregistering the fixed file

- **Status**: 🟡 Open
- **Severity**: 🟠 High — bounded fixed-file slot + kernel reference leak
- **Category**: Teardown ordering / resource ownership
- **Files**: `src/transports/stream/constructors.zig:326-349`
- **Related**: [BUG-284](284.md), [BUG-117](117.md), [BUG-367](367.md), [Mandate #6](../architectural-mandates.md)

## Description

`stream_clear` runs `deinitialize_object_fields` (which decrefs **and nulls** `self.loop`) before the
fixed-file cleanup:

```zig
python_c.deinitialize_object_fields(py_transport, &.{"protocol_buffer"});   // nulls loop
...
if (py_transport.fixed_file_index != 0) {
    if (py_transport.loop) |loop_obj| { ... unregister_fixed_file ... }       // loop is NULL here
    py_transport.fixed_file_index = 0;                                        // slot lost
}
```

Because the `if (py_transport.loop)` is null, `unregister_fixed_file` is never called, yet
`fixed_file_index` is zeroed — the slot is neither returned to `fixed_file_free` nor unregistered from
the kernel, so it leaks permanently.

## Trigger

Any `StreamTransport` created with a registered fixed file (the common fixed-file path) that reaches
`stream_clear` / `stream_dealloc`.

## Consequences

Gradual exhaustion of the 1024-entry fixed-file table → `NoFixedFileSlots` on new connections, plus a
stale kernel file reference.

## Fix

Capture `loop` (or perform the fd/fixed-file cleanup) **before** `deinitialize_object_fields`, e.g.:

```zig
const loop_obj = py_transport.loop;
... cleanup fd + unregister_fixed_file(loop_obj) ...
python_c.deinitialize_object_fields(py_transport, &.{"protocol_buffer"});
```

## 2026-11-12 Validation

- Ordering confirmed: `deinitialize_object_fields` (`constructors.zig:330`) decrefs and nulls every
  `?PyObject` field including `loop` (`python_c.zig:666-673`; field is `loop: ?PyObject`,
  `stream/main.zig:54`) before the fixed-file block (`:338-344`), so `unregister_fixed_file` is
  skipped while `fixed_file_index` is zeroed — the bounded-table slot and its kernel fget leak.
- Precision: the leak is confined to transports that reach `stream_clear`/`stream_dealloc` **without**
  a prior `cancel_and_close_fd` — the normal close path unregisters the fixed file before teardown
  (BUG-367's fix covers that path).
