# BUG-288 — `parseIp6` accepts >8 groups without `::`

- **Status**: 🟢 Fixed (2026-08-23)
- **Severity**: 🟡 Medium — Silent acceptance of invalid network input
- **Files**:
  - `src/utils/address.zig:151` (`while (i < host.len and group_i < 8)` — loop silently caps at 8)
  - `src/utils/address.zig:199-204` (`if (group_i != 8) return error.IncompleteAddress;` — cannot detect overflow)
- **Lessons**: [Security & Input Validation §Lesson 92](../lessons/09-security-and-input-validation.md), [Security & Input Validation §Lesson 58](../lessons/09-security-and-input-validation.md)
- **Description**: For input without `::`, the loop exits when `group_i` hits 8 even if characters remain. Validation passes because `group_i == 8`. `"1:2:3:4:5:6:7:8:9"` therefore parses successfully as `1:2:3:4:5:6:7:8`, discarding `":9"`; a trailing bare colon is likewise ignored. `inet_pton` rejects both. BUG-70 only added rejection for the `::` + ≥8-groups case; the no-`::` overflow branch was missed.
- **Trigger**: Malformed IPv6 literals supplied to connect/bind/getaddrinfo-style paths.
- **Consequences**: Connects/binds against a different endpoint than requested — wrong-target/security issue.
- **Fix (Applied — 2026-08-23)**: Two guards in the no-`::` path: the 8th group followed by any remaining character rejects immediately (`InvalidIPAddressFormat`) — this catches both trailing junk and the extra-empty-group form (`…:8:`) whose separator was consumed in-loop; plus a post-loop `i < host.len` check.
- **Regression test**: Zig unit tests in `address.zig` ("parseIp6 rejects more than 8 groups without :: (BUG-288)") covering junk-suffix, trailing-colon, over-long `::` form, and the still-valid IncompleteAddress case.
