# BUG-310 — Systemic PyObject reference leaks in all socket operations on io.queue failure

- **Status**: 🟢 Fixed (2026-09-07)
- **Severity**: 🔴 High — Systemic Python object reference leak across all 7 socket operations under submission backpressure or allocation failure
- **Files**:
  - `src/loop/python/io/socket/ops.zig` (`loop_sock_accept`: lines 144–155; `loop_sock_connect`: lines 250–260; `loop_sock_recv`: lines 357–366; `loop_sock_sendall`: lines 486–496; `loop_sock_recvfrom`: lines 602–623; `loop_sock_sendto`: lines 737–759; `loop_sock_recv_into`: lines 810–820)
- **Lessons**: [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md), [Python C-API Correctness](../lessons/05-python-c-api-correctness.md)
- **Description**:
In all 7 socket operation initiators in `src/loop/python/io/socket/ops.zig`:
```zig
sd.* = .{
    .future = python_c.py_newref(fut),
    .loop = python_c.py_newref(self),
    ...
};
errdefer allocator.destroy(sd);
loop_data.io.queue(sd) catch |err| {
    return PyErr(err);
};
```
If `loop_data.io.queue(sd)` fails (e.g. ring full or OOM), `errdefer allocator.destroy(sd)` frees the memory of `sd` but does NOT call `python_c.py_decref` on `sd.future` or `sd.loop`. Both Python references are permanently leaked in the CPython runtime.
- **Root Cause**: The `errdefer` only frees the container struct and fails to release the owned Python object references stored in its fields.
- **Trigger Scenario**: Ring saturation, submission queue exhaustion, or memory allocation error during `sock_accept`, `sock_connect`, `sock_recv`, `sock_sendall`, `sock_recvfrom`, `sock_sendto`, or `sock_recv_into`.
- **Proposed Remediation**: Update `errdefer` across all 7 functions to release `sd.future` and `sd.loop`: `errdefer { python_c.py_decref(sd.future); python_c.py_decref(sd.loop); allocator.destroy(sd); }`.

- **Fix (Applied — 2026-09-07)**:
  - All 7 initiators in `src/loop/python/io/socket/ops.zig` (`loop_sock_accept`, `loop_sock_connect`, `loop_sock_recv`, `loop_sock_sendall`, `loop_sock_recvfrom`, `loop_sock_sendto`, `loop_sock_recv_into`) gained the full-release errdefer after the data-struct init — mirroring the pattern already used in `getaddrinfo.zig:188`/`getnameinfo.zig:111`: on `io.queue` failure the owned `future` and `loop` references are decref'd before the struct is destroyed (LIFO ordering keeps the recv_into `Py_buffer` release correct). The op was never queued on that path, so its completion cleanup would never run.
  - The io.queue-failure path is not deterministically triggerable from Python (requires submission-ring exhaustion); the success/cancellation paths (the cleanup callbacks the errdefer mirrors) are heavily exercised by the suite.
- **Regression test**: `tests/test_socket_ops.py::test_sock_ops_future_refcount_stability` — 12 accept/connect/sendall/recv cycles asserting zero net reference drift (catches double-decref/missed-decref regressions in the cleanup paths shared with the new errdefers).
- **Validation (2026-09-07)**: Confirmed still present in all 7 initiators.
  - Each `errdefer` destroys the data struct without releasing the `py_newref`'d `future`/`loop` fields when `io.queue` fails: `ops.zig:145` (accept, fields 147-148, queue 154), `:251` (connect, 253-254/259), `:358` (recv, 360-361/366), `:487` (sendall, 489-490/496), `:603` (recvfrom, 605-606/622), `:738` (sendto, 740-741/758), `:811` (recv_into, 813-814/819).
  - The correct pattern already exists in sibling files (`getaddrinfo.zig:188`, `getnameinfo.zig:111` wrap the release in a full `errdefer { ... }` block) — the fix is mechanical.
