# BUG-440 — `Future.get_loop()` returns NULL without an exception on an uninitialized Future

- **Status**: 🟡 Open
- **Severity**: 🟢 Low — crash on `Future.__new__(Future).get_loop()`
- **Category**: Null handling
- **Files**: `src/future/python/constructors.zig:140-142`
- **Related**: [BUG-369](369.md), [Mandate #4](../architectural-mandates.md), [BUG-446](446.md) (sibling: `handle_talyn_future_object` null-unwrap)

## Description

```zig
pub fn future_get_loop(self: *PythonFutureObject) callconv(.c) ?PyObject {
    return python_c.py_newref(self.?.py_loop);   // py_loop may be null
}
```

`z_future_new` leaves `py_loop == null` (zeroed by `future_set_initial_values`). `py_newref(null)` →
`Py_IncRef(NULL)` → segfault.

## Fix

Return `get_py_none()` (or raise) when `py_loop == null`.

## 2026-11-12 Validation

- Missing null check + reachable null confirmed: `constructors.zig:140-142` returns
  `python_c.py_newref(self.?.py_loop)` with no guard, and `z_future_new` (`:40-44`) only runs
  `future_set_initial_values`, which zeroes `py_loop` via `initialize_object_fields` (`:13-22`) and
  never calls `future_init_configuration`.
- Crash-mechanism correction: `py_newref` calls CPython's `Py_IncRef`, which is documented to accept
  NULL ("Py_IncRef() accepts NULL whereas _Py_IncRef() doesn't"). The actual failure is a NULL return
  **without an exception set** → Python raises `SystemError: ... returned NULL without setting an
  error` — a broken API, not a segfault. Severity unchanged (Low); the proposed fix (return None or
  raise) still applies.
- Sibling filed as BUG-446: `handle_talyn_future_object` (`task/callbacks.zig:392`) unwraps
  `future.py_loop.?` with no released/null guard — a genuine unwrap panic in the same object state.
