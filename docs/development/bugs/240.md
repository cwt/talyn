# BUG-240 — `reserved_slots` underflow in DNS `ControlData.release` and `mark_resolved_and_execute_user_callbacks`

- **Status**: ✅ Fixed (2026-08-17)
- **Severity**: 🔴 High — Event loop stall / massive syscall overhead under free-threading
- **File**: `src/loop/dns/resolv.zig:169-175` (ControlData.release), `src/loop/dns/resolv.zig:228` (mark_resolved_and_execute_user_callbacks)
- **Lessons**: [Event Loop §Lesson 1 — Atomic Sleep](../lessons/02-concurrency-and-thread-safety.md), [io_uring §Lesson 19 — Syscall Elimination / Short-Circuit Empty-SQE](../lessons/03-event-loop-lifecycle.md), [BUG-216](0216.md) (reserved_slots desync)
- **Description**: `dispatch_guaranteed` (`src/loop/scheduling/soon.zig:25`) unconditionally decrements `reserved_slots`. It is designed for **blocking-task callbacks** whose slots were reserved by `reserve_slots(1)` at task creation time — the decrement is paired with a later re-increment when the blocking task is finalized (`fetch_completed_tasks` in `runner.zig:250`). This pattern is correct for blocking tasks because each callback owns exactly one slot.

  However, DNS query paths use `dispatch_guaranteed` incorrectly:

  1. **`ControlData.release()`** (line 721): reserves exactly **1 slot** via `reserve_slots(1)`, then `errdefer loop.reserved_slots -= 1` on allocation failure. But if `release()` is called with N ≥ 2 user callbacks (typical for multi-server DNS queries), lines 169–175 call `dispatch_guaranteed` N times — each decrementing `reserved_slots`. The net effect: `reserved_slots = 1 - N`, which **underflows to `maxInt(usize)`**.

  2. **`mark_resolved_and_execute_user_callbacks()`** (line 228): calls `dispatch_guaranteed` N times with **no corresponding `reserved_slots` increment anywhere**. This is a pure leak — `reserved_slots` is decremented N times without any prior reservation.

  The `reserved_slots` counter gates the event loop's blocking behavior in `poll_blocking_events` (`runner.zig:260`):
  ```zig
  if (should_wait and self.reserved_slots == 0) {
      should_wait = false;
  }
  ```
  When `reserved_slots` underflows to a huge positive value, this short-circuit never triggers. The loop calls `io_uring_enter(1)` on **every iteration** even when there are no in-flight operations, causing massive syscall overhead. Under free-threading with concurrent DNS lookups, this can lead to **event loop stalls** as the kernel polls are serialized by the GIL.

  Additionally, the `reserved_slots` counter is used to detect "nothing in-flight" state. An underflow makes the loop believe there are always slots reserved, preventing it from entering the deep-sleep fast path.

- **Trigger**: Any DNS query with N ≥ 2 user callbacks (multi-server DNS, recursive lookups, or synchronous lookups that queue callbacks). The underflow is deterministic — it happens on every DNS query with multiple callbacks.
- **Consequences**: 
  - Underflow to `maxInt(usize)` on the first multi-callback DNS query.
  - Event loop performs unnecessary `io_uring_enter(1)` syscalls on every iteration.
  - Under heavy concurrent DNS load (free-threaded Python), the syscall overhead can cause visible latency spikes and event loop stalls.
- **Resolution (2026-08-17)**: Replaced `dispatch_guaranteed` / `dispatch_guaranteed_nonthreadsafe` with `Soon.dispatch` / `Soon.dispatch_nonthreadsafe` in both `ControlData.release()` (lines 169-175) and `mark_resolved_and_execute_user_callbacks()` (line 228). These push to the ready queue without touching `reserved_slots`, which is the correct behavior for callbacks that are not backing a reserved blocking task slot. The `errdefer loop.reserved_slots -= 1` at line 722 remains for the allocation-failure path.
- **Verification**: After fix, `zig build test` should pass. Under free-threaded Python with concurrent DNS lookups, `io_uring_enter` call count should drop to near-zero during idle periods.
