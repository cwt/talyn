# BUG-260 — Talyn clamps RLIMIT_NOFILE to `TotalTasksItems+64`, exhausting fds under proxy load

- **Status**: 🔴 Open (discovered 2026-08-20)
- **Severity**: 🟠 High (production-breaking for high-concurrency servers using Talyn as the event loop; misdiagnosed because the real errno is masked)
- **File**: `src/loop/scheduling/io/main.zig` — `IO.init` fd-limit clamp (lines 530–534); symptom surfaces in `src/loop/python/io/client/create_connection.zig:520` and `src/loop/dns/resolv.zig:583`; consumer: wormhole proxy (`../wormhole/wormhole/server.py:24`).
- **Description**: At loop init, `IO.init` raises the process fd limit based on the io_uring SQE depth, not on expected socket concurrency:
  ```zig
  // src/loop/scheduling/io/main.zig:531-534
  const nr_files: u32 = TotalTasksItems;          // = 1024 (line 16)
  var rlim: std.os.linux.rlimit = undefined;
  _ = std.os.linux.getrlimit(.NOFILE, &rlim);
  _ = std.os.linux.setrlimit(.NOFILE, &.{ .cur = nr_files + 64, .max = rlim.max });
  ```
  `TotalTasksItems = 1024` is the io_uring submission-queue depth (line 16) and has **no relationship** to how many sockets a proxy opens. This `setrlimit` forces the process's soft fd limit to **`1088`** at most — and actually *lower* if the prior hard limit was below 1088, because the `_ =` discards the `EINVAL` and leaves the limit at the OS default (typically `1024`). So the entire host process (including wormhole) can never hold more than ~1088 fds.

  A forward proxy keeps **≈2 fds per tunnel** (one client socket + one backend socket) plus DNS/eventfd fds. wormhole derives its concurrency cap from this same limit: `MAX_TASKS = int(0.9 * resource.getrlimit(resource.RLIMIT_NOFILE)[0])` (`wormhole/wormhole/server.py:24`). It reads the limit at *import time*, before Talyn's loop exists and lowers it, and it counts **tasks, not fds**. With Talyn in place the ceiling collapses to ~1088 while wormhole still admits ~921 tasks, each needing ≥2 fds → ~1842 fds demanded. Once load is sustained (e.g. a high-traffic asset host like `github.githubassets.com`), the process is permanently fd-starved.

  When fds run out, every new outbound `socket()` returns `EMFILE`/`ENFILE`. Talyn's connect path **blindly collapses every socket() failure to `error.SystemResources`**:
  ```zig
  // src/loop/python/io/client/create_connection.zig:520
  if (utils.getSyscallErrno(socket_ret) != .SUCCESS) return error.SystemResources;
  ```
  (`src/loop/dns/resolv.zig:583` and `src/loop/python/io/datagram/create_endpoint.zig:247` do the same.) `error.SystemResources` is normally reserved for io_uring registered-buffer / `RLIMIT_MEMLOCK` failures (see [BUG-117](../117.md)), so the name points operators at the wrong subsystem. The future is then set with a generic `OSError: SystemResources` and wormhole retries 3× (`MAX_RETRY = 3`, `wormhole/server.py:12`) before returning `502`.

- **Trigger**: Run wormhole (or any Talyn-backed proxy keeping many concurrent client+backend sockets) under sustained load. The failure is deterministic and persistent (not burst-only) once steady-state fd usage exceeds the ~1088 ceiling. Observed: `CONNECT 502 github.githubassets.com:443 (All connection attempts failed after 3 retries. Last error: SystemResources)`.
- **Why it looks Talyn-specific**: The default asyncio loop imposes no such 1088 cap (it inherits whatever the OS/hard limit allows), so the same proxy "works" on the stock loop and only breaks once Talyn artificially lowers the fd ceiling at loop init.
- **Consequences**:
  - All outbound connects fail with a misleading `SystemResources` (actually `EMFILE`/`ENFILE`) once fd usage is sustained.
  - The proxy returns `502` for otherwise-reachable destinations; retries cannot help because the ceiling is structural, not transient.
  - Diagnosis is obscured by the errno masking (related to the accept-side `EMFILE`/`ENFILE` handling in [BUG-33](../033.md) and the fixed-file-slot accounting in [BUG-26](../026.md)/[BUG-27](../027.md)).
- **Root cause (two coupled defects)**:
  1. **Design flaw**: fd limit coupled to io_uring SQE depth (`TotalTasksItems`). The SQE depth and the fd ceiling are independent quantities; clamping `RLIMIT_NOFILE` to `TotalTasksItems + 64` is both too low and, when the prior hard limit is lower, silently ineffective.
  2. **Diagnostic flaw**: `socket()` failures are reported as `error.SystemResources` instead of the real `EMFILE`/`ENFILE`, hiding the true cause.
- **Resolution (proposed, not yet implemented)**:
  - In `IO.init`, stop clamping `RLIMIT_NOFILE` to `TotalTasksItems + 64`. Either raise it to a genuinely high value (keep the existing hard limit, or a large fixed floor), or make it a configurable parameter decoupled from `TotalTasksItems`.
  - In `create_connection.zig:520`, `resolv.zig:583`, and `create_endpoint.zig:247`, map `EMFILE`/`ENFILE` to distinct errors (or surface the raw errno) so operators see "too many open files" rather than `SystemResources`.
  - In wormhole: account for ≈2 fds per task and read `RLIMIT_NOFILE` *after* the loop is created.
- **Reproduction**: Run wormhole with Talyn on a host whose `RLIMIT_NOFILE` hard limit is ≤ 1088 (common default `1024`), drive sustained concurrent CONNECT traffic, and observe `socket()` returning `EMFILE` masked as `SystemResources`. A focused regression test would (a) init a `Loop`, assert the resulting `RLIMIT_NOFILE` is not clamped to `TotalTasksItems+64`, and (b) assert that a simulated `EMFILE` from `socket()` surfaces as `EMFILE`/`ENFILE` rather than `SystemResources`.
