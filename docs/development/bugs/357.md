# BUG-357 — Unresolved futures (infinite hang) when DNS `on_query_sent` fails on the last nameserver or `getaddrinfo_callback` / `getnameinfo_callback` error or cancel

- **Status**: ✅ Fixed (2026-10-18)
- **Severity**: 🔴 High — causes `await loop.getaddrinfo(...)` and `await loop.getnameinfo(...)` to hang forever when sending the DNS query fails (`ENETUNREACH`/`ECONNREFUSED`) or when result construction fails
- **Category**: Logic Bug (Infinite Hang)
- **Files**:
  - `src/loop/dns/resolv.zig:371-374`
  - `src/loop/python/io/socket/getaddrinfo.zig:31-59`
  - `src/loop/python/io/socket/getnameinfo.zig:28-73`
- **Related**: [BUG-332](332.md), [BUG-355](355.md)

## Overview & Root Cause

1. **`on_query_sent` failure on the last nameserver dispatches callbacks as `cancelled = true` (`src/loop/dns/resolv.zig:371-374`)**:
   Compare `on_response_received` (lines 406–415):
   ```zig
   if (io_uring_err != .SUCCESS or io_uring_res <= 0) {
       const control_data = server_data.control_data;
       if (control_data.active_servers == 1) {
           try mark_resolved_and_execute_user_callbacks(control_data);
       }
       server_data.release();
       return;
   }
   ```
   with `on_query_sent` (lines 371–374):
   ```zig
   if (io_uring_err != .SUCCESS) {
       server_data.release();
       return;
   }
   ```
   When `on_query_sent` fails on the last active nameserver (`control_data.active_servers == 1`, e.g., `ENETUNREACH` when offline), `server_data.release()` decrements `active_servers` to `0` and calls `control_data.release()` while `control_data.resolved` is still `false`!
   `control_data.release()` then sets `v.data.set_cancelled(true)` on every user callback and appends them to `ready_tasks_queues`.

2. **`getaddrinfo_callback` and `getnameinfo_callback` return early on `if (data.cancelled())` and on `try` errors without resolving the `Future`**:
   In `src/loop/python/io/socket/getaddrinfo.zig:31-59`:
   ```zig
   fn getaddrinfo_callback(data: *const CallbackManager.CallbackData) !void {
       const gaid: *GetAddrInfoData = @ptrCast(@alignCast(data.user_data.?));
       defer cleanup_getaddrinfo(data.user_data);

       if (data.cancelled()) {
           return;
       }
       ...
       const list = try build_addrinfo_list(addrs, gaid.port, gaid.family, gaid.sock_type, gaid.proto);
       defer python_c.py_decref(list);

       const future_data = utils.get_data_ptr(Future, gaid.future);
       try Future.Python.Result.future_fast_set_result(future_data, list);
   }
   ```
   And identically in `src/loop/python/io/socket/getnameinfo.zig:28-73`:
   - When `data.cancelled()` is true (such as when `on_query_sent` fails above), `getaddrinfo_callback` and `getnameinfo_callback` clean up `gaid`/`gnid` and return without setting an exception on `gaid.future`/`gnid.future`. If the Python caller is still awaiting that `Future`, it **hangs forever**!
   - Likewise, if `try build_addrinfo_list(...)` in `getaddrinfo_callback` fails, or if `try loop_data.dns.lookup_hostname(...)` / `orelse return error.PythonError` in `getnameinfo_callback` fails, the callback returns an error without calling `set_future_exception` on `gaid.future`/`gnid.future`, leaving the `Future` pending forever.

## Trigger Scenario

1. Call `await loop.getaddrinfo("example.com", 80)` when all configured nameservers in `/etc/resolv.conf` are unreachable (`ENETUNREACH` on UDP send).
2. `on_query_sent` sees `io_uring_err != .SUCCESS` and calls `server_data.release()`, which dispatches `getaddrinfo_callback` with `data.cancelled() == true`.
3. `getaddrinfo_callback` hits `if (data.cancelled()) return;`, frees `gaid`, and never sets an exception on `gaid.future`. The coroutine awaiting `loop.getaddrinfo` hangs forever.

## Proposed Remediation

1. In `on_query_sent` (`src/loop/dns/resolv.zig:371-374`), mirror `on_response_received`: if `control_data.active_servers == 1`, call `try mark_resolved_and_execute_user_callbacks(control_data);` before `server_data.release()`.
2. In `getaddrinfo_callback` (`src/loop/python/io/socket/getaddrinfo.zig`) and `getnameinfo_callback` (`src/loop/python/io/socket/getnameinfo.zig`), if `data.cancelled()` is true and `future_data.status == .pending`, set a cancellation or `gaierror` exception on `future`; and catch errors from `build_addrinfo_list` / `lookup_hostname` / tuple construction to pass them to `set_future_exception(err, future)`.

## Resolution (2026-10-18)

1. **`on_query_sent`** (`src/loop/dns/resolv.zig`): the failure/`resolved`/cancelled branch now mirrors the shipped BUG-317 pattern from the response-read error path — when `should_fail_resolution_on_server_finish(control_data)` (this server is the last outstanding one and nobody resolved yet), `mark_resolved_and_execute_user_callbacks(server_data)` runs before `server_data.release()`, so the user callbacks execute against the (empty) record and fail the futures cleanly instead of being dispatched as cancelled.
2. **`getaddrinfo_callback`** (`src/loop/python/io/socket/getaddrinfo.zig`): the cancelled branch and the `dns.lookup` error path resolve a still-pending future via a new `resolve_future_error(future, msg)` helper (raises `RuntimeError(msg)` when no exception is pending; routes an already-pending exception into the future; silently skips futures already resolved/cancelled). `build_result_tuple` failures also resolve the future now.
3. **`getnameinfo_callback`** (`src/loop/python/io/socket/getnameinfo.zig`): same helper; `build_reverse_name` errors and all result-construction failures (`PyUnicode`/`PyLong`/`PyTuple_Pack`) resolve the future instead of returning bare errors (which ran only the cleanup, leaving the future pending).

Test (`tests/test_getaddrinfo.py::test_bug357_failed_resolution_resolves_future_promptly`): repeated failing `getaddrinfo("nonexistent.invalid")` and `getnameinfo(("127.0.0.1", 8080))` calls must raise within a bounded wait (a pending-forever future fails the test via `wait_for` + elapsed assertions). Passes on 3.13/3.13t/3.14/3.14t.
