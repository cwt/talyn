# BUG-311 — Task context reference leak on task_schedule_coro failure in fast_new_task

- **Status**: 🔴 Open (2026-09-07)
- **Severity**: 🔴 High — Context object reference leak on task scheduling failure
- **Files**:
  - `src/task/constructors.zig` (`fast_new_task`: lines 74–76 and 84–88)
- **Lessons**: [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md), [Python C-API Correctness](../lessons/05-python-c-api-correctness.md)
- **Description**:
In `fast_new_task`:
```zig
errdefer {
    instance.py_context = null;
}
...
if (context) |ctx| {
    python_c.py_incref(ctx);
    instance.py_context = ctx;
}
task_schedule_coro(instance) catch |err| {
    return PyErr(err);
};
```
BUG-304 added the `py_incref` for the context at line 85. However, the legacy `errdefer` from lines 74–76 was left unchanged. If `task_schedule_coro` fails, the `errdefer` sets `instance.py_context = null`. When the Python GC deallocates `instance`, `task_dealloc` checks `if (self.py_context) |ctx| python_c.py_decref(ctx);`. Because `py_context` was cleared to `null`, `py_decref` is never called, leaking the acquired reference to `context`.
- **Root Cause**: The error-handling path clears the pointer holding an owned reference without first decrementing its reference count.
- **Trigger Scenario**: Task creation failure when `task_schedule_coro` encounters an error while a non-null `context` is provided.
- **Proposed Remediation**: In the `errdefer`, decref the context if set: `errdefer { if (instance.py_context) |ctx| python_c.py_decref(ctx); instance.py_context = null; }`.

- **Validation (2026-09-07)**: Confirmed still present.
  - `fast_new_task`: the `errdefer { instance.py_context = null; }` (`src/task/constructors.zig:74-76`) runs before the `py_decref(instance)` errdefer (`:71`), so `task_dealloc` never sees the context; the instance-owned reference taken at `:85` (BUG-304 `py_incref(context)`) leaks when `task_schedule_coro` (`:88`) fails.
  - Contrast: `z_task_init` (`constructors.zig:214, 231-233`) is safe — its `errdefer py_decref(context.?)` at `:214` releases the single owned reference, and nulling `py_context` merely suppresses the dealloc-side decref. In `fast_new_task` the `py_incref` at `:85` is the only owner, so nulling the field orphans it.
