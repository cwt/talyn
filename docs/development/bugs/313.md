# BUG-313 — Child watcher map inconsistency and handler orphan on duplicate registration

- **Status**: 🟢 Fixed (2026-09-07; code fix landed in the BUG-326 commit — same file, and the regression test depends on the BUG-326 errno-decode fix)
- **Severity**: 🔴 High — Child watcher map corruption and descriptor leak on concurrent or rapid child re-registration
- **Files**:
  - `src/loop/child_watcher.zig` (`on_child_exit`: lines 237–244)
- **Lessons**: [Event Loop Lifecycle](../lessons/03-event-loop-lifecycle.md), [Data Structures & Algorithms](../lessons/07-data-structures-and-algorithms.md)
- **Description**:
In `on_child_exit`:
```zig
if (self.handlers.fetchRemove(handler.pid)) |entry| {
    const removed_handler = entry.value;
    if (removed_handler == handler) {
        self.teardown_child_handler(handler);
    }
}
```
If a new handler was added for the same PID before the CQE for the previous handler was reaped:
1. `fetchRemove(handler.pid)` extracts and removes the *new handler* from the hashmap.
2. `removed_handler == handler` evaluates to `false`.
3. The block exits without tearing down either handler.
4. The newly registered handler is now permanently lost from `self.handlers` (orphaned), while the old exiting `handler` is never torn down, leaking its `pidfd` and memory.
- **Root Cause**: Unconditional `fetchRemove` on PID key rather than checking identity (`get() == handler`) before removal.
- **Trigger Scenario**: Re-registering a child watcher for a reused or rapidly replaced PID.
- **Proposed Remediation**: Inspect `self.handlers.get(handler.pid)`: only remove from the map if the currently stored handler pointer matches `handler`. In all cases, tear down the exiting `handler`.

- **Fix (Applied — 2026-09-07)**:
  - `on_child_exit` (`src/loop/child_watcher.zig`): the finalize step no longer blindly `fetchRemove`s the pid. The exiting handler tears itself down unconditionally; the map entry is removed only when it still points at THIS handler (identity-guarded `get` + `remove`). A re-register during the user callback would otherwise have pulled the NEW handler out of the map (orphaning it — its armed op could then never be torn down) while skipping our own teardown.
  - Reachability note: after the BUG-307 pre-`waitid`/post-callback `removed` guards, the divergent-entry case is unreachable — the identity check hardens the invariant against future re-entry between the checks (the two consolidations are behaviorally equivalent; teardown now happens unconditionally at the end of the non-cancelled path).
  - Corollary observed while testing: re-registering for the same pid inside the exit callback deterministically fails with `No such process` (the child was already reaped by this handler's `waitid`; `pidfd_open` → ESRCH) and routes to `call_exception_handler` — the map then ends empty and consistent.
- **Regression test**: `tests/test_child.py::test_re_register_inside_exit_callback_stays_consistent` — exit-callback re-register flow asserts the original callback fired, the exception was routed, `remove_child_handler` reports `False`, and the loop stays healthy.
- **Validation (2026-09-07)**: Confirmed still present.
  - `on_child_exit` (`src/loop/child_watcher.zig:237-244`) matches the quoted code verbatim.
  - Reachability: the user callback invoked at `child_watcher.zig:206` (`PyObject_Call(handler.callback, ...)`) can re-register the same pid via `add_child_handler` — which (per BUG-307) fetchRemoves and destroys the currently-executing handler. Control then returns into `on_child_exit`, where `fetchRemove(handler.pid)` extracts the NEW handler, `removed_handler == handler` is false, and no teardown happens for either handler.
