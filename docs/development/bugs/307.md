# BUG-307 — Child watcher replacement use-after-free and double-free on cancelled CQE

- **Status**: 🟢 Fixed (2026-09-07)
- **Severity**: 🔴 Critical — Use-after-free and double-free in event loop core when re-registering child process handlers
- **Files**:
  - `src/loop/child_watcher.zig` (`add_child_handler`: lines 85–95; `on_child_exit`: lines 130–137)
- **Lessons**: [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md), [io_uring & Kernel](../lessons/04-io-uring-and-kernel.md), [Event Loop Lifecycle](../lessons/03-event-loop-lifecycle.md)
- **Description**:
  When a user calls `add_child_handler` for a PID that is already being monitored:
  ```zig
  if (self.handlers.get(pid)) |old_handler| {
      _ = self.loop.ring.cancel(old_handler.task_id, .CancelIO) catch {};
      self.loop.allocator.destroy(old_handler);
  }
  ```
  The cancellation request is queued asynchronously to `io_uring`, but the kernel CQE for `old_handler.task_id` has not yet completed. The memory for `old_handler` is freed immediately via `allocator.destroy(old_handler)`.
  When the cancelled CQE arrives, `on_child_exit` receives `data` pointing to the freed memory:
  ```zig
  pub fn on_child_exit(data: *anyopaque, res: i32) void {
      const handler: *ChildHandler = @ptrCast(@alignCast(data));
      if (handler.removed) {
          handler.loop.child_watcher.teardown_child_handler(handler);
          return;
      }
  ```
  Reading `handler.removed` is a Use-After-Free. If the freed heap slot contains non-zero residual bytes, `handler.removed` evaluates to `true`, calling `teardown_child_handler(handler)`, which destroys the memory a second time (`allocator.destroy(handler)`) and attempts to close an already-closed or reassigned `pidfd`.
- **Root Cause**:
  Immediate heap destruction of an active `io_uring` completion target while the asynchronous cancellation CQE is still pending in flight.
- **Trigger Scenario**:
  Replacing an existing child watcher via `loop.add_child_handler(pid, new_callback)` while the child process is running or terminating.
- **Proposed Remediation**:
  Mirror the deferred destruction model used in `remove_child_handler`: mark `old_handler.removed = true` and do NOT call `allocator.destroy(old_handler)` in `add_child_handler`. Allow `on_child_exit` to perform `teardown_child_handler` when the CQE arrives.

- **Fix (Applied — 2026-09-07)**:
  - `add_child_handler` (`src/loop/child_watcher.zig`): the replaced handler is no longer destroyed inline. It is marked `removed = true` and its armed op is cancelled; teardown ownership transfers to its own `on_child_exit` invocation (BUG-280 deferred-destruction model). The same deferred model now applies in `ChildWatcher.deinit`, which had the identical destroy-while-cancel-pending hazard (every `Loop.release()` dispatch path forces `cancelled=true`, so the cancelled branch always owns the final destroy).
  - `on_child_exit` gained a pre-`waitid` `removed` guard: when a replacement's cancellation loses the kernel race (`ASYNC_CANCEL` → `ENOENT`), the completion arrives as a normal POLLIN. The replaced handler must not consume the exit status — doing so starved the replacement's own `waitid` (`ECHILD`) and its callback never fired. The replaced handler now skips `waitid` and the user callback entirely and finalizes; the replacement handler reports the exit. Deterministic asyncio replace-semantics restored.
  - Cancelled-branch comment updated: all three cancel sources (`remove_child_handler`, replacement in `add_child_handler`, `deinit`) now mark `removed`.
- **Regression test**: `tests/test_child.py::test_replace_child_handler_cancelled_cqe_is_safe` — deterministic half replaces a self-pid handler (never exits → guaranteed ECANCELED dispatch); racy half replaces a live child's handler then terminates the child, asserting the replacement receives `(-SIGTERM)` and the loop stays healthy. First run of this test reproduced the waitid race live (old handler reaped first, ECHILD starved the replacement) and drove the pre-`waitid` guard.
- **Validation (2026-09-07)**: Confirmed still present.
  - `add_child_handler` (`src/loop/child_watcher.zig:85-95`) queues `.{ .CancelIO = old_handler.task_id }` and then immediately calls `allocator.destroy(old_handler)` — the exact destroy-before-CQE-arrival hazard described.
  - The cancelled-CQE path in `on_child_exit` (`child_watcher.zig:129-139`) dereferences `data.user_data` and reads `handler.removed` on the freed handler; non-zero residual bytes route into `teardown_child_handler` → double-destroy and double-decref.
  - Snippet drift: the quoted code predates the BUG-277 rewrite (code now uses `fetchRemove` + `io.queue(.CancelIO)` instead of `ring.cancel`); the hazard is identical.
