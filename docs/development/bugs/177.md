# BUG-177 — Systemic double-free and double-decref on error in DynamicRingBuffer completion callbacks

- **Status**: ✅ Fixed
- **Severity**: 🔴 Critical — Heap memory corruption, use-after-free, CPython reference count corruption
- **Files**: `src/loop/python/io/socket/ops.zig:48-50, 194-196, 293-295, 403, 432, 524-526, 644-646, 866-868`, `src/transports/datagram/write.zig:26-28`, `src/transports/subprocess/transport.zig:237-239`, `src/transports/write_transport.zig:234`, `src/transports/read_transport.zig:176, 183`
- **Lessons**: [Memory Management & Refcounting §Lesson 04](../lessons/01-memory-and-reference-counting.md), [Concurrency & Event Loop §Lesson 24](../lessons/02-concurrency-and-thread-safety.md)
- **Description**: In `ops.zig` (all 7 socket completion callbacks), `datagram/write.zig` (`sendto_completed`), `subprocess/transport.zig` (`pidfd_exit_callback`), and stream transports, tasks are registered with a `.cleanup` function pointer. Inside the completion callback, a `defer cleanup(user_data)` (or `defer py_decref(transport)`) is placed at function entry. When the callback function returns a Zig error (e.g. `error.PythonError`), the function's local `defer` runs cleanup/decref, and then `CallbackManager.execute_dynamic_ring_buffer` catches the error and executes `callback.cleanup` a **second time** on the already-freed pointer.
- **Trigger**: Any runtime Python exception, memory allocation failure, or cancelled state inside socket, datagram, subprocess, or stream completion callbacks.
- **Consequences**: Heap use-after-free, double `free()` on user data structs/buffers, and double `Py_DecRef` causing interpreter crashes.
- **Fix**: Replaced unconditional cleanup defers with `var success = false; defer if (success) cleanup(...)` across `ops.zig`, `datagram/write.zig`, `subprocess/transport.zig`, `write_transport.zig`, and `read_transport.zig`, guaranteeing exactly-once cleanup semantics on both success and error paths.
