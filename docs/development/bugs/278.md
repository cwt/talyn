# BUG-278 — FS watcher iterates stale slice across Python re-entry

- **Status**: 🟢 Fixed (2026-08-23)
- **Severity**: 🟠 High — Use-after-free / stale pointer across callback re-entry
- **Files**:
  - `src/loop/fs_watcher.zig:85-91` (`for (self.watchers.items) |watcher|` + `try self.dispatch_event(...)`)
  - `src/loop/fs_watcher.zig:117` (`PyObject_Call(watcher.callback, ...)` — runs Python)
  - `src/loop/fs_watcher.zig:152` (`self.watchers.append(...)` in `add_watch` — can reallocate)
  - `src/loop/fs_watcher.zig:156-170` (`remove_watch` mutates the list mid-iteration hazard)
- **Lessons**: [Memory & Reference Counting §Lesson 4](../lessons/01-memory-and-reference-counting.md), [Concurrency & Thread Safety](../lessons/02-concurrency-and-thread-safety.md)
- **Description**: The `for` header captures the ArrayList slice once; `dispatch_event` synchronously executes user code per matching entry. If that callback registers another watch on the same event batch (the classic recursive-watch-on-IN_CREATE pattern), `append` reallocates and frees the old buffer, so subsequent iterations dereference freed memory and may invoke `dispatch_event` with a garbage `*Watcher` → wild `PyObject_Call`. `remove_watch`'s swapRemove mid-loop additionally skips/duplicates entries.
- **Trigger**: Two or more watchers matching one event batch where any callback adds/removes watches.
- **Consequences**: UAF crash or wild call into arbitrary memory during ordinary filesystem-watch usage.
- **Fix (Applied — 2026-08-23)**: Per inotify event, the watcher pointer array is snapshotted (pure-Zig dupe, no Python re-entry), and each entry is re-validated against the LIVE list immediately before its callback runs — no stale slice reads, no dispatch through freed `Watcher` structs.
- **Regression test**: `tests/test_fs.py::test_watch_callback_may_add_watcher_mid_dispatch` — a watcher callback registers another watch mid-dispatch; both receive subsequent events and the process stays healthy.
