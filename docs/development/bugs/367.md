# BUG-367 — `DatagramTransport.close()` never calls `protocol.connection_lost(None)` and delays fixed-file unregistration until GC deallocation

- **Status**: ✅ Fixed
- **Severity**: 🔴 High — violates the `asyncio.DatagramTransport` contract (`protocol.connection_lost` is never called on `close()`) and keeps the kernel UDP socket (`struct file`) and port bound in `io_uring`'s fixed-file table after `transport.close()` until GC deallocation
- **Category**: Logic Bug & Kernel Socket / Port Leak
- **Files**:
  - `src/transports/datagram/main.zig:22, 46-66, 157-179`
  - `src/transports/datagram/constructors.zig:105`
- **Related**: [BUG-16](016.md), [BUG-20](020.md), [Lesson 64](../lessons/04-io-uring-and-kernel.md)

## Overview & Root Cause

In `src/transports/datagram/constructors.zig:105`, `set_protocol` caches `protocol.connection_lost` on `DatagramTransportObject.protocol_connection_lost`:

```zig
self.protocol_connection_lost = python_c.PyObject_GetAttrString(protocol, "connection_lost\x00") orelse return error.PythonError;
```

However, a search across all files in `src/transports/datagram/` shows that `protocol_connection_lost` is **never called anywhere**!

Look at `datagram_close` in `src/transports/datagram/main.zig:157-179`:

```zig
pub fn datagram_close(self: ?*DatagramTransportObject, _: ?PyObject) callconv(.c) ?PyObject {
    const instance = self.?;
    if (!instance.closing) {
        instance.closing = true;
        if (instance.loop) |loop_obj| {
            const loop_data = utils.get_data_ptr(Loop, @as(*Loop.Python.LoopObject, @ptrCast(loop_obj)));
            if (loop_data.initialized) {
                if (instance.read_task_id > 0) {
                    _ = loop_data.io.queue(.{ .CancelIO = instance.read_task_id }) catch {};
                    instance.read_task_id = 0;
                }
                if (instance.write_task_id > 0) {
                    _ = loop_data.io.queue(.{ .CancelIO = instance.write_task_id }) catch {};
                    instance.write_task_id = 0;
                }
            }
        }
        if (instance.fd >= 0) {
            _ = std.os.linux.close(instance.fd);
            instance.fd = -1;
        }
    }
    return python_c.get_py_none();
}
```

This causes two bugs:

1. **`protocol.connection_lost(None)` is never called**:
   Per the Python `asyncio.DatagramProtocol` specification, `transport.close()` must schedule `protocol.connection_lost(None)` on the event loop (`loop.call_soon`). Any application or test awaiting a `connection_lost` future on a `DatagramProtocol` hangs forever.

2. **`instance.fixed_file_index` is not unregistered in `datagram_close`**:
   `datagram_close` closes the userspace file descriptor (`std.os.linux.close(instance.fd)`), **but** leaves `instance.fixed_file_index` registered in `io_uring`'s fixed-file table until `cleanup_resources` runs in `datagram_dealloc` / `datagram_clear`!
   Because `io_uring`'s registered file table holds a kernel-level `fget` reference to the underlying `struct file`, closing the userspace `fd` alone does **not** close the kernel socket or release the bound UDP port! Attempting to re-bind the same UDP port after `transport.close()` while the `DatagramTransport` Python variable is still in scope fails with `EADDRINUSE` (Lesson 64).

## Trigger Scenario

1. Create a UDP endpoint bound to `('127.0.0.1', port)` via `transport, protocol = await loop.create_datagram_endpoint(...)`.
2. Call `transport.close()` and `await asyncio.sleep(0)`.
3. `protocol.connection_lost` is never called, and binding a new UDP socket to `('127.0.0.1', port)` while `transport` is still referenced in Python fails with `EADDRINUSE`.

## Proposed Remediation

In `datagram_close` (`src/transports/datagram/main.zig:157-179`):
1. Unregister `instance.fixed_file_index` immediately before closing `instance.fd`:
   ```zig
   if (instance.fixed_file_index != 0) {
       loop_data.io.unregister_fixed_file(instance.fixed_file_index);
       instance.fixed_file_index = 0;
   }
   ```
2. Schedule `instance.protocol_connection_lost` with `Py_None` via `loop.call_soon` (matching `StreamTransport.close_transports` in `src/transports/stream/lifecycle.zig:83-90`).


## Resolution (2026-10-18)

Both defects confirmed live and fixed in `datagram_close`
(src/transports/datagram/main.zig; the report's line numbers had drifted
to ~157-178):

1. **`connection_lost` never dispatched (fixed)**: new
   `schedule_datagram_connection_lost(instance, loop_obj)` mirrors the
   stream transport's `lifecycle.close_transports`: dispatch
   synchronously when the loop `is_closed()`, otherwise via
   `loop.call_soon(connection_lost, None)` (with `defer python_c.py_decref(none)` balancing `get_py_none()`); callback failures route to
   `loop.call_exception_handler` with a `{message, exception}` context
   (never propagating into `close()`). It is invoked when the close
   body completes (fd closed, cancels queued), so no cancelled-read
   callback can double-dispatch.

2. **Fixed-file unregistration delayed until dealloc (fixed)**:
   `datagram_close` now unregisters `instance.fixed_file_index` from
   io_uring's fixed-file table (via `unregister_fixed_file`, zeroing the
   sentinel after) BEFORE closing the userspace fd — the table's fget
   reference no longer keeps the kernel socket (and the bound UDP port)
   alive after close while the Python object is still referenced
   (EADDRINUSE on an immediate re-bind).

## Test

`tests/test_datagram_close.py` (three tests): `connection_lost(None)`
reached inside the same running loop after `close()`; `/proc/net/udp`
must stop listing the port right after close (returned transport still
alive in Python — dealloc cleanup could not have run); a fresh exclusive
bind of the same port must succeed.

**Bite verification**: reverting datagram/main.zig to the pre-fix shape
makes all three fail: `TimeoutError` (callback never dispatched), "UDP
port still bound after transport.close()", and
`OSError: [Errno 98] Address already in use` on the re-bind.

Passes on 3.13/3.13t/3.14/3.14t in ReleaseFast (419 passed × 4; the
three documented standalone artifacts of test_datagram.py pass inside
the full suite).
