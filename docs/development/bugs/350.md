# BUG-350 — Uninitialized `fixed_buffer_index` (`0`) on `DatagramTransportObject` corrupts `RegisteredBufferPool` when `DatagramTransport` allocation fails

- **Status**: ✅ Fixed (2026-10-18)
- **Severity**: 🔴 Critical — releases registered buffer slot `0` belonging to another active transport, causing two transports to share the same 64 KB `io_uring` registered buffer simultaneously (memory corruption / data cross-talk)
- **Category**: Memory / Buffer Pool Corruption (Aliased Buffer)
- **Files**:
  - `src/transports/datagram/constructors.zig:8-14, 59-75, 118-132`
  - `src/transports/datagram/main.zig:34, 56-66`
- **Related**: [Lesson 40](../lessons/05-python-c-api-correctness.md), [BUG-17](017.md)

## Overview & Root Cause

In `src/transports/datagram/main.zig:34`, `DatagramTransportObject` declares:

```zig
pub const DatagramTransportObject = extern struct {
    ...
    fixed_buffer_index: i32 = -1,
    ...
};
```

However, `DatagramTransportObject` is allocated via CPython's `tp_alloc` (`PyType_GenericAlloc`) in `datagram_new` (`src/transports/datagram/constructors.zig:10-12`) and `new_datagram_transport` (`src/transports/datagram/constructors.zig:119-121`), which **zero-initializes** the struct memory (`memset(0)`). As documented in Lesson 40, Zig struct field default values (`= -1`) are **never** applied by `tp_alloc`, so `self.fixed_buffer_index` starts at `0` (not `-1`)!

Now trace `z_datagram_init` (`src/transports/datagram/constructors.zig:59-75`) and `new_datagram_transport` (`src/transports/datagram/constructors.zig:118-132`):

```zig
self.loop = python_c.py_newref(@ptrCast(talyn_loop));
errdefer {
    python_c.py_decref(@ptrCast(talyn_loop));
    self.loop = null;
}

if (loop_data.io.lease_buffer()) |leased| {
    self.read_buf_slice = leased.slice;
    self.fixed_buffer_index = @intCast(leased.index);
} else {
    self.read_buf_slice = try loop_data.allocator.alloc(u8, 65536);
    self.fixed_buffer_index = -1;
}
```

And if a caller instantiates `DatagramTransport.__new__(DatagramTransport)` without `__init__`, or if `z_datagram_init` is called via `new_datagram_transport` (where `errdefer python_c.py_decref(@ptrCast(self))` runs `datagram_dealloc` -> `cleanup_resources(self)`), look at what happens when `lease_buffer()` returns `null` (pool exhausted) and `loop_data.allocator.alloc(u8, 65536)` fails at line 72:
- Wait: in `z_datagram_init`, if `alloc` fails at line 72, the `errdefer` at line 60 sets `self.loop = null`, so `cleanup_resources` skips the `if (self.loop)` block.
- **However**, what if `z_datagram_init` fails at lines 36–57 (before `self.fixed_buffer_index` is set) on a second `__init__` call, OR what if `set_protocol(self, protocol)` fails at line 91 when `lease_buffer()` was not reached or if `datagram_new` set `self.fd = -1` without setting `self.fixed_buffer_index = -1`?
- Even more directly: in `datagram_new` (`src/transports/datagram/constructors.zig:8-14`):
  ```zig
  pub fn datagram_new(type_obj: ?*python_c.PyTypeObject, _: ?PyObject, _: ?PyObject) callconv(.c) ?PyObject {
      const self: ?*DatagramTransportObject = @ptrCast(@alignCast(type_obj.?.tp_alloc.?(type_obj, 0)));
      if (self) |instance| {
          instance.fd = -1;
      }
      return @ptrCast(self);
  }
  ```
  `datagram_new` sets `instance.fd = -1` because `0` is a valid fd (`stdin`), **but forgets to set `instance.fixed_buffer_index = -1`** (where `0` is a valid `RegisteredBufferPool` index)! And `new_datagram_transport` (`src/transports/datagram/constructors.zig:118-132`) does not initialize `instance.fd = -1` or `instance.fixed_buffer_index = -1` after `tp_alloc` before calling `z_datagram_init`! If `z_datagram_init` fails at line 50 (`fcntl` error) or line 56 (`Invalid event loop`), `new_datagram_transport`'s `errdefer python_c.py_decref(@ptrCast(self))` runs `datagram_dealloc` -> `cleanup_resources` with `self.fd == 0` (closing `stdin`, fd `0`!)!

Let's verify that in `src/transports/datagram/constructors.zig:118-132` and `src/transports/datagram/main.zig:63-65`:
In `new_datagram_transport`:
```zig
const self: *DatagramTransportObject = @ptrCast(@alignCast(
    DatagramTransport.DatagramTransportType.tp_alloc.?(DatagramTransport.DatagramTransportType, 0) orelse return error.PythonError,
));
errdefer python_c.py_decref(@ptrCast(self));

try z_datagram_init(self, protocol, loop, fd);
```
And in `z_datagram_init` (lines 48–58):
```zig
const flags = std.os.linux.fcntl(fd, std.posix.F.GETFL, @as(usize, 0));
if (@as(isize, @bitCast(flags)) < 0) return error.Unexpected;
_ = std.os.linux.fcntl(fd, std.posix.F.SETFL, flags | @as(usize, @bitCast(std.posix.O{ .NONBLOCK = true })));

if (!python_c.type_check(@ptrCast(talyn_loop), Loop.Python.LoopType)) {
    python_c.raise_python_type_error("Invalid event loop\x00");
    return error.PythonError;
}
```
Notice that `self.fd = fd;` is not executed until line 89! Until line 89, `self.fd` is **`0`** (from `tp_alloc` zero-initialization)!
And in `cleanup_resources` (`src/transports/datagram/main.zig:63-65`):
```zig
if (self.fd >= 0) {
    _ = std.os.linux.close(self.fd);
    self.fd = -1;
}
```
So if **anything** in `z_datagram_init` fails before line 89 (such as `fcntl` failing at line 50, `allocator.alloc(u8, 65536)` failing at line 72, or `allocator.create(std.os.linux.msghdr)` failing at line 81), `new_datagram_transport`'s `errdefer python_c.py_decref(@ptrCast(self))` calls `datagram_dealloc` -> `cleanup_resources`, which sees `self.fd == 0 >= 0` and **closes file descriptor `0` (`stdin`)**!

## Trigger Scenario

1. `new_datagram_transport` allocates `self` via `tp_alloc`, which zero-initializes `self.fd = 0` and `self.fixed_buffer_index = 0`.
2. In `z_datagram_init`, if `fcntl` (line 50), `allocator.alloc` (line 72), or `allocator.create` (line 81) fails before line 89 (`self.fd = fd`), `errdefer python_c.py_decref(@ptrCast(self))` runs `cleanup_resources(self)`.
3. `cleanup_resources` sees `self.fd == 0 >= 0` and executes `std.os.linux.close(0)`, closing the process's `stdin` (or whatever socket holds fd `0`)!
4. Similarly, if `self.loop` is set before `self.fixed_buffer_index = -1` is initialized, `self.fixed_buffer_index == 0` causes `cleanup_resources` to release slot `0` of `RegisteredBufferPool`.

## Proposed Remediation

In both `datagram_new` (`src/transports/datagram/constructors.zig:10-13`) and `new_datagram_transport` (`src/transports/datagram/constructors.zig:119-122`), immediately initialize both sentinel fields right after `tp_alloc`:

```zig
self.fd = -1;
self.fixed_buffer_index = -1;
```

## Resolution (2026-10-18)

Applied the proposed remediation, plus an invariant-level guard:

1. `datagram_new` (`src/transports/datagram/constructors.zig`) now sets `instance.fixed_buffer_index = -1` right after `tp_alloc` (alongside the existing `fd = -1`).
2. `new_datagram_transport` sets both `self.fd = -1` and `self.fixed_buffer_index = -1` immediately after `tp_alloc`, before any fallible step.
3. Defense-in-depth: `init_configuration` resets `fixed_buffer_index = -1`, `buffer_ptr = null`, `buffer_len = 0` right after `self.fd = fd`, so ANY future caller (including re-`__init__` paths) unwinds with clean sentinels if a later step fails; on an alloc failure the cleanup now frees the previous heap buffer correctly instead of releasing pool slot 0.
