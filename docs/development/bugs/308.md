# BUG-308 — StreamServer socket double-close on startup failure

- **Status**: 🟢 Fixed (2026-09-07)
- **Severity**: 🔴 Critical — Double-close on server socket file descriptor risking FD hijacking across threads
- **Files**:
  - `src/loop/python/io/server/create_server.zig` (`z_create_server_socket`: lines 421–425 and 473–482)
- **Lessons**: [Memory & Reference Counting](../lessons/01-memory-and-reference-counting.md), [Network Protocols & IO](../lessons/06-network-protocols-and-io.md)
- **Description**:
In `z_create_server_socket`:
```zig
var success = false;
defer if (!success and server_data.socket_fd < 0) std.os.linux.close(fd);
...
const server = create_server_instance(self, server_ptr) catch {
    return null;
};
if (StreamServer.start_serving(server_ptr)) {
    success = true;
} else {
    python_c.py_decref(server);
    return null;
}
```
When `server` is allocated, `server_ptr.socket_fd = fd` assigns socket ownership to the `StreamServer`.
If `StreamServer.start_serving` fails:
1. `python_c.py_decref(server)` calls `streamserver_dealloc` -> `StreamServer.deinit`, which calls `std.os.linux.close(server_ptr.socket_fd)`.
2. The function returns `null`.
3. Because `success` is `false` and `server_data.socket_fd` is still `-1`, the local `defer if (!success and server_data.socket_fd < 0) std.os.linux.close(fd)` fires and executes a second `close(fd)`.
This double-close can close an unrelated file descriptor opened concurrently by another thread.
- **Root Cause**: The defer block relies on `server_data.socket_fd < 0` to determine whether `fd` was handed off, but ownership was already transferred to `server_ptr.socket_fd`.
- **Trigger Scenario**: Server socket bind/listen initialization where `StreamServer.start_serving` fails due to internal queue or socket state errors.
- **Proposed Remediation**: Update `server_data.socket_fd = fd` immediately before instantiating the server, or mark `success = true` once ownership is given to `server_ptr`.

- **Fix (Applied — 2026-09-07)**:
  - `z_create_server_socket` (`src/loop/python/io/server/create_server.zig`): `success = true` now executes immediately after the `StreamServer` constructor returns (its `tp_init` takes ownership of `fd` via `self.server_fd = fd`, and the server's dealloc closes it on every subsequent error path — `start_serving` failure, `PyList_Append` failure). The per-iteration `close(fd)` defer can therefore no longer fire a second close after ownership transfer, while a construction failure (`orelse return`) still leaves `success = false` so the not-yet-owned fd is closed exactly once. Failure paths are `continue`-based, so per-iteration defer scoping is unchanged.
  - Note: the `start_serving` failure path itself is not deterministically triggerable from Python (it requires io.queue exhaustion); the fix is verified by the ownership-order argument plus the full suite.
- **Regression test**: `tests/test_create_server.py::test_create_server_fd_hygiene_across_cycles` — warm-up cycle then 8 create/close cycles asserting zero `/proc/self/fd` drift, catching fd leaks/double-transfer regressions on the server lifecycle paths.
- **Validation (2026-09-07)**: Confirmed still present.
  - Failure path is now `continue`-based with `last_err` collection rather than `return null`, but the ownership flip is unchanged: the `StreamServer` constructor takes `py_fd` (`src/transports/streamserver/main.zig:125` assigns `server_fd = fd`), and `StreamServer.deinit()` (`streamserver/main.zig:34-46`, reached via `streamserver_dealloc`) closes `server_fd >= 0`.
  - `create_server.zig:473-477` decrefs the freshly-created server (refcount 1) on `start_serving` failure → dealloc closes the fd; the per-iteration defer (`create_server.zig:421-424`, condition `!success and server_data.socket_fd < 0`) then closes the same `fd` a second time on `continue` → double-close confirmed.
