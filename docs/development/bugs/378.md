# BUG-378 — `StreamTransport` lifecycle bugs: `close_transports` omits `transport.is_closing = true` and schedules `connection_lost` before write buffer drains, while `close()` + `abort()` invokes `protocol.connection_lost` twice

- **Status**: 🔴 Open
- **Severity**: 🔴 High — violates the fundamental `asyncio.BaseTransport` guarantee that `protocol.connection_lost()` is called **at most once**, and prematurely cancels/closes in-flight writes on `transport.close()`
- **Category**: Logic Bug (Transport State Machine)
- **Files**:
  - `src/transports/stream/lifecycle.zig:28-118, 152-187`
  - `src/transports/write_transport.zig:99-116`
- **Related**: [BUG-16](016.md), [Lesson 55](../lessons/06-network-protocols-and-io.md)

## Overview & Root Cause

In `src/transports/stream/lifecycle.zig`, `StreamTransport` has three interconnected lifecycle state machine bugs:

1. **`close_transports` does not set `transport.is_closing = true` (`src/transports/stream/lifecycle.zig:28-42`)**:
   ```zig
   pub fn close_transports(
       transport: *StreamTransportObject,
       read_transport: *ReadTransport,
       write_transport: *WriteTransport,
       exception: PyObject
   ) void {
       const closed_already = transport.closed;

       read_transport.close() catch |err| std.log.warn("read_transport close failed: {s}", .{@errorName(err)});
       write_transport.close() catch |err| std.log.warn("write_transport close failed: {s}", .{@errorName(err)});

       transport.is_reading = false;

       if (closed_already) return;
   ```
   When `close_transports` is called from `Read.read_operation_completed` on EOF (`src/transports/stream/read.zig:96`) or from `connection_lost_callback` on an I/O error (`src/transports/stream/lifecycle.zig:25`), `transport.is_closing` is **never set to `true`**!
   And if `write_transport` currently has a write in flight or buffered data (`write_transport.write_in_flight or write_transport.buffer_size > 0`), `write_transport.closed` remains `false`, so `maybe_close_fd` at line 92 does **not** set `transport.closed = true` either!
   Consequently:
   - `transport.is_closing()` returns `False` after EOF / I/O error!
   - If the user calls `transport.close()` before the pending write completes, `transport_close` (`line 98: if (instance.is_closing or instance.closed)`) sees both flags `false` and calls `close_transports` a **second** time, scheduling `protocol.connection_lost` **twice**!

2. **Calling `transport.close()` followed by `transport.abort()` calls `protocol.connection_lost` twice (`src/transports/stream/lifecycle.zig:95-118, 152-183`)**:
   - When `transport.close()` is called while a read or write is in flight, `instance.is_closing` is set to `true` and `close_transports` schedules `loop.call_soon(connection_lost, None)`, while `instance.closed` remains `false` (until the read/write cancellation CQE completes and `maybe_close_fd` sets `self.closed = true`).
   - If `transport.abort()` (`transport_force_close`) is called before that CQE completes, line 155 checks **only** `if (instance.closed)` (ignoring that `close_transports` already scheduled `connection_lost` via `call_soon`) and synchronously calls `PyObject_CallOneArg(connection_lost, exc_arg)` at line 178! Then on the next tick, the `call_soon(connection_lost, None)` scheduled by `transport.close()` fires a **second** time!

3. **`transport.close()` cancels the in-flight write and schedules `connection_lost` before buffered writes flush (`src/transports/write_transport.zig:99-116` & `src/transports/stream/lifecycle.zig:83-92`)**:
   Per the Python `asyncio.WriteTransport.close()` specification:
   > *"Close the transport. Buffered data will be flushed asynchronously. No more data will be received. After all buffered data is flushed, the protocol’s `connection_lost()` method will be called with `None` as its argument."*
   Instead:
   - `WriteTransport.close()` (`src/transports/write_transport.zig:105-109`) queues `.{ .CancelIO = self.blocking_task_id }` on the currently in-flight write SQE!
   - `close_transports` (`src/transports/stream/lifecycle.zig:83-90`) schedules `loop.call_soon(connection_lost, exception)` **immediately**, before `write_transport` has finished flushing `pending_buffers` and before `maybe_close_fd` has closed the socket!

## Trigger Scenario

1. Call `transport.write(large_payload)` followed immediately by `transport.close()`. `protocol.connection_lost(None)` fires on the very next loop tick while `large_payload` is still being written to the socket (and the first in-flight write SQE was cancelled via `CancelIO`).
2. Call `transport.close()` followed immediately by `transport.abort()` -> `protocol.connection_lost(None)` is invoked twice.

## Proposed Remediation

1. Set `transport.is_closing = true;` inside `close_transports` (`src/transports/stream/lifecycle.zig:35`).
2. Add a `connection_lost_called: bool = false` guard on `StreamTransportObject` so that `protocol.connection_lost` is scheduled/invoked **at most once** across all combinations of `close_transports`, `transport_close`, and `transport_force_close`, and only **after** `read_transport.closed and write_transport.closed` (when buffered writes have finished draining, or immediately on `force_close` / fatal write error).
3. In `WriteTransport.close()` (`src/transports/write_transport.zig:99-116`), do **not** cancel `self.blocking_task_id` (only `WriteTransport.force_close()` should cancel an in-flight write); allow `flush_buffered_writes` and `write_operation_completed` to finish draining `self.buffer_size` before setting `self.closed = true` and calling `maybe_close_fd`.
